# Library-first vs. moon-first: resolving §0.1

**Summary of the recommendation.** Take **Option C**, but with a much narrower definition of "library-first" than §0.1 currently implies. The evidence from release-please, Nx Release, semantic-release, and knope does *not* support Option B's premise — that callisto has three equally-weighted consumers — because callisto's own design has already decided the GitHub Action is a bash-composite that shells out to the CLI binary (§12.1), not an independent API consumer. That leaves exactly two real consumers: `callisto-cli` and `callisto-moon` — and the second reaches the core through a narrow, enumerated I/O seam (see "Crate-boundary implications" below) and gets no independent API-stability promise, rather than a symmetric second API surface. What the prior art actually validates is not consumer symmetry but **seam placement**: Nx's v21 rewrite was caused by ecosystem I/O logic being smeared into coordination logic, and knope's cascade is permanently trapped inside its binary crate. So: keep the coordination core moon-free and binary-free as a hard, CI-enforced rule; ship moon as the one blessed integration; and do *not* pay for a stable public Rust API, a C ABI, or dyn-compatible traits before v1.0. One concrete correction falls out of this: `MoonProjectGraphResolver` as specced in §15 is the wrong shape and should be deleted — moon's project graph structurally cannot supply the data §7.4's cascade rules need.

## Recommendation: Option C — library-first internals, moon as the single reference integration

### Option B's premise is already false in callisto's own design

§0.1 frames Option B as "moon integration, the GitHub Action, and the standalone CLI are three independent, equally thin consumers." §12.1 of the same document already decided the Action is "composite (bash-in-YAML), not TypeScript," whose logic is "`gh` CLI calls, `callisto` CLI calls, and branching on JSON." That is not a library consumer. It is a *CLI* consumer, and it consumes the `--format json` contract, not a Rust API.

This distinction is exactly what the release-please analogy hides. release-please's Action genuinely is a second library consumer — `release-please-action/src/index.ts:16` does `import {GitHub, Manifest, CreatedRelease, PullRequest, VERSION} from 'release-please'` and calls the same `Manifest.fromConfig`/`fromManifest` the CLI does. But that is nearly free for release-please, because the Action and the library are both Node in the same runtime: importing the library costs one line. For callisto, the equivalent would be a Rust or napi-bound Action binary, and §12.1 explicitly rejected that on supply-chain and auditability grounds. So release-please's proof of "N equally-weighted consumers" does not transfer; it is an artifact of a single-runtime ecosystem.

There is a second reason the release-please analogy transfers less than it looks. `Manifest.fromManifest` does not read a working tree — `parseConfig`/`parseReleasedVersions` (`src/manifest.ts:444-449`) fetch config and manifest JSON through `github.getFileContentsOnBranch(...)`. release-please's world model is a remote-addressable SCM. Its library-first shape bought portability across *hosting* consumers, all of which talk to the same GitHub API. Callisto's consumers all operate on a local checkout with a local project graph. The axis release-please's abstraction was built to span is not an axis callisto has.

One narrower point, not a pillar of the argument: §16 licenses the coordination core AGPL-3.0 with CLA. AGPL doesn't bar consumers, it prices them — first-party consumers (a future callisto-maintained Nx plugin, say) are unaffected, and the CLA exists precisely to sell exceptions to anyone it does deter. So this says nothing about where the seams belong; all it does is lower the expected number of *third-party* consumers, which lowers the option value of a semver-stable public Rust API specifically. The real argument is Nx, knope, and semantic-release below, not licensing.

### But Option A is genuinely dangerous, and knope shows exactly how

knope is the closest structural analogue to callisto that exists (Rust, Cargo + npm dual-published packages, changeset files, `versioned_files` as the base abstraction), and it is a clean cautionary tale. `crates/knope-versioning/src/lib.rs` declares six modules — `action`, `changes`, `package`, `release_notes`, `semver`, `versioned_file` — and there is no `workspace`, `graph`, or `cascade` module anywhere in the library. The entire multi-package cascade mechanism lives in `crates/knope/src/config/package.rs` as two functions, the private `cargo_workspace_members()` (`crates/knope/src/config/package.rs:101-183` — private, confirmed not `pub`, so "unreachable without vendoring" holds at the visibility level too) and `npm_workspaces()` (`:189`), which scan every workspace member's manifest for sibling references and append them to that package's `versioned_files` list so they get rewritten in lockstep. There is no `pub` graph type, no `DependencyGraph`, no reusable API. A second consumer — an editor plugin, a CI action, a moon extension — cannot reach any of it without vendoring that file.

Nx's evidence points the same direction from a different angle. The v21 rewrite (`nrwl/nx#30418`) replaced `ReleaseVersionGenerator` with `VersionActions` (`packages/nx/src/command-line/release/version/version-actions.ts`) precisely because generic logic — git-tag resolution, bump application, cross-group dependent traversal, version-data bookkeeping — had been duplicated per ecosystem plugin and diverged. The bug list Nx attributes to that architecture is a list of exactly callisto's problem domain: cross-release-group dependents not bumped (#21466), duplicate version-data keys when two groups touch one project (#26444, #30363), independent versioning over-incrementing a dependent once per changed dependency instead of once total (#27823), workspace/file-protocol specs not rewritten before publish (#28049). Note that all of these are *coordination* bugs caused by *ecosystem* code owning coordination decisions. Nx's own PR states the fix as a rule: "No core business logic about releases is handled within a `VersionActions` implementation."

That rule is the transferable lesson, and it is a statement about seams, not about consumers. Nx also validated the new abstraction end-to-end against exactly one blessed integration (JS, dogfooded on angular-eslint) before flipping the default in v21 — and even so, early `VersionActions` adopters in 20.8 ate a breaking interface change (`manifestRootsToUpdate: string[]` → `manifestsToUpdate: {manifestPath, preserveLocalDependencyProtocols}[]`) before v21 stabilized. Nx's own team needed two iterations to place the seam correctly *with* a real consumer to test against. Designing three equally-weighted consumer surfaces up front, against two hypothetical consumers, would be strictly worse odds.

semantic-release closes the argument from the other side: a clean library API is necessary but not sufficient. `index.js` exports a callable async function and `cli.js` is a thin yargs wrapper — textbook library-first — and monorepo support *still* had to be built externally (`@qiwi/multi-semantic-release` does `import semanticRelease from "semantic-release"` and wraps the whole thing), because the nine-hook lifecycle in `lib/definitions/plugins.js` extends *what each step does* and cannot change *which packages are processed or when*. The orchestration loop must live in the core. For callisto that means: aggregation (§7.1), graph construction (§7.2), cascade-to-fixpoint (§7.4), group alignment (§7.5), and mutation ordering (§7.6) all belong in library crates, and no integration — moon included — may own any part of that loop. This is P6 restated, and it is the one thing that is non-negotiable under any option.

### The minimal version of library-first, and why it captures ~all the benefit

Yes, there is a minimal version, and it is the right one. It is four CI-enforceable rules, not an API design project:

1. **Zero moon in the dependency tree of the core.** `callisto-format`, `callisto-model`, `callisto-graph`, `callisto-manifests`, `callisto-conventional`, `callisto-changelog` must not depend on `callisto-moon` or on any moon crate, transitively. Enforce with a CI step, not a convention.
2. **The core must build for `wasm32-wasip1` *and* pass its fixture suite under `wasmtime` with only the workspace root preopened.** Compilation alone is a weaker forcing function than it looks: WASI preview1 has a real `std::fs`, and `std::process::Command` compiles (it just fails at runtime via std's `unsupported` PAL shim) — only the `tokio`/`reqwest` class actually fails to build. What breaks under moon's extism host is unpreopened directories and absolute host paths, which is invisible to `cargo build --target` and only shows up at runtime. §11/§10 already commit the core to needing an **exec seam** (`version`'s conventional-commit inference and §P2's stateless `last_tag_for` both need `git`, run via `exec_command` on moon's side) and a **path-resolution seam** (`from_virtual_path`/`to_virtual_path`) in addition to project discovery — enumerate `CommandRunner` and a path/FS trait as core seams alongside `ProjectLocator` below, don't leave them implicit. §9.5 already got the core most of the way there by removing the publish executor; make the wasmtime fixture run a CI job from v0.1, before `callisto-moon` exists.
3. **Compute/apply split, borrowed verbatim from release-please.** `Manifest.buildPullRequests()` / `createPullRequests()` and `buildReleases()` / `createReleases()` (`src/manifest.ts`) is the single most transferable idea in the prior art: every command is a pure function returning a plan value, plus a separate applier that touches disk. Every CLI handler in `src/bin/release-please.ts:483-566` is literally construct-manifest → call one `build*`/`create*` → print. If callisto adopts that split, consumer equivalence is a *consequence* rather than something you design for.
4. **The stable public contract is `--format json` on stdout, not the Rust API — and not `.callisto/plan.json` either.** §7.6 step 10 and invariant 4 (§13) are explicit that `.callisto/plan.json` is `.gitignore`d and "never load-bearing (P2)"; the versioned, fixtured contract per §P7 is the stdout JSON with `schemaVersion` (§9.2), full stop. Fixture the stdout shape, and explicitly document the Rust API of AGPL crates as unstable pre-1.0. This is what lets you take an Nx-style breaking interface change in `DependencyResolver` at v0.3 without it being an ecosystem event.

Everything Option B would add beyond this — a C ABI, semver-stabilized Rust APIs, dyn-compatible traits, a plugin registration surface analogous to release-please's `factories/plugin-factory.ts` — is cost with no identified beneficiary. And release-please shows the symmetry doesn't hold anyway even when you try: `Bootstrapper` (`src/bootstrapper.ts`), which implements the `bootstrap` command, is imported directly by the CLI (`src/bin/release-please.ts:32`) and is **not** re-exported from `src/index.ts`. A capability that matters — first-run config generation — never made it to the public API in a codebase that is otherwise a model of library-first discipline. Assume the same will happen to callisto and decide up front what is *allowed* to be CLI-only glue rather than discovering it as a violated principle. In callisto's case that turned out to be a short list once §11 was actually worked through: `completions` alone (needs shell-integration machinery WASM has no use for) — `tag` and `init`, initially assumed CLI-only here, both resolved WASM-compatible once §11 traced their real dependencies (`tag` only needs `git` via moon's `exec_command`, not a push; `init`'s prompts route through moon's own `initialize_extension` host surface).

## Crate-boundary implications

**Before (§15, provisional):** eight crates — `callisto-format`, `callisto-model`, `callisto-graph`, `callisto-manifests`, `callisto-conventional`, `callisto-changelog`, `callisto-cli`, `callisto-moon` — with `callisto-graph` exposing a `DependencyResolver` trait with two impls, `ManifestWalkResolver` and `MoonProjectGraphResolver`.

**Under "moon-first, don't overthink it" (Option A).** `callisto-model`, `callisto-graph`, `callisto-manifests`, `callisto-conventional`, and `callisto-changelog` collapse into one `callisto-core`, because with no consumer boundary to defend there is no reason to pay for five crate boundaries; only `callisto-format` survives separately as the MIT primitive. `DependencyResolver` disappears — you call `moon project-graph --json` directly and Q1 resolves to "moon is authoritative." `callisto-cli` grows a second, degraded discovery path (an `ignore`-crate walk) that is separately maintained and separately buggy. That is precisely knope's shape, and it is where knope's private `cargo_workspace_members()`/`npm_workspaces()` ended up. The failure mode is not that you can't ship — knope shipped — it is that the moment you want a second surface you vendor or rewrite, and the two discovery paths drift, which is Nx's #21466/#28695 class of bug.

**Under "fully library-first" (Option B).** You add at least two crates and change trait shapes materially. A `callisto-plan` crate holding the plan/report value types and the JSON schema, licensed MIT/Apache since it is the public contract. A `callisto-ffi` (C ABI) or a stable WASM ABI crate for non-Rust consumers, plus the versioning policy and soundness testing that implies. `callisto-graph` plausibly splits into a pure-graph crate and a `callisto-cascade` policy crate so third parties can reuse the graph without inheriting callisto's cascade opinions. Most concretely: **`DependencyResolver` as written in §15 cannot survive.** Its methods return `impl Iterator<Item = &Package>` / `impl Iterator<Item = &DepEdge>`, which is RPITIT and therefore not dyn-compatible. A genuinely open plugin boundary requires `Box<dyn DependencyResolver>`, which forces every method to `Box<dyn Iterator<Item = …> + '_>` — the same shape `Manifest::iter_dependencies` already has. That is a real, independently-confirmed runtime and ergonomics cost (RPITIT has been non-dyn-compatible since its 1.75 stabilization, with no stabilized escape hatch as of this writing) paid to serve a third-party-consumer population that AGPL-3.0 + CLA (§16) makes small — not zero, and not "unable to exist," just a smaller expected audience than the API-stability cost assumes. `callisto-manifests`'s `Manifest` trait would likewise need to be publicly implementable and therefore frozen early.

**Under the recommendation (Option C).** The eight crates stay as-is, plus one addition (see
change 3 below, since it isn't optional once `DependencyResolver`'s second-implementor
question is taken seriously). Four specific changes:

1. **Delete `MoonProjectGraphResolver`.** This is a correctness change, not a stylistic one. moon's project graph does not carry version requirements. `crates/config/src/project/dep_config.rs` defines `ProjectDependencyConfig { id: Id, scope: DependencyScope, source: DependencySource, via: Option<String> }` — `scope` is `Build | Development | Peer | Production | Root`, `source` is `Explicit | Implicit`, and `via` is provenance metadata. There is no version-requirement string anywhere on the edge or its `ProjectDependsOn` wrapper, including for implicit edges injected by toolchain plugins through `ProjectGraphBuilder::extend_with_dependency` (`crates/project-builder/src/project_builder.rs:211-224`), which merely stamps `source = Implicit` on the same struct — verified independently against both current `main` and the tree at commit `50d91a0` (a docs-only commit that happens to be current tip-of-main at time of writing, not one that touched this file; cite it only as "state of main as of writing," not as the commit that introduced the struct). §7.4's entire cascade table pivots on "spec covers new version," and §7.3's `DepSpec` requires the original spec string for lossless round-trip. moon cannot supply either. A `MoonProjectGraphResolver` would have to re-read the manifests to fill in what it's missing, at which point it *is* `ManifestWalkResolver`.

2. **Introduce a narrower trait — `ProjectLocator` — for discovery, and treat edge cross-checking as a separate, lossy-mapped concern.** This actually resolves two different sub-questions from §18 Q1, not one:
   - **Q1a (discovery — moon is authoritative when present).** `fn projects(&self) -> Result<Vec<ProjectRoot>, LocateError>`, with `IgnoreWalkLocator` in `callisto-graph` and `MoonProjectLocator` in `callisto-moon`. When moon is available its project roots supersede the `ignore` walk outright — this is where moon adds real, unambiguous value (catching an implicit edge or a `moon.yml`-declared project the manifest walk has no way to see at all).
   - **Q1b (edges — cross-check only, explicitly lossy).** An optional `fn declared_edges(&self) -> Option<Vec<DeclaredEdge>>` where `DeclaredEdge` is a **callisto-owned** type in `callisto-model` (`{from: PackageId, to: PackageId, kind: DeclaredEdgeKind, via: Option<String>}`) — not moon's `DependencyScope` reused under a colliding name, which would either violate rule 1 (moon type leaking into the core's dependency tree) or silently drop the fact that the mapping is lossy: moon has `Root` and no `Optional`; moon's `Production` doesn't cleanly separate from callisto's `Runtime`+`Optional` split, which matters specifically for the napi `optionalDependencies` pattern §7.5 exists to serve. `MoonProjectLocator` owns an explicit, documented `DependencyScope → DeclaredEdgeKind` mapping; the cross-check compares edge *presence* (plus `via` for a human-readable diagnostic), never kind equality. Disagreement policy: warn by default, `--strict-graph` hard-fails, and surface it as a field in `--format json` output so the Action/moon workflow can gate on it — this is what makes §18 Q1's "disagreement is itself a useful diagnostic" promise real instead of silently dropped.

   This also shrinks the moon integration to something a WASM extension can actually do well, and maps cleanly onto Nx's `VersionActions` rule: moon supplies discovery I/O, the core owns all coordination. One risk to name rather than discover later: `ProjectLocator`'s shape is exactly the kind of trait Nx's own `VersionActions` rewrite shows breaking under a real second consumer (`manifestRootsToUpdate: string[]` → `manifestsToUpdate: {...}` inside one Nx minor). Treat `ProjectLocator`/`declared_edges` as expected to break pre-1.0, and prefer a versioned DTO (`callisto-moon` producing a `ProjectSet` value type owned by `callisto-model`) over a long-lived trait contract where practical — data contracts version more gracefully than trait signatures. `callisto-moon` should pin a specific moon compatibility range accordingly.

3. **`DependencyResolver` keeps `-> impl Iterator` and static dispatch, and needs a named second implementor to justify keeping the trait at all.** No boxing, no dyn-compatibility, no pre-1.0 stability promise — but after change 1 deletes `MoonProjectGraphResolver`, `ManifestWalkResolver` is the *only* implementor, and a one-implementor trait is exactly the "cost with no identified beneficiary" this doc argues against for Option B elsewhere. The legitimate second implementor is a fixture/in-memory resolver for the `callisto-fixtures` golden-test suite (construct a graph from literal `Package`/`DepEdge` values, no filesystem, for cascade unit tests) — keep the trait and name that as the reason. If that suite ends up not needing one, demote `DependencyResolver` to a concrete `ManifestWalkResolver` struct and let §15's "moon-agnostic core" commitment be carried by the CI rule in rule 1 instead of by trait shape. Document `callisto-graph`'s Rust API as unstable in its README either way; the supported contract is `--format json` + `schemaVersion` on stdout.

4. **Plan/report types live in `callisto-model`, licensed MIT/Apache with `callisto-format`.** The §9.2 plan is the public contract per P7; putting it in the permissive tier means the Action, a future Nx plugin, and anyone writing a consumer can depend on the schema types without touching AGPL code. `callisto-cli` then contains only argv parsing, rendering, and process-level I/O — the release-please `bin/release-please.ts` shape — and mutation (§7.6 steps 3-8) lives in `callisto-manifests`/`callisto-changelog`, not in the binary crate.

One addition, not optional: a ninth crate, `callisto-fixtures` (dev-only, unpublished), holding the byte-compat corpus and plan-schema golden files shared by `callisto-cli` and `callisto-moon` tests (P7's "fixtured contract" made literal) — this is what change 3 above actually cites as `DependencyResolver`'s second implementor, so it's load-bearing for that trait's justification, not a nice-to-have. Alongside it, a CI rule that `callisto-cli/src` contains no graph construction or cascade code — the automated version of "don't become knope."

## Secondary question: group-priority / simultaneous release groups

**Confirmed: callisto does not need a group-priority mechanism, and pre-release mode is not why.**

release-please's `GroupPriority` plugin (`src/plugins/group-priority.ts:53-74`) is a post-processing filter over already-computed `CandidateReleasePullRequest[]`: it buckets candidates by `pullRequest.group`, walks a maintainer-ordered `groups: string[]`, and returns only the highest-priority non-empty bucket, discarding every lower-priority candidate for that run. It exists because release-please's `Manifest.buildPullRequests()` runs independent per-path strategies that can each independently decide "I want to release now," and `group` is a *label on candidates*, not a versioning constraint. Two labelled candidate sets can therefore collide and need arbitration — the canonical case being Java snapshot PRs vs. stable-release PRs.

Callisto's model forecloses this by construction, for three independent reasons. Fixed and linked groups (§7.5) are inputs to version *computation*, not labels on emitted candidates — members are forced to a shared version before any plan exists. Callisto emits exactly one plan per invocation; there is no multi-strategy pass that can produce competing candidate sets. And §8 makes the `snapshot` subcommand and pre-mode mutually exclusive, which is precisely the dual-track scenario `GroupPriority` arbitrates.

So the answer is not "pre-release mode covers it" — pre-mode is single-track and is itself one of the reasons the collision can't arise. The correct framing is that callisto has no dual-channel concept at all. Two follow-ons:

- **Add config-parse-time validation instead of runtime arbitration** (P5): a package must belong to at most one fixed group and at most one linked group, and fixed ∩ linked must be empty. Reject at parse time with a clear error. Multi-group membership is the closest analogue to release-please's colliding-labels problem, and rejecting it is strictly better than arbitrating it.
- **Heed the `#2207` lesson about identity resolution.** `googleapis/release-please#2207` (Node project wrapping a Rust workspace — structurally callisto's case F) has sat open since Jan 2024 with no maintainer comment; `linked-versions` silently no-ops under `include-component-in-tag: false`, and the two candidate fixes (`#1749` open since March 2023, `#2211` closed unmerged) were never reviewed. `LinkedVersions.preconfigure()` keys off `strategiesByPath` while component identity is derived through tag-parsing logic that the tag-inclusion flag perturbs — two code paths for one concept. For callisto: `PackageId` → tag name resolution must be **one function** in `callisto-model`, used identically by §7.5 group forcing, `plan-publish`'s `releases[].tagName`, and the §P2 stateless `last_tag_for` primitive. If `tag_template` (§5.1) can change a package's identity for one of those three and not the others, you have rebuilt #2207.
- **Revisit only if** callisto ever adds a genuine dual-channel feature (same package, two cadenced release lines from the same commits) or relaxes the pre/snapshot mutual exclusion. Note the trigger in the design doc so the decision is revisitable rather than forgotten.

## Secondary question: 0.x remap rigidity (§6.2)

**Revised — but not in the direction the research implied.** Keep §6.2 rigid and unconditional. Add the opt-in one layer up, in §7.1's inference, never in `bump_version`.

The case for adding a `bumpMinorPreMajor` equivalent is real: it originates in `googleapis/release-please#558`, opened by a user citing SemVer's clause-4 carve-out and the Rust API guidelines' `C-STABLE` as the reason libraries are deliberately held at 0.x — verbatim callisto's audience. `DefaultVersioningStrategy` (`src/versioning-strategies/default.ts:27-105`) implements both `bumpMinorPreMajor` and `bumpPatchForMinorPreMajor`, defaulting to `false`, rerouting breaking → `MinorVersionUpdate` and `feat` → `PatchVersionUpdate` when `version.isPreMajor`. And the demand has been sustained: #2087 ("initial version 0.0.0 means pre-major options are not respected," still open, `help wanted`) and #2635 ("pre-major settings being ignored," Dec 2025) show the feature is load-bearing enough that people file bugs about it years later.

But applying that directly to §6.2 would be a mistake, for two reasons.

**First, this extends P1, and the extension only holds for `Changeset`-trigger packages.** P1 as written is byte-compatibility of the *file format*; nothing in it literally forbids a remap flag. The stronger claim — that P1's adoption-gate spirit implies *semantic* equivalence of computation, not just file round-trip — is a real and defensible extension, not a citation, and it only holds where a changeset file is the input: a remap flag there would mean callisto computes a *different version* than `@changesets/cli` from the *identical* file, destroying one-commit rollback. It does not extend to `Auto`-trigger packages, which live entirely outside the changesets model — there is no `@changesets/cli` computation to diverge from, because changesets doesn't have conventional-commit inference at all. That's exactly why the inference-layer flag below is admissible and a `bump_version` flag is not: the line is "does a changeset file exist for this package," not "is this a bump."

**Second, and more interesting: release-please's flag corrects an *inference*, not an explicit human decision.** In release-please, "major" arrives because a commit said `feat!:` — the human never chose a bump level, so remapping is a reasonable correction of a heuristic. In callisto, `major` in a changeset frontmatter is a human typing `major` next to a package name. Silently turning that into `0.6.0` overrides stated intent, and it is exactly the "why did my patch bump become a minor" surprise that generated #2635.

Callisto does, however, have release-please's actual situation: `ReleaseTrigger::Auto` (§5.1, §7.1) infers severity from conventional commits when no changeset names the package. **That** is where the flag belongs. Concretely:

- `callisto-format`'s `bump_version` stays exactly as §6.2 specifies — `0.5.2 + major → 1.0.0`, no exceptions, no flag, no config reaching it. It stays in the MIT crate as the canonical Rust implementation of changesets semantics, and its fixtures stay a pure byte/behavior-compat suite.
- Add an opt-in inference policy in `callisto-conventional`, per-package or per-group, e.g. `pre-major-inference = "conservative"`, that maps `breaking → Severity::Minor` and (separately gated) `feat → Severity::Patch` **when producing a severity for an `Auto`-trigger package whose current version is `0.y.z` with `y > 0`**. Default off.
- §7.1's existing rule — "a changeset always wins over inference" — means an explicit `major` still produces `1.0.0` under any setting. That is the right semantics and it falls out for free.
- **Specify the bootstrap interaction explicitly**, because that is where release-please is still leaking bugs three years on. If the current version is `0.0.z`, or there is no prior tag, the policy is inert: no remap, and the tool says so. #558's original thread traced failures to `defaultInitialVersion` defaulting to `v1.0.0` regardless of the flag; #2087 is the same disagreement at `0.0.0`. Callisto's §P2 stateless detection makes "no tag yet" a routine state, so this must be a tested case from day one, not an emergent one.
- **Document the divergence loudly.** `@changesets/cli` has no remap concept. Anything callisto infers that changesets couldn't have inferred is a divergence, and the migration guide (v0.4) should say so in the same breath as the one-commit-rollback promise — rollback is only lossless for `Changeset`-trigger packages.

Net effect: callisto gets the feature its Rust audience asks for, structurally cannot reproduce release-please's #558/#2087/#2635 bug class (because the remap never touches the bump primitive and never overrides explicit intent), and P1 stays intact.
