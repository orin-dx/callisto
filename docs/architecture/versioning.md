# Plan and apply

How `callisto version` turns changesets into file edits, and where interrupted-command recovery stops. Behavior: [`docs/specs/versioning.json`](../specs/versioning.json). Write mechanics: [ADR 8](../adr/0008-format-preserving-writes-gated-by-apply-permit.md). The emitted decision: [ADR 2](../adr/0002-committed-decision-is-release-authority.md).

## Two phases

| Phase | Entry point | Touches disk |
| --- | --- | --- |
| Plan | `commands::plan_version` (`crates/callisto-graph/src/commands/version.rs`) returns a `VersionPlan` | No |
| Apply | `apply_version_plan` (`crates/callisto-graph/src/apply.rs`) | Yes; takes `&ApplyPermit` |

- `VersionPlan` (`crates/callisto-graph/src/plan.rs`) is the whole change: bumps, dependency spec rewrites, platform manifest writes, owner `optionalDependencies` pins, changelog sections, consumed changesets, `pre.json` updates and diagnostics. It is in memory only (no `Serialize`).
- A changelog section is `## {version}`, a date and compare-link line, then Major, Minor and Patch Changes groups (`[changelog] layout = "grouped"`, the default), or the heading and one bullet list (`"flat"`). `render_section` is pure: the planner puts the layout, the UTC date and the link in `ChangelogInput::style`, and the link needs a GitHub repository (`[release] forge-repository`, else the `origin` remote) plus a tag on the previous version. Readers (`find_section`, `has_heading`, release notes) key on the `## {version}` line only, so they read both layouts; a fixed group's release notes file each member's entries under the bump group the member recorded them in.
- `plan_version` is shared: `version`, `status`, `compose-pr-body` and `release plan --package` all compute the same plan.
- `crates/callisto-graph/src/changelog/markdown/` is the only place Markdown is scanned: fenced code, ATX headings, heading rebase, the headline split and `Breaking:`/`Action:` markers (`markers.rs`). A new pass asks those questions there and joins `corpus.rs`; it does not write its own line scanner.
- `ReleasePreview` (`crates/callisto-graph/src/release_preview.rs`) is the serializable, versioned view of a plan for people: packages, merged changes, bystanders and findings. Surfaces such as the PR body render it; they do not recompute from the plan. `version --emit-preview` writes it before apply consumes the changesets, and `compose-pr-body --preview` renders from that file. `ReleasePreview` also carries findings from the changesets (a `Breaking:` or `Action:` marker, and no \"backward compatible\" claim when there is a breaking one) and `unreleased`, the publishable packages with source changes since their last tag that the plan does not bump (`version --emit-preview` computes it; a failure to look is a warning). `pr_labels()` derives the managed label catalog, with an `applied` flag per label, from the same findings. `--publish-plan` adds `publish`, the outcome of `plan_workspace_release_offline` on the versioned tree for exactly the packages the preview bumps (the committed decision holds those, not every unreleased package). It never observes a registry or the forge, so the checks that need one (a published version left behind, a name another project owns) are left to the release itself; a refusal becomes a `Stop` finding. Rows are keyed by the qualified release identity, so `cargo/x` and `npm/x` stay apart.
- `changed_source_files_since_last_tag` lists, per package, the files that differ from its last tag after dropping `DEFAULT_IGNORED_PATHS` (tests, benches, examples, snapshots, Markdown), and `uncovered_changes` returns the changed packages that no pending changeset, nor any member of their fixed or linked group, covers. Neither is wired into the CLI or the PR body yet.
- A dry run never gets a permit, so it reports the plan and never calls apply.
- `snapshot` applies with `ApplyOptions::transient`: manifests are written, while changelogs, changeset deletion and git staging are skipped.

## Idempotent apply

A crash can stop apply after some files are written. Applying the same in-memory plan again is file-level idempotent; a fresh command does not retain that plan.

- Each `PlannedBump` carries `from` and `to`. Before writing a manifest (or a platform manifest), apply reads its current version: `from` means write, `to` means already done, anything else is `UnexpectedManifestVersion`.
- A manifest already at `to` is still staged: the crashed run may have written it without `git add`.
- Apply refreshes affected lockfiles and stages generated version state before consuming changesets or exiting `pre.json`. It stages input deletions with `git rm --cached --ignore-unmatch` before removing the files from disk, so a failed index update leaves the inputs available for recovery. A fresh command does not retain the in-memory plan and can refuse already-stable staged outputs; E121 directs the user to inspect both diffs and finish consuming retained inputs only when the staged outputs are verified. Automatic replay is not guaranteed.
- A Cargo member that inherits its version (`version.workspace = true`) is pinned to a literal version when it is bumped, and `[workspace.package]` is never written, so a member that still inherits keeps the shared version. A bump of every member of a fixed group pins each of them.
- `ApplyOutcome::staged` lists every path apply staged.

## Command boundary and known gaps

`version --emit-decision` derives and validates the decision before writes, applies the plan, and writes the decision only after apply succeeds. The decision file is not wrapped in the stdout report envelope. `--emit-preview` follows the same rules: it is refused with `--dry-run`, built only from a plan without errors, and written after apply succeeds. A relative path for `--emit-decision` is relative to the workspace root, because it names a committed repository file; every other file flag (`--emit-preview`, `compose-pr-body --preview`, and the hidden `release` and `release-pr` flags `--intent`, `--receipt`, `--out`, `--artifact-dir`, `--input`, `--artifact-manifest`, `--source-root`) is relative to `--cwd`, like `git -C`. An absolute path is used as given.

Outside `mode: pre`, `check_partial_run` refuses with E121 when a canonical manifest's effective version differs from `HEAD` while a changeset remains in `HEAD` or in the working tree (including untracked files), or when a canonical manifest with an effective staged version change is present in the index. Staged metadata-only edits are allowed. During `mode: exit`, prerelease versions awaiting stable finalization remain eligible, but changed stable versions are not exempt from the retry guard. It does not restore a lost plan. Apply retains changesets and pre-state deletion inputs until lock refresh and staging of generated state succeed, then stages their removal before unlinking them from disk. A late `--emit-decision` write failure is actionable refusal, not automatic replay of an in-memory plan that no longer exists.

Apply refreshes each existing lockfile for every ecosystem represented by an actual version, dependency, platform or optional-dependency write, including dual-manifest packages and workspace-root Cargo writes. Cargo lockfiles are refreshed and staged per Cargo workspace, in that workspace's directory. Dependency cascade, co-release floor and snapshot rewrites resolve names in each declaration's native manifest context; pnpm workspace protocols and aliases remain distinct inputs. These behaviors are covered by the [versioning contract](../specs/versioning.json).
