## 2. Key Technical Concepts

- **`[[package-set]]`** — bulk config-override mechanism in `callisto.toml`. Uses glob patterns (NOT `PackageId` exact match). Applies to ALL packages whose name matches the glob. `[[package]]` always takes priority over `[[package-set]]` for the same package.
- **`PackagePattern`** — a new type in `callisto-graph/src/config/pattern.rs` wrapping `globset::GlobMatcher`. Has `matches(&PackageId) -> bool` that tests `id.name()` against the glob.
- **`PackageId::matches()`** — existing method that does exact OR bare-wildcard matching. `Bare("foo").matches(Prefixed(Cargo, "foo"))` → true; `Bare("foo").matches(Prefixed(Npm, "foo"))` → also true. This is Track E's concern.
- **Idempotent apply** — `apply_version_plan` should check current manifest version against `bump.from`/`bump.to` before writing. Three cases: at-from → write; at-to → skip write but still stage; at-neither → `Err(UnexpectedManifestVersion)`.
- **`ApplyPermit`** — capability token required for all mutating operations.
- **`WorkspaceCargoResolver::workspace_version()`** — new method reading `[workspace.package] version` from an already-parsed document. Needed for idempotency guard on CargoWorkspacePackage writes.
- **Semantic Model approach** — spec concepts (PackageId, Workspace, VersionPlan, ApplyOutcome, PublishPlan), not features. Invariants numbered per concept. Tests named after invariant numbers.
- **`VersionPlan` serializability** — `VersionPlan` and `PublishPlan` already derive `Serialize`/`Deserialize`/`JsonSchema` but are never persisted. Major missed opportunity (Release Please pattern).
- **`PackageMatchedNothing`** — error variant exists in `ConfigError` but is never emitted anywhere. Config rules that match no packages silently succeed.
- **Track E** — `identity.rs::matches()` is unchanged. Bare PackageId still matches any ecosystem. In a polyglot workspace with `cargo:foo` AND `npm:foo`, a `[[package]] match = "foo"` rule applies to both packages identically.

### `crates/callisto-graph/src/config/pattern.rs` (CREATED THIS SESSION)
New file. `PackagePattern` wraps `globset::GlobMatcher` for glob-based package name matching in `[[package-set]]` blocks.

```rust
use callisto_model::PackageId;
use globset::{Glob, GlobMatcher};

#[derive(Clone, Debug)]
pub struct PackagePattern {
    raw: String,
    matcher: GlobMatcher,
}

impl PackagePattern {
    pub fn parse(s: &str) -> Result<Self, globset::Error> {
        let glob = Glob::new(s)?;
        Ok(Self {
            raw: s.to_string(),
            matcher: glob.compile_matcher(),
        })
    }

    pub fn matches(&self, id: &PackageId) -> bool {
        self.matcher.is_match(id.name())
    }

    pub fn as_str(&self) -> &str { &self.raw }
}
```

## 8. Current Work

The user asked (in the final message) for Track E analysis — text only, no tools. This is the immediate task.

**Track E background:**
- `identity.rs::matches()` behavior: `Bare("foo").matches(Prefixed(Cargo, "foo"))` → true; `Bare("foo").matches(Prefixed(Npm, "foo"))` → also true
- In `walk.rs`, config rule application: `cfg.packages.find(|(p,_)| p.matches(&id))` — for each discovered package, finds the first matching rule. If `[[package]] match = "foo"` is in config and both `cargo:foo` and `npm:foo` are discovered, the SAME rule applies to BOTH packages.
- `[[package-set]]` using `PackagePattern::matches()` also only checks `id.name()`, ignoring ecosystem — by design (glob semantics apply across ecosystems)
- Track E asks: should `[[package]] match = "foo"` (bare name) apply to all ecosystems or be restricted?

**The design question:** Is it a bug or a feature that a bare `[[package]]` name pattern applies to multiple ecosystems?

**The key distinction:**
- For `[[package-set]]`: Multi-ecosystem application is DESIRED — that's the whole point of a bulk override
- For `[[package]]`: The user likely intends ONE specific package; applying to multiple is probably accidental

**Proposed resolution:** The fix should NOT change `PackageId::matches()` itself (that would break legitimate uses). Instead:
- After workspace walk (in the same validation pass that would emit `PackageMatchedNothing`), check if any bare-name `[[package]]` rule matched packages in more than one ecosystem. If so, emit a diagnostic warning recommending the user use an ecosystem-prefixed pattern like `cargo:my-lib`.
- This connects Track E to the config validation work — they're the same validation pass, checking different invariants.
- `[[package-set]]` is exempt from this warning because multi-ecosystem application is its explicit purpose.
- This is backwards-compatible (warning not error), gives operators time to migrate configs.
