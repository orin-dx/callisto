Some more context on matrix:

On callisto matrix itself — the underlying design is actually solid: once napi.targets is declared, it resolves each triple to hostRunner/useCross/artifactName (verified in callisto-graph/src/matrix.rs) — exactly the three things a GH Actions matrix job needs, covering 18 known triples. So the mechanism itself doesn't need rework. Two real gaps worth raising upstream though:

1. Silent-empty is a bad failure mode. callisto matrix returning {} for a package that clearly looks like a napi package (has @napi-rs/cli as a devDependency, a napi build --platform script) but hasn't declared napi.targets gives zero signal that anything's missing. Worse: callisto validate said "Validation passed" despite this gap — its own readiness check doesn't catch it. This cost real time to trace through source. Callisto-side fix: validate/status should emit a diagnostic when a package looks napi-shaped but has no napi.targets declared.
2. No reference pattern for the actual multi-job release flow. Checked callisto's own docs and every sibling org repo (lumen, monokl, prism) — none demonstrate the "matrix → per-platform build → collect artifacts → publish" pipeline this feature exists to drive. nativeMatrix as a callisto-action output is also structurally awkward — it's only populated mid-way through the actual publish attempt, too late to define a job-level strategy.matrix from it in the same run. The raw callisto matrix CLI works fine called standalone/early (bypassing callisto-action for that step, which is what I'd do for michi), but that's not documented anywhere as the intended pattern.
