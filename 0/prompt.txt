### [High] `add` and `pre` ignore `ws.config.changesets_dir`, always write to `.changeset/`

- **Status**: CONFIRMED — execution fully traced
- **Location**: `commands/add.rs:L180,L183`, `commands/pre.rs:L70-L71`
- **Classification**: Silent Fallback / Spec Drift
- **Root Cause**: `ResolvedConfig` (in `callisto-graph/src/config/resolve.rs:L17`) exposes `changesets_dir: PathBuf`, populated from `callisto.toml`'s `[changesets] dir` field, defaulting to `".changeset"`. `Workspace` re-exposes it as `pub config: ResolvedConfig` (`lib.rs:L53`). The graph layer reads `cfg.changesets_dir` correctly (`aggregate.rs:L46`). But `add.rs` hardcodes the path in two separate places:
  ```rust
  // add.rs:180
  let changeset_dir = ws.root.join(".changeset");
  // add.rs:183
  let rel_path = format!(".changeset/{filename}");
  ```
  And `pre.rs` does the same despite having a `PRE_JSON_REL` constant:
  ```rust
  // pre.rs:70-71 (enters the changeset dir via hardcoded literal)
  let pre_dir = ws.root.join(".changeset");
  let pre_path = pre_dir.join("pre.json");
  ```
  Both should be `ws.root.join(&amp;ws.config.changesets_dir)`.
- **Failing Scenario**: User sets `[changesets]\ndir = "my-changes"` in `callisto.toml`. `callisto status`/`callisto version` read from `my-changes/` (graph layer uses `changesets_dir`). `callisto add` writes to `.changeset/` (hardcoded). All newly written changesets are invisible to subsequent commands.
- **Severity**: High — functional mismatch silently discards all changesets when a non-default dir is configured
- **Verification Strategy**: Add `[changesets]\ndir = "custom-cs"` to a fixture `callisto.toml`, run `callisto add --package foo:patch --summary test`, assert the file appears under `custom-cs/`, not `.changeset/`.

### [High] `publish --dry-run` emits `PublishPlan` JSON; real run emits `PublishReport` JSON — no discriminating field

- **Status**: CONFIRMED
- **Location**: `commands/publish.rs:L35`, `commands/publish.rs:L51`
- **Classification**: Spec Drift / Silent Fallback
- **Root Cause**: The dry-run branch calls `write_json(&amp;mut std::io::stdout(), &amp;plan)` where `plan: PublishPlan`, while the real-run branch calls `write_json(&amp;mut std::io::stdout(), &amp;report)` where `report: PublishReport`. These are structurally different types: `PublishPlan` contains `releases: Vec&lt;PublishTarget&gt;`, while `PublishReport` contains `attempts: Vec&lt;PublishAttempt&gt;`. No `dryRun` field is emitted in either path. A JSON consumer receiving output from `callisto publish --format json` cannot determine whether they are looking at a plan or a publish report without schema introspection.
- **Failing Scenario**: A CI consumer parses `callisto publish --format json --dry-run` expecting to get the same schema as `callisto publish --format json`. The field `attempts` is absent (replaced by `releases`), and the `status` per-package field is absent entirely.
- **Severity**: High — breaks any downstream consumer that handles both modes
- **Verification Strategy**: Run `callisto publish --format json --dry-run | jq .releases` and `callisto publish --format json | jq .attempts` — only one of each pair will be non-null.

### [Medium] `add.rs` slug `unwrap_or(0)` silently collapses to a single fixed slug when the system clock is before UNIX epoch

- **Status**: CONFIRMED
- **Location**: `commands/add.rs:L266-L270`
- **Classification**: Silent Fallback
- **Root Cause**:
  ```rust
  let timestamp = std::time::SystemTime::now()
      .duration_since(std::time::UNIX_EPOCH)
      .map(|d| d.as_nanos())
      .unwrap_or(0);
  ```
  When `SystemTime::now() &lt; UNIX_EPOCH` (misconfigured system clock, or container with a broken clock), `duration_since` returns `Err`. The fallback is `0`. With timestamp `0`, all three modulo operations produce index 0, so every invocation of `generate_human_slug()` returns `"swift-foxes-run"`. Since `atomic_write` will then overwrite the same destination filename for every `add` invocation, all but the last changeset are silently destroyed.
- **Failing Scenario**: Container with clock set to 1969-12-31. Every `callisto add` writes to `.changeset/swift-foxes-run.md`, each silently overwriting the prior one.
- **Severity**: Medium — data loss under a reachable (misconfigured-clock) condition
- **Verification Strategy**: In a unit test, replace `SystemTime::now()` with a seeded constant of `0` and assert that multiple calls still produce distinct slugs (they won't — this is the failing assertion).

### [Medium] `pre.rs` JSON output hardcodes `"pre"` and `"exit"` as string literals instead of serializing `PreMode`

- **Status**: CONFIRMED — divergent serialization paths verified
- **Location**: `commands/pre.rs:L90,L113,L151,L162`
- **Classification**: Spec Drift
- **Root Cause**: `PreMode` has `#[serde(rename_all = "lowercase")]` in `callisto-format/src/pre.rs:L40`. `write_pre_json` correctly goes through `serde_json::to_value(state.mode)` (L132 of `pre.rs`) — so the `.changeset/pre.json` file always gets the enum's canonical serialization. But the CLI's own stdout JSON output for `--format json` hardcodes the strings:
  ```rust
  // L113 — real enter path
  "mode": "pre",
  // L162 — real exit path
  "mode": "exit",
  // L90 — dry-run enter preview
  preview(global, "pre", &amp;tag, &amp;text)?;
  // L151 — dry-run exit preview
  preview(global, "exit", &amp;pre_state.tag, &amp;updated)?;
  ```
  These four strings are a manual copy of the serde rendering. The `.json` file and the CLI JSON stdout now have two independent serialization paths for the same enum. If `rename_all` is changed or a new variant is added, they will diverge silently.
- **Severity**: Medium — latent spec drift; currently correct but mechanically fragile
- **Fix direction**: Use `serde_json::to_value(PreMode::Pre).unwrap()` and `serde_json::to_value(PreMode::Exit).unwrap()` at the four call sites, or serialize a `PreMode` value directly via the `json!` macro.

### [Low] `add.rs` slug generation uses magic bit-shifts `&gt;&gt; 4` and `&gt;&gt; 8` with no explanatory comment

- **Status**: CONFIRMED
- **Location**: `commands/add.rs:L272-L273`
- **Classification**: Hardcoded Constant / Magic Number
- **Root Cause**:
  ```rust
  let a = adjectives[(timestamp as usize) % adjectives.len()];
  let n = nouns[((timestamp &gt;&gt; 4) as usize) % nouns.len()];
  let v = verbs[((timestamp &gt;&gt; 8) as usize) % verbs.len()];
  ```
  The shifts 4 and 8 are chosen to use non-overlapping bit ranges of the nanosecond timestamp, spreading selections across the three word lists. No comment explains this. The modulo against `.len()` (correct, dynamic) means the array sizes are not brittle. However the effective collision domain over any 5.12µs window (`20 × 256ns`) is only `20 × 16 × 1 = 320` distinct slugs (verb repeats every 5.12µs, noun repeats every 320ns). Two `callisto add` calls within the same nanosecond window can only produce one of 16 `(adj, noun)` pairs for any given verb.
- **Note**: The `% adjectives.len()` pattern is correct and will adapt automatically to word-list changes. Only the shift constants are magic.
- **Severity**: Low — affects slug uniqueness guarantees under rapid sequential calls but not correctness of the overall flow
