  ## Design decisions
  
  **Model.** `ReleaseOperationRole::ForgePublish` added (wire `forgePublish`), with `ReleaseOperationId::forge_publish` / `ReleaseOperation::forge_publish` and `operation_id_text` -> `"forge-publish"` (so it enters the intent digest). `ReleaseIntentV1::SCHEMA_VERSION` 2 -> 3.
  
  **DAG.** `Tag` -> `ForgeRelease` (draft) -> every `ArtifactUpload` -> `ForgePublish`. `ForgePublish` is derived for *every* package that has a forge release, with prerequisites `[ForgeRelease] + all uploads of that package` — including the zero-upload case. Built in its own pass after the artifact-slot pass in `derive_release_inputs`, so it cannot miss slots. `canonical_operation_order` needed no change (generic topological sort).
  
  **Evidence.** `ProviderEvidenceV1::ForgeRelease` now serves both forge roles. `matches_role` became `check_role -> Result<(), EvidenceRejection>` so a `draft: true` release paired with `ForgePublish` is rejected by a *distinct* typed error, `ProviderObservationError::DraftReleaseCannotProvePublication`, rather than being folded into `EvidenceRoleMismatch`.
  
  **Prerelease.** One source: `Version::is_prerelease()` — the same call that computes the npm `next` dist-tag in `derive.rs`. It is read once per operation at derivation and carried on the prepared operations (`ForgeReleaseOperation`, `ArtifactUploadOperation`, `ForgePublishOperation` each gained `prerelease: bool`); no provider re-derives it.
  
  **Lookup.** `github_release_by_tag` is now private; `github_release_for_tag` is the one lookup all three roles share: tag endpoint first, then a bounded scan of `GET /releases?per_page=100&page=N` (max 10 pages, stops on an empty page). Both use the existing `retry_observation` + `timeouts::FORGE_API`. `malformed_github_response` extracted (artifact.rs was hand-rolling the same `ReleaseCommand` construction).
  
  **Observation.** Tag mismatch -> `ForgeReleaseDiffers`. Prerelease-flag mismatch -> new `ProviderConflictReason::ForgeReleasePrereleaseDiffers`. `ForgeRelease` is Exact for draft *or* published; `ForgePublish` is Exact only when `draft: false`, `Absent` while still a draft. Not found -> `Absent`. Both effects re-observe exactly as the other roles do; `ForgePublish`'s post-effect conflict is the new `RemoteConflict::ForgeReleaseNotObservedAfterPublish`.
  
  **Effects.** `gh release create TAG --repo R --verify-tag --draft --generate-notes [--prerelease]`; `gh release upload TAG PATH --repo R` (no `--clobber`, asserted by test); `gh release edit TAG --repo R --draft=false`. Provider selection stays in the single `provider_for` table.
  
  **Typed stale-intent failure.** `check_schema_version` now names found and expected. `read_intent` (callisto-cli) checks `schemaVersion` before serde and returns the new typed `CliError::ReleaseIntentSchemaUnsupported { path, found, expected }`, diagnostic code `callisto::release_intent_schema_unsupported`, whose help names `callisto release plan` as the fix.
  
  ### Deviation you asked me to state: published-but-incomplete release
  **A published release missing an asset uploads that asset; it is not a conflict.** Reasoning: the operation's identity is the *asset*, and `Absent` is the only observation that authorizes an effect in this model. Calling it a conflict would make an otherwise recoverable release permanently unrecoverable for the non-immutable case. On a real immutable release GitHub refuses the upload, which surfaces as the existing typed `GraphError::ReleaseCommand` rather than a release wrongly reported complete. Covered by `a_published_release_missing_an_asset_re_uploads_only_that_asset`, and recorded in the semantic model.
