So `platformArchABI` is exactly the derived-triple concept your abstraction needs — it's a **lossy, curated projection of the Rust triple**, not parsed generically. Not every rustc target has an entry; napi-rs hand-maintains the mapping.

**B. Shape** — target strings ARE Rust triples (`x86_64-unknown-linux-musl`, etc.) at the input/config layer. The *output* identifier (`platformArchABI`, e.g. `linux-x64-musl`, `win32-arm64-msvc`) is a napi-rs-specific derived string, structured as `{platform}-{arch}[-{abi}]`, not a triple and not parseable by any Rust tool — it's a lookup table, not a transform. `platform` uses Node's `process.platform` vocabulary (`darwin`/`win32`/`linux`/`android`/`freebsd`/`openharmony`), `arch` uses Node's `process.arch` vocabulary (`x64`/`arm64`/`arm`/`ia32`), diverging from Rust's `x86_64`/`aarch64`/`i686` vocabulary. This is a second, independent naming scheme layered on top of Rust's.

**C. Output & distribution** — VERIFIED pattern (https://napi.rs/docs/deep-dive/release + npm ecosystem convention e.g. @node-rs/*):
- Root package `@scope/addon` declares `optionalDependencies` pointing at exact-version platform packages named `@scope/addon-{platformArchABI}` (e.g. `@scope/addon-linux-x64-gnu`, `@scope/addon-darwin-arm64`).
- Each platform package's package.json carries `os: ["darwin"]`, `cpu: ["arm64"]`, and (Linux only) `libc: ["glibc"|"musl"]` — npm/yarn/pnpm use these three fields to skip installing incompatible optional deps automatically. This is the load-bearing mechanism; there's no separate "download at install time" step, it's static npm dependency resolution.
- `.node` binary filename: `{binaryName}.{platformArchABI}.node`, e.g. `index.win32-x64-msvc.node` (VERIFIED literal example from docs).
- GitHub release attachment: UNCERTAIN. Docs mention release/recovery workflows but I could not find an authoritative statement that `.node` binaries or platform tarballs are attached to GitHub Releases as a standard convention — npm optionalDependencies is the primary distribution channel, not GitHub Releases. Don't build on this without more digging if it matters.

Source: https://napi.rs/docs/cli/build. So yes — napi-rs's build step is cargo/rustc underneath, same as any Rust build.

## Python / PyPI

**A. Enumeration** — There is no single "list all wheel targets" command analogous to `rustc --print target-list`, because platform tags aren't an enumerable finite set the same way — they're a compatibility *predicate* evaluated per-machine/build-target, not a catalog. The authoritative spec is the Python Packaging User Guide's Platform Compatibility Tags page (VERIFIED, read directly): https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/. Two live tools compute the *current machine's* accepted tag set: `packaging.tags.sys_tags()` (Python API, from the `packaging` PyPI library) and `pip debug --verbose` (CLI, prints "Compatible tags" list). Per a pip issue thread these two do NOT always agree exactly (pip issue #11404) — UNCERTAIN/flag: don't assume they're interchangeable, note the discrepancy if you build tooling on either.

**B. Shape** — Tags are NOT free-form; each of the three components has a defined grammar (VERIFIED):
- **Python tag**: `{impl}{version_nodot}` — `cp312` (CPython 3.12), `py3` (generic), `pp310` (PyPy), compound form `py2.py3` for cross-version pure-Python.
- **ABI tag**: `cp312` (version-specific extension ABI), `abi3` (CPython stable/limited ABI — build once, runs on any newer CPython 3.x), `none` (pure Python, no C extension).
- **Platform tag**, several sub-grammars:
  - Windows: `win32`, `win_amd64`, `win_arm64`.
  - macOS: `macosx_{major}_{minor}_{arch}`, e.g. `macosx_11_0_arm64`; `universal2` arch variant covers x86_64+arm64 in one wheel.
  - Linux glibc: `manylinux_{glibc_major}_{glibc_minor}_{arch}` (PEP 600, "perennial" scheme), e.g. `manylinux_2_17_x86_64`; legacy fixed aliases `manylinux1`/`manylinux2010`/`manylinux2014` map to specific glibc versions (2.5/2.12/2.17) and are still emitted/accepted for compat.
  - Linux musl: `musllinux_{musl_major}_{musl_minor}_{arch}` (PEP 656), e.g. `musllinux_1_2_x86_64`.
  - Android: `android_{apilevel}_{abi}`, e.g. `android_27_arm64_v8a`.
  - iOS: `ios_{major}_{minor}_{arch}_{sdk}`, sdk ∈ {iphoneos, iphonesimulator}.
  
  Full tag string: `{python tag}-{abi tag}-{platform tag}`, e.g. `cp312-abi3-manylinux_2_17_x86_64`. This is structured/parseable (packaging.tags module parses it), not opaque.

**C. Output & distribution** — Wheels uploaded to PyPI (or any index) via `twine`/`gh-action-pypi-publish`. VERIFIED filename grammar (https://packaging.python.org/en/latest/specifications/binary-distribution-format/): `{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl`. Real example: `distribution-1.0-1-py27-none-any.whl`; a realistic Rust/PyO3 one would look like `mypkg-1.2.3-cp312-abi3-manylinux_2_17_x86_64.whl`. Normalization: distribution name run of `-_.` → single `_`, lowercased; version normalized per PEP 440; the three tag components can't contain `-` (multi-tag compat sets use `.` join instead, expanded combinatorially by the resolver). GitHub Release attachment: NOT a standardized convention — the canonical target is PyPI itself; PyPA's own guidance/examples (gh-action-pypi-publish, cibuildwheel's github-deploy example) build wheels as CI artifacts and push straight to PyPI. Some projects additionally upload dist/* to a GitHub Release via a generic action, but that's project choice, not ecosystem convention — UNCERTAIN as anything to model as "the" behavior.

**D. Toolchain — confirms your hypothesis, with a caveat.** VERIFIED: maturin (PyO3/maturin, https://github.com/PyO3/maturin) is literally "a Rust project that can be built using `cargo build` normally"; maturin's `BuildOptions`→`BuildContext` wraps cargo/rustc and then packages the resulting cdylib into a wheel with the right tags. So napi-rs and maturin are both thin Rust-native wrappers around cargo/rustc — target *resolution* (triple validity, linker requirements) is genuinely shareable in principle. **Caveat**: maturin additionally has to pick the *tag*, not just the triple — e.g. it decides `abi3` vs version-pinned ABI, and for Linux it must pick a manylinux/musllinux *policy version*, which has no cargo/rustc equivalent at all (glibc-symbol-version auditing, done by `auditwheel`/maturin's built-in equivalent). That policy-selection layer is genuinely Python-specific and not expressible as a Rust triple.

Non-Rust paths (real, and NOT unifiable with the cargo/rustc model):
- **setuptools + C extensions**: build backend invokes a C/C++ compiler directly (distutils/setuptools `Extension`), no cargo involved at all.
- **cibuildwheel** (VERIFIED, https://cibuildwheel.pypa.io/en/stable/faq/): backend-agnostic orchestrator — builds inside manylinux/musllinux Docker containers per target (pulls `CIBW_MANYLINUX_*_IMAGE`), handles non-native arch via QEMU emulation (`binfmt_misc`) rather than cross-compilation, delegates the actual build to whatever backend the project uses (setuptools, Cython, or maturin). It's explicitly documented as usable with maturin too, so it sits *above* both the Rust and non-Rust paths as a matrix/orchestration layer, not a builder itself.
- **node-gyp** is the Node-world analog (C++ addons, not Rust) — not relevant to napi-rs/maturin comparison but confirms the general pattern: every "native extension" ecosystem has both a Rust-cargo path and a legacy C-compiler path, and only the former is realistically modelable generically.

Realistic scope for a release tool: model the cargo/rustc-backed paths (napi-rs, maturin) generically via shared triple resolution; treat setuptools/C-extension and non-maturin cibuildwheel matrices as opaque "external build command produces N tagged artifacts" — don't try to derive their target sets from Rust's.

**E. Cross-compilation** — cargo: already known to you (`cross`, or `--target` + configured linker). napi-rs: real per-target need for linker/SDK, confirmed by docs' own warnings; exact current tool (zig vs docker) UNCERTAIN — my fetch of the cross-build guide 404'd, re-fetch https://napi.rs/docs/cross-build (without the `.en` suffix, or check https://github.com/napi-rs/cross-build examples repo directly) before depending on specifics. maturin: VERIFIED — supports `--zig` (via bundled cargo-zigbuild) for Linux cross/manylinux-compliant builds, and/or building inside a manylinux Docker container (the `pyo3/maturin` image, based on manylinux2014) for full manylinux compliance; zig path is "regularly tested on CI" for Linux, other host/target combos are less proven per maturin's own docs. cibuildwheel: containers for Linux; QEMU emulation (not cross-compilation) for non-native arch elsewhere.

"Needs cross" is meaningful per-ecosystem but means different things: for cargo it's linker+sysroot; for maturin on Linux it's additionally a *manylinux policy compliance* concern (glibc symbol versions), which zig/containers solve as a side effect of how they link, not because they're "cross-compilers" in the traditional sense.

**F. Naming** — napi-rs: package `@scope/{binaryName}-{platformArchABI}`, file `{binaryName}.{platformArchABI}.node` (both literal, verified above). Python: wheel filename grammar `{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl`, example `distribution-1.0-1-py27-none-any.whl` (verified from spec).
