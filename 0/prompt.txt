### Specific Blocker

**mmap is not implemented in WASI.** Both code paths fail at the same syscall:

- **Loose objects** (prior run): `Find(Loose(Io { source: Kind(Unsupported), action: "open or map", path: "/.git/objects/..." }))`

`std::io::ErrorKind::Unsupported` is WASI's response to `mmap()` — it returns ENOSYS. Both `gix-odb` (loose object reader) and `gix-pack` (pack index + data reader) use memory-mapped I/O internally. There is no public API in either crate to opt into read-based I/O instead. The callisto repo's objects happen to be fully packed right now, so the pack path fails first.

### Verdict Summary

**NO-GO for gix-native object reads inside WASM.**

- gix-ref (ref reads, HEAD resolution, branch name resolution) — **works** in WASI via regular file I/O
- gix-odb / gix-pack (any object content or header read) — **fails** with `Unsupported` (mmap ENOSYS)

The correct approach for `callisto-moon` remains the current exec-seam design: shell out to the host's `git` binary via `warpgate_pdk::exec_command`. A hybrid (native gix-ref reads for lightweight lookups + host exec for commit data) is technically possible but adds complexity for minimal gain. The mmap blocker will not be resolved without WASI gaining mmap support or gix-odb gaining an opt-in read-fallback path, neither of which is imminent.
