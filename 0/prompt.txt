  ## Phase 1: Reset the product contract

  Produce a short, binding product/architecture decision that answers:

  - Who is the primary user?
  - Which ecosystems are supported before v1?
  - Is Changesets the primary authoring model?
  - Are conventional commits supplemental or a second primary model?
  - Does Rust own actual publication? Recommended answer: yes.
  - Does CI own only scheduling and credentials? Recommended answer: yes.
  - Are binary assets required before v1?
  - What is the product-level version and tag?
  - Which existing CLI/JSON interfaces are retained before v1?

  Recommended decisions:

  - Cargo, npm, Python, and native npm coordination remain the supported scope.
  - Changesets are primary; conventional commits can generate equivalent change intent.
  - Merge of the reviewed version PR is release approval.
  - No environment reviewer gate.
  - One canonical release plan and executor.
  - Remove legacy surfaces before v1 where compatibility has no real consumer.

  Exit condition:

  - README, design document, CLI help, and actual behavior describe the same product.

  ———

  ## Phase 2: Add failing tests for every observed incident

  Before correcting the implementation, create tests that reproduce the real failures:

  1. A failed operation left Attempting, followed by a rerun.
      - It must never return zero merely because no operation is eligible.

  2. A resume on a fresh runner with no local state.
  3. A publisher succeeds remotely but the local process receives an ambiguous failure.
  4. A workflow artifact containing a hidden directory.
  5. Artifacts downloaded outside the trusted worktree.
  6. Resume after main advances.
  7. Resume after the original workflow artifact expires.
  8. Explicit version installation when the exact asset/package does not exist.
      - It must not install main.

  9. Malformed Cargo/pnpm workspace definitions.
      - They must fail closed.

  10. A complete self-release against fake registries and a bare Git remote.
  11. The same release executed twice.

  - The second execution must perform no duplicate publication and still issue a valid receipt.

  Static workflow assertions can remain, but only as supplemental lint.

  Exit condition:

  - Each historical incident has a test that fails for the original reason, not merely for a similar helper function.

  ———

  ## Phase 3: Repair executor correctness

  1. Define a provider observation interface.
  2. Observe every operation before execution.
  3. Observe again after successful or ambiguous execution.
  4. Resolve abandoned Attempting operations through external state.
  5. Treat mismatched existing state as a conflict.
  6. Require a terminal receipt before returning exit code zero.
  7. Persist the journal after every state transition.
  8. Upload the journal with if: always() for diagnostics.
  9. Make journal loss survivable by reconstructing from the plan and providers.
  10. Add an explicit recovery command targeted by commit and plan digest.

  Exit condition:

  - Killing the executor at every transition and rerunning always converges to success or a precise conflict.
  - It cannot duplicate an already completed publication.
  - It cannot report success for a partial release.

  This is the highest-priority implementation phase.

  ———

  ## Phase 4: Simplify the GitHub workflow

  Target workflow:

  Changesets
      ↓
  Version PR with immutable release plan
      ↓ review + merge
  Release executor
      ↓
  Observe → apply missing operations → verify
      ↓
  Terminal receipt

  Specific changes:

  - Treat merge as the approval.
  - Remove the reviewer environment gate.
  - Keep environment scoping only where needed for secrets.
  - Avoid a build/artifact job boundary for source-only registry releases.
  - Run binary build jobs only when the release plan contains artifact operations.
  - Add workflow_dispatch inputs for release commit and plan digest.
  - Check out the requested commit, not implicitly current main.
  - Keep artifacts out of the trusted worktree.
  - Upload execution journals and receipts independently from build artifacts.
  - Validate every restored artifact against plan digests.

  Exit condition:

  - Happy path, delayed retry, advanced main, and partial remote publication all use the same workflow and executor.

  ## Phase 5: Unify the release API and domain model

  2. Resolve user selectors once at the boundary.
  3. Build one release graph used by planning, CLI display, and execution.

  7. Expose JSON Schema for every stable automation artifact.
  8. Add schema-version migration or explicit rejection behavior.

  Exit condition:

  - All frontends call that implementation.

  7. Add adversarial fixtures for path normalization, nested workspaces, excludes, symlinks, and platform packages.

  # Recommended decisions on open questions

  My defaults would be:

  1. Binary assets before v1?
     Defer unless the setup actions are already a required external contract. Finish the source-release engine first.

  2. Product tag?
     Use a product-level callisto@X.Y.Z release for CLI/WASM assets, while retaining ecosystem package tags for individual registry artifacts.

  3. Legacy CLI compatibility?
     Remove misleading preview-only commands before v1 or turn them into explicit aliases backed by the new engine. Do not maintain two
     implementations.

  4. Fixtures in the fixed version group?
     Exclude the unpublished dev-only fixture crate unless its version is part of a concrete compatibility contract.

  5. Manual release approval?
     No second approval. Reviewed release PR merge is the approval.

  6. Execution journal as authority?
     No. It is valuable evidence, but remote state plus the immutable plan is the recovery authority.
