<pasted_content id="77e5">
Callisto has a credible alpha proposition for mixed Cargo/npm/PyPI repositories. Its market fit is still unproven, and “polyglot Changesets” is no longer sufficient differentiation. The strongest opportunity is a release workflow that owners can inspect, approve, and recover when publication partially fails.

The competition has moved materially. Changesets v3 addresses several historical complaints; Nx supports change files; Sampo directly overlaps Callisto’s category; and pnpm now documents built-in release management.

I saved the evidence and recommendations in a research report (docs/research/2026-11-17-release-tool-landscape.json). Research is current to November 17, 2026, against Callisto 0.21.1, commit ab3c030. Below is the user-facing assessment.

What has changed in the landscape

Four findings should shape our positioning:

- Changesets is actively improving. Version 3 introduced build/pack/publish workflows, reduced installation overhead, changed peer-dependent bumping, and preserves package.json formatting. Comparing Callisto against old Changesets behavior would exaggerate our advantage. Announcement (https://changesets.dev/blog/announcing-changesets-v3), migration guide (https://changesets.dev/guide/migration).
- Authored release intent is established across the category. Nx version plans provide file-based bump declarations independently of commit messages, with a CI check for missing plans. Nx version plans (https://nx.dev/docs/guides/nx-release/file-based-versioning-version-plans).
- There is already a direct polyglot competitor. Sampo discovers packages, consumes changesets, updates versions and dependencies, and publishes across multiple ecosystems. Sampo documentation (https://raw.githubusercontent.com/bruits/sampo/main/crates/sampo/README.md).
- Package managers are absorbing release tooling. pnpm documents Changesets-compatible intent files, dependency propagation, changelogs, groups, and prerelease lanes. An npm-only owner increasingly has the option of adding no separate release tool. pnpm release management (https://pnpm.io/versioning).

These establish competitive pressure. They do not establish market share or customer satisfaction; I did not find evidence sufficient to quantify either.

The main competitors, from an owner’s perspective

| Tool | Why an owner chooses it | Where Callisto has an opening | Where Callisto is behind |
|---|---|---|---|
| Changesets | Explicit, reviewable release notes and coordinated npm package releases. Fixed/linked policies, prereleases, and publishable snapshots. | Native Cargo and Python handling avoids surrogate JavaScript metadata and custom publishing glue. | npm-focused workflow depth, preview publication, and increasingly capable packing/publishing automation. |
| Knope | Flexible release automation using changesets, Conventional Commits, multiple versioned files, and configurable workflow steps. | Native dependency discovery, range-aware propagation, and registry-observed completion can remove explicit wiring. | Broader file-format coverage, Windows support, Gitea integration, and flexible workflow composition. |
| Nx Release | Release management integrated with an existing project graph and task system. | A standalone release tool can serve owners who do not want another repository-management framework. | Existing Nx owners already have graphs, groups, version plans, dependent updates, and programmatic integration. |
| release-please | Keep a release PR current from Conventional Commits; merging controls when releases happen. Polyglot strategies and workspace plugins. | Integrated registry publication and recovery can replace the downstream publishing scripts. | Broader language strategies and an established commit-driven workflow. Callisto’s inferred-only managed workflow is incomplete. |
| Sampo | A standalone, polyglot, changeset-driven tool with discovery, publishing, GitHub App, and Action. | Callisto’s release authority, confirmation, and recovery model is a plausible distinction that needs a direct rehearsal. | Wider ecosystem coverage, MIT licensing, and current npm staged/trusted-publishing capabilities. |
| pnpm native tooling | Fewer tools and configuration files for a pnpm workspace. | Coordinating actual Cargo/Python releases alongside npm. | For npm-only owners, Callisto must justify another executable and policy surface. |

Some distinctions deserve emphasis:

Knope is more capable than “a version bumper.” It already combines changesets and commit inference, supports multiple versioned files per package, and can invoke publishing commands through workflows. The concrete Callisto advantage is its native dependency and release orchestration. Knope documents exact-version dependency updates rather than range preservation, and its Python handler does not support dependency rewriting. That is a useful comparison for a real mixed workspace. Dependency-update limitations (https://knope.tech/recipes/updating-dependencies/), Python support (https://knope.tech/reference/config-file/packages/#pyprojecttoml).

release-please really does support monorepos and dependency graphs. Its Cargo workspace plugin builds a graph, propagates bumps, and updates the lockfile. Its explicit boundary is package-manager publication. Our case against it should be fewer downstream release scripts and better completion/recovery behavior. Manifest releaser (https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md), project scope (https://github.com/googleapis/release-please).

Sampo is the most important direct comparison to add. Its November 0.24 release includes out-of-range dependent bumping, npm staged publishing, Bun-workspace trusted publishing, and Ruby support. We cannot claim that polyglot changesets or selective cascades distinguish Callisto by themselves. I did not audit Sampo’s recovery implementation, so parity there remains unresolved. Sampo releases (https://github.com/bruits/sampo/releases).

Nx’s Rust story needs a pinned trial. Its current recipe simultaneously requires legacy versioning and says that implementation was removed in Nx 22. That is contradictory documentation, not proof that present Nx cannot release Rust. We should avoid making the stronger claim. Rust recipe (https://nx.dev/docs/kb/publish-rust-crates).

Other alternatives worth taking seriously

| Alternative | Relevant owner need |
|---|---|
| release-plz | Rust-library releases with release PRs, publishing, and API compatibility feedback from cargo-semver-checks. This is a meaningful capability Callisto lacks today. Overview (https://release-plz.dev/docs), API checks and limitations (https://release-plz.dev/docs/semver-check). |
| cargo-release | Deliberate Cargo-native CLI releases, workspace selection, dependency updates, hooks, and safety checks. Dry run is the default. Project documentation (https://github.com/crate-ci/cargo-release). |
| semantic-release | Commit-driven continuous releases, prerelease channels, maintenance releases, and publishing plugins. Monorepo coordination requires evaluating the chosen extension rather than assuming the core provides it. Official introduction (https://semantic-release.org/intro/), monorepo extension (https://github.com/pmowrer/semantic-release-monorepo). |
| Lerna / Rush | Existing npm monorepos with established versioning and publishing policies. Staying with the installed system can be cheaper than migrating. Lerna (https://lerna.js.org/docs/features/version-and-publish), Rush (https://rushjs.io/pages/maintainer/publishing/). |
| dist / cargo-dist | Binary distribution, installers, checksums, and generated release CI. Owners shipping CLIs need this experience beyond package publication. dist documentation (https://axodotdev.github.io/cargo-dist/book/). |

What Callisto actually offers today

I checked implementation paths and ran focused tests rather than treating the README or roadmap as proof.

The core offering is substantial:

- Native Cargo, npm, and Python discovery and version handling.
- Dependency-aware bump propagation and requirement rewriting.
- Native lockfile refreshes.
- Explicit fixed/linked grouping policies.
- Changesets, prerelease commands, snapshots, and some commit inference.
- Reviewable version and release plans.
- Registry publication, tags, GitHub releases, and selected binary/napi assets.
- Structured reports, schemas, diagnostic codes, and strict configuration.
- Recovery that observes completed effects instead of blindly repeating them.

The native-resolution suite passed 12/12, including mixed workspaces, Python/uv resolution, pnpm protocols, packing, and installation checks. That is stronger evidence than manifest snapshots alone. Native-resolution tests (crates/callisto-cli/tests/native_resolution_e2e_tests.rs).

However, this is three native ecosystems under one release workflow. Arbitrary relationships between languages are not inferred. Owners must explicitly couple releases where appropriate. Scoped release model (docs/architecture/polyglot-v1.md).

Where we have a credible advantage

1. Release completion and recovery are first-class behavior.

Callisto distinguishes planned effects, effects completed by this run, and effects already observed as satisfied. Required registry publications precede the package’s tag and public announcement. Retries can adopt completed work, and a success receipt requires completion.

For an owner, the valuable promise is: “If publication fails halfway through, I can rerun the approved release and understand what remains.” That addresses real operational work. Release architecture (docs/architecture/release.md), state transitions (crates/callisto-model/src/release_transition.rs:75).

This is a verified design advantage over assembling an uncoordinated sequence of scripts. It is not yet evidence that Callisto recovers better than every competitor. That requires identical failure rehearsals.

2. Native dependency semantics across the supported ecosystems.

Callisto can propagate Python dependency changes, preserve npm range operators, and refresh native lockfiles. Compared with Knope’s documented manual dependency entries and exact-version limitations, this is a concrete reduction in owner configuration.

3. A focused adoption boundary.

A mixed repository can adopt Callisto without adopting Nx’s broader repository model. That is useful for teams already happy with their build system.

The native executable also avoids requiring Node merely to manage Cargo or Python releases. Native package managers and build tools are still required for their respective operations.

4. Inspectability for custom automation.

JSON reports, schemas, explicit bump reasons, and diagnosable errors help owners build CI around the tool. These are useful product qualities, though several competitors also expose plans or APIs.

Where we are behind—or have important qualifications

| Area | Verified limitation | Consequence for an owner |
|---|---|---|
| Managed prereleases | Release-PR decision-making rejects active prerelease mode. | The presence of pre enter does not provide a complete managed alpha/beta release workflow. |
| Published previews | snapshot writes temporary versions; release refuses them. | Owners cannot use Callisto’s normal release path to publish PR-testable snapshots. Changesets documents that workflow. |
| Commit-driven automation | Release PRs are derived from has_changesets. | An inferred-only bump can appear in status/version without opening a release PR. |
| Contributor enforcement | status --check checks error diagnostics. | A green result does not prove that changed packages have release documentation. |
| Python layouts | Static PEP 621/Poetry; co-located Cargo/Maturin fails discovery. | Some particularly natural Rust/Python customers cannot adopt it. |
| Private Python indexes | Authenticated reads and HTML-only indexes need explicit support. | “Alternate registry configuration” is broader than the actual supported private-index experience. |
| Trusted publishing | Generated integration uses tokens; OIDC is future work. | Owners retain credential setup and rotation costs. |
| Platforms/forges | No Windows support; generated workflows target GitHub. | Mixed developer fleets and other forge users face exclusion or manual integration. |
| Workflow upgrades | Internal CI commands require matching versions and regenerated workflows. | Upgrading carries coordination work beyond replacing the binary. |

Evidence: release-PR implementation (crates/callisto-cli/src/commands/release_pr.rs:108), status check (crates/callisto-cli/src/commands/status.rs:13), publishing limits (docs/publishing.md), stability contract (docs/stability.md), Changesets snapshots (https://changesets.dev/guide/snapshot-releases).

Trusted publishing deserves particular attention. Both npm and PyPI have supported OIDC publication paths. Provenance support and isolating tokens to the publishing job are valuable, but they do not remove token administration. From an owner’s perspective, postponing integrated OIDC is a competitive cost. npm trusted publishing (https://docs.npmjs.com/trusted-publishers/), PyPI trusted publishing (https://docs.pypi.org/trusted-publishers/).

Release safety also needs precise wording. Cross-registry publication is not atomic. Registry version presence does not universally prove identical bytes. Python’s sealed file sets provide stronger checks, while unsealed rebuilds have different guarantees; the generated Python-only workflow is unsealed. Native publish hooks can perform effects outside Callisto’s graph. Recovery boundaries (docs/architecture/release.md).

Migration has more friction than file compatibility suggests

Three examples matter:

1. Changesets configuration is not imported equivalently. Callisto warns about ignored keys including linked, ignore, access, and baseBranch. Keeping existing change files does not preserve release policy. Migration diagnostics (crates/callisto-graph/src/commands/init.rs:569).
2. Linked groups mean different things. Callisto bumps every live member and aligns their targets. Changesets does not automatically bump an unchanged linked member. That can increase an owner’s release scope unexpectedly. Callisto implementation (crates/callisto-graph/src/cascade.rs:312), Changesets semantics (https://changesets.dev/guide/config#linked).
3. Peer bump defaults differ. Callisto enables peer escalation by default. Changesets v3 describes patch bumps for peer dependents. Neither policy is universally correct, but a migration can change version outcomes. Callisto configuration (docs/config.md:34), Changesets v3 (https://changesets.dev/blog/announcing-changesets-v3).

A convincing migration experience should compare the resulting plans and explain differences before owners switch.

Licensing is another adoption consideration. Callisto’s main implementation uses FSL-1.1-MIT; the model crate is MIT. The license expressly permits internal use and restricts competing commercial use, with a future MIT grant after two years. Against MIT/Apache alternatives, additional policy review and reduced fork freedom are plausible friction. That does not mean ordinary commercial internal use is prohibited. License (LICENSE).

Who should choose Callisto?

This is my assessment of fit, not measured demand:

| Repository owner | Current fit |
|---|---|
| GitHub-hosted Cargo + npm repository, especially napi-rs, with Linux/macOS developers | Strongest alpha hypothesis. Multiple native outputs and publication ordering create a reason for one release workflow. |
| Cargo/npm plus separate-directory Python packages | Promising, subject to Python versioning and registry constraints. |
| npm-only repository already using Changesets or pnpm | Weak switching case unless recovery or policy benefits are demonstrated. |
| Existing Nx or Rush repository | Weak default case. Reusing its existing graph and policies may cost less. |
| Rust-only library workspace | Competitive but undifferentiated. release-plz’s API checks are a meaningful advantage. |
| Co-located Rust/Maturin project | Currently unsuitable. |
| Windows-heavy team or non-GitHub forge | Poor current fit. |
| CLI product needing installers and broad distribution | Partial fit. Package and GitHub asset publication do not replace a distribution system. |

What I would prioritize before broadening scope

These are recommendations, not new release gates.

1. Prove the mixed-ecosystem owner experience. Use released binaries, fresh repositories, real credentials, and real consumer installs. Measure setup time and manual interventions.
2. Make migration outcomes explicit. Provide plan comparisons and explain groups, peer bumps, publication access, and ignored configuration.
3. Resolve the supported prerelease story. Owners approaching v1 naturally need alpha/beta cycles. Define the end-to-end workflow and state preview-publication limits clearly.
4. Reconsider OIDC priority. Credential administration is part of the product experience.
5. Publish recovery evidence. Demonstrate a partial publish, delayed registry visibility, a conflicting tag, a missing Python artifact, and a successful rerun.
6. Keep scope narrow until adoption repeats. More ecosystems will not establish that the current workflow saves owners effort.

The current roadmap (docs/projects/ROAD-TO-V1.md) already identifies important evidence gaps: production-path Cargo/PyPI registry testing, a recorded native install/load matrix, and unmeasured first-release onboarding time.

A useful alpha experiment would recruit five external mixed-ecosystem owners and follow three release cycles each. Measure whether Callisto removes meaningful scripts and maintenance work, whether contributors can follow the process, and whether owners recover from a failure without implementation help. If those owners do not prefer it to their existing setup or Sampo/Knope/release-please, we should revisit the proposition before expanding.

My recommended positioning is:

> Reviewable, dependency-aware releases for Cargo, npm, and Python monorepos—with explicit publication plans and recovery from partial failures.

Confidence in the verified capability assessment is high. Confidence in that positioning is medium because this research did not include customer interviews, retention evidence, or head-to-head competitor execution.

Verification was mixed: cascade scenarios passed 9/9, lifecycle tests 5/5, and native-resolution tests 12/12. The graph library suite had 1,152 passes and one unresolved Cargo registry-observation failure, which also failed in isolation. I did not run complete CI, publish externally, or benchmark competing tools. The saved report records these limits and separates confirmed findings from inference.

Callisto should delegate OIDC to native tools and own the small compatibility and workflow layer needed to make them work. We should avoid implementing token exchanges, refresh logic, or a general authentication framework.

The source inspection supports a smaller scope than our existing OIDC plan proposes.

What Changesets v3 does

Changesets primarily gets out of the way:

- It invokes the selected npm, pnpm, or Yarn publishing command.
- The native CLI receives its authentication environment and configuration.
- The native CLI handles trusted publishing.
- The documented workflow grants id-token: write to the publishing job and separates packing/building from publication.
- Interactive authentication handling responds to native CLI failures; Changesets does not implement its own OIDC exchange.

There is no Changesets-specific OIDC configuration model that duplicates registry trust settings. npm adapter (https://github.com/changesets/changesets/blob/c9269c01af5f3f7463adc648890fc3a8a729dd18/packages/cli/src/lib/npm.ts), publishing workflow (https://changesets.dev/guide/automating).

That is a good model for Callisto: native authentication, with a reliable release coordinator around it.

What Sampo does

Sampo follows the same principle, with one targeted adaptation:

| Publishing route | Sampo’s approach |
|---|---|
| npm/pnpm/Yarn | Delegate to native publishing tools and their authentication. |
| Python | Run uv publish; uv owns credentials and trusted publishing. |
| Bun with npm trusted publishing | Pack with Bun, then upload the tarball with npm. |

The Bun bridge matters. Simply substituting npm publish could lose Bun’s transformations of workspace: and catalog: references. Sampo preserves Bun’s packing behavior, delegates authentication to npm, and handles the lifecycle hooks surrounding that split. It also recognizes setup-node’s placeholder token so that it does not mistake it for a real credential. It still does not implement the OIDC protocol. Bun bridge (https://github.com/bruits/sampo/blob/01b484549021f6f458c5aa93820d4a63a39d9485/crates/sampo-core/src/adapters/npm.rs#L687), Python uploader (https://github.com/bruits/sampo/blob/01b484549021f6f458c5aa93820d4a63a39d9485/crates/sampo-core/src/adapters/pypi/pip.rs#L420).

Where Callisto actually stands

There are two important corrections to the earlier assessment.

npm is already largely unobstructed. Our action writes token configuration only when NPM_TOKEN is nonempty. Our runner preserves GitHub OIDC variables for npm-family tools, and generated publishing jobs already have id-token: write. That makes native npm trusted publishing a path to validate, rather than something requiring a new authentication subsystem. Action credential setup (.github/actions/callisto-action/scripts/run-release.sh:16), child environment policy (crates/callisto-cli/src/runner.rs:82).

Twine already supports trusted publishing. Our plan’s statement that it cannot mint tokens is stale; I missed that in the first pass. Twine added built-in support in 6.1.0 and refresh handling in 6.2.0. Callisto already pins 7.0.0. However, our runner currently strips GitHub OIDC variables from Twine, preventing that native capability from working. Twine changelog (https://twine.readthedocs.io/en/stable/changelog.html), Callisto’s Twine pin (crates/callisto-graph/src/commands/init.rs:801), environment policy (crates/callisto-cli/src/runner.rs:82).

Consequently, switching Python uploaders solely for OIDC is unnecessary.

What I recommend tackling

| Area | Smallest useful responsibility for Callisto |
|---|---|
| npm | Validate tokenless publication through native npm; document required versions and trust configuration. Test pnpm/Yarn separately rather than assuming identical support. |
| PyPI | Allow the Twine uploading process to receive the required OIDC context while continuing to withhold credentials from explicit build processes. Let Twine exchange and refresh tokens. |
| crates.io | Compose the official crates-io-auth-action before execution and pass its temporary token through the existing CARGO_REGISTRY_TOKEN path. |
| Bun | State the supported native capability clearly. Add a Bun-pack/npm-upload bridge only if users need it before Bun supports the desired flow. |
| Generated workflows | Provide working native-auth recipes, avoid injecting empty credentials, and place identity permission on the publishing job. |

The official Cargo helper already supplies a temporary token consumable by Cargo; there is no reason for Callisto to reproduce that exchange. crates.io authentication action (https://github.com/rust-lang/crates-io-auth-action).

I would also avoid adding oidc = true to callisto.toml at this stage. Registry trust belongs in registry settings, CI permission belongs in the workflow, and authentication behavior belongs to the publisher. A Callisto setting should exist only if it controls a concrete behavior we actually own.

“Get out of the way” still needs verification

Our useful work is a small compatibility contract:

- No token is required when the native publisher supports trusted publishing.
- Publisher identity survives our subprocess environment filtering.
- Build processes retain their existing credential isolation.
- Native configuration and credential precedence remain intact.
- Packing semantics survive any uploader substitution.
- A real tokenless release succeeds, and a misconfigured trusted publisher produces an understandable failure.

Publishing authentication also differs from authentication for private dependency installation or registry reads; OIDC publication does not automatically replace those credentials. npm trusted publishing (https://docs.npmjs.com/trusted-publishers/).

Finally, npm staged publishing should remain a separate decision. It changes when a release becomes publicly available and therefore affects tags, receipts, and announcements. It should not become an incidental part of adding OIDC.

No authentication implementation or workflow policy was changed; actual OIDC publication remains untested.

<pasted_content id="77e5">
I’d keep Callisto’s synchronous core, strengthen its existing adapters, and use traits at external boundaries. Tokio and a general plugin or workflow framework are not justified by what we’ve found.

The useful lessons concern where responsibilities belong. Callisto already has much of the right structure.

I saved the detailed comparison in the Rust implementation report (docs/research/2026-11-17-rust-implementation-lessons.json).

What each implementation teaches us

| Implementation | Pattern worth adopting or reinforcing |
|---|---|
| Changesets v3 | Compute version consequences to a fixed point; distinguish dependency edits from package releases; separate packing from uploading; preserve prerelease prose across stabilization. |
| Sampo | Keep ecosystem-specific behavior in adapters; preserve native packing when changing upload transport; support complete prerelease workflows rather than just suffix arithmetic. |
| release-please | Separate version policy, file transformation, workspace coordination, and forge reconciliation; construct candidates before applying effects; avoid unnecessary release-PR updates. |

We should translate these responsibilities into idiomatic Rust, rather than reproduce release-please’s inheritance hierarchy or introduce a plugin system.

1. Keep narrow adapters—we already have them

These are existing Callisto boundaries:

| Existing abstraction | Responsibility |
|---|---|
| Manifest | Read and edit native manifests. |
| RegistryEcosystem | Invoke and interpret an ecosystem’s registry tools. |
| ReleaseProviderSet | Present the outside world to the release executor. |
| CommandRunner | Execute subprocesses with controlled environments, output, and deadlines. |
| DependencyResolver | Supply discovered packages and dependency relationships. |

Sources: manifest interface (crates/callisto-manifests/src/lib.rs), registry adapter (crates/callisto-graph/src/commands/release/provider/registry.rs:219), executor providers (crates/callisto-graph/src/commands/release/provider/mod.rs:130).

That is already an adapter architecture. I would preserve those boundaries and avoid combining them into one large EcosystemPlugin responsible for discovery, versioning, builds, authentication, publishing, and changelogs.

Sampo’s Bun implementation illustrates why: the tool that packs a package can differ from the tool that uploads it. Bun understands its workspace/catalog metadata; npm supplies the required authentication transport. An all-purpose ecosystem object can obscure that distinction. Sampo implementation (https://github.com/bruits/sampo/blob/01b484549021f6f458c5aa93820d4a63a39d9485/crates/sampo-core/src/adapters/npm.rs#L725).

If Callisto needs that capability, add a small internal pack/upload boundary for that concrete case.

2. Use traits for replaceable behavior; enums for our own rules and states

My rule would be:

- Traits: subprocess execution, provider observation, manifest editing, discovery, time/waiting.
- Enums: operation states, dependency kinds, group policies, completion outcomes, version authority.
- Functions: deterministic version arithmetic, dependency propagation, group alignment, and plan validation.

The strongest existing Rust patterns are ApplyPermit, AbsentProof, ExactEvidence, and validated release inputs. They make important preconditions explicit instead of relying on callers remembering a sequence.

Release-please separates version arithmetic from language strategies. We can preserve that separation using ordinary functions and typed policy values; it does not require a new trait for every configurable rule. Versioning policy (https://github.com/googleapis/release-please/blob/05c6a4f71022304d4edad24ea90c1c16324503d5/src/versioning-strategies/default.ts).

I would keep runtime-selected adapters behind &dyn Trait where that is convenient. Existing generic seams can remain where they help composition and testing. There is no evidence that dispatch overhead matters beside subprocess and network costs.

3. Keep one shared version solver and a separate effect graph

Changesets and Sampo both settle graph propagation and group consequences repeatedly. A group can raise a version, which invalidates another dependency, which introduces another release.

Callisto already has a worklist and fixed-point calculation. That should remain the single authority for these consequences. Adapters should supply native dependency facts and rewrite behavior, rather than independently implementing cascade policy. Callisto solver (crates/callisto-graph/src/cascade.rs:223).

Also preserve the distinction between:

- An edit needed to keep the workspace consistent.
- A package needing a new published version.
- An external operation needing another operation completed first.

Changesets demonstrates this concretely: a dev-only dependency can have its range rewritten without releasing the dependent. Its publishing graph excludes those dev edges. Dependency handling (https://github.com/changesets/changesets/blob/c9269c01af5f3f7463adc648890fc3a8a729dd18/packages/assemble-release-plan/src/determine-dependents.ts).

That is a domain-model lesson with direct user consequences.

4. Preserve planning, validation, and application as distinct stages

Release-please constructs candidate updates before creating PRs and releases. Its file updates are represented as data and combined by path, preventing independent updates to a shared file from overwriting one another. Update representation (https://github.com/googleapis/release-please/blob/05c6a4f71022304d4edad24ea90c1c16324503d5/src/update.ts), composition (https://github.com/googleapis/release-please/blob/05c6a4f71022304d4edad24ea90c1c16324503d5/src/updaters/composite.ts).

Callisto already has VersionPlan and groups manifest writes by path. Keep that ownership centralized. Write classification (crates/callisto-graph/src/apply.rs:38).

The important discipline is:

> Collect facts, calculate decisions, validate authority, then apply permitted effects.

Some fact collection necessarily performs I/O. Once collected, policy calculations should be deterministic and independently testable.

I would retain Callisto’s committed decision and validated intent as authority. Release-please’s labels and parsed PR prose are useful UI mechanisms, but they carry operational state we should continue representing with typed documents.

5. Keep workflow semantics in Rust

GitHub Actions should:

- Schedule jobs and select toolchains.
- Transport plans and artifacts.
- Supply credentials or identity.
- Invoke Callisto’s entry points.

Rust should own:

- The approved package/version roster.
- Operation prerequisites.
- Artifact validation.
- Registry completion rules.
- Retry/adoption decisions.
- Whether a success receipt can be issued.

Changesets’ granular actions offer useful composability. They do not imply we need a workflow-engine crate or more release-policy shell scripts. Our architecture already states this boundary. Release architecture (docs/architecture/release.md).

6. Async and Tokio: defer until a measured need appears

Callisto currently launches native tools and has bounded read concurrency. Its in_parallel helper runs up to eight scoped workers and restores results to input order. That is a reasonable implementation for this workload. Current concurrency (crates/callisto-graph/src/commands/release/capability.rs:365).

Introducing async would also mean preserving the runner’s existing responsibilities: concurrent pipe draining, deadlines, credential filtering, redaction, and handling descendants that retain output pipes.

Tokio could become worthwhile if we need:

- Much greater simultaneous I/O.
- A long-running watch/service mode.
- A subprocess cancellation and streaming redesign that demonstrably simplifies the runner.

Merely wrapping blocking operations in async changes little. spawn_blocking still consumes threads, and a started blocking task cannot be aborted. Tokio’s child processes also continue running when dropped unless configured otherwise. Blocking-task behavior (https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html), process cancellation (https://docs.rs/tokio/latest/tokio/process/index.html).

If that need emerges, keep async in the I/O infrastructure. Version arithmetic and state transitions should remain independent of the runtime.

7. Crates: mostly use what we already have

| Need | Recommendation |
