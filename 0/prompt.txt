# Callisto — Deep Analysis & Competitive Evaluation

## 1. What it is

**Callisto** is a pre-v1, Rust-implemented, changeset-driven versioning and release tool for **Cargo, npm/pnpm, and Python/PyPI monorepos** by Orin DX. It deliberately occupies the exact wedge no incumbent covers: *dependency-aware, cross-registry* release management — reading native manifests to compute which dependents must move, then coordinating registry publishes, git tags, and GitHub releases as one ordered, re-runnable execution.

| Metric | Value |
|---|---|
| Source | ~96K lines of Rust across 5 crates (graph 43K, model 16K, manifests 7K, cli 9K, fixtures 0.5K) |
| Tests | ~20.3K lines in `tests/` plus unit tests, proptest regression corpora, a fuzz target, mutation testing, and a 90% line-coverage CI gate |
| History | 673 commits — 653 by one human (Gabe Castro), 14 by the release bot, 6 by dependabot |
| Docs | [ARCHITECTURE.md](/Users/gabe/Projects/callisto/ARCHITECTURE.md), 12 ADRs, 5 JSON behavior specs, 3 deep architecture topics, a v1 findings register, a scoped v1 model |
| Self-hosting | Yes — generates its own CI, release-PR bot action, and release workflow, but **has not yet verified a full self-release** (see §6) |
| License | `callisto-model` MIT; everything else FSL-1.1-MIT (becomes MIT 2 years after each release) |

The repo is clearly agent-assisted (`.claude/`, `.codex/`, `.gemini/`, `.opencode/`, `.entire/`, `.agents/` + a rigorous [AGENTS.md](/Users/gabe/Projects/callisto/AGENTS.md)), which the documentation discipline betrays in a good way.

## 2. Architecture evaluation

**The layering is clean and enforced.** `cli → graph → manifests → model`, a MIT leaf that no FSL crate may depend on, and dependencies only point down. That license seam is unusual and deliberate: the domain vocabulary (identity, version, changeset format, VCS, the release authority types) is the open core; the engine is the commercial layer.

**The invariants are structural, not aspirational** (the standout of the whole codebase):
- `unsafe_code = "forbid"` workspace-wide, with centralized lint policy.
- **`ApplyPermit`** ([permit.rs](/Users/gabe/Projects/callisto/crates/callisto-model/src/permit.rs)): a capability token with a private field; the only constructor returns `None` on `--dry-run`, so any write path that forgets the dry-run check *fails to compile*. The comment is honest about its origin — "several forgot" (pre enter/exit, init) — matching a known class of real bugs even in cargo.
- **One file-write primitive**: `atomic_write` (temp in target dir → fsync → rename → fsync parents). Manifest edits go through `toml_edit`'s CST for TOML and fingerprinted JSON round-trips for `package.json` — no regex or line edits, ever (ADR 8 pins it).
- **System git only** (ADR 5) — no embedded git; Callisto sees exactly what the user's git sees.
- Every user-facing error is a miette diagnostic with a stable code and help text, published in [docs/errors.md](/Users/gabe/Projects/callisto/docs/errors.md).

**The release engine is the genuinely novel part.** [release_execution.rs](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/release_execution.rs) is a small, pure state machine: a closed transition table (95 lines) of `Pending / Attempting / Published / AlreadySatisfied / Blocked / Failed`, proof tokens (`AbsentProof`, `ExactEvidence`) that only matching observations can mint, single-constructor run envelope and execution state, and a receipt built *only* from recorded state. Every run starts fresh, observes each provider effect first (exact → adopt; absent → perform then confirm; conflict/indeterminate → stop), and executes a DAG of operations (platform publishes → registry publishes → tag → draft release → uploads → publication) ordered by real prerequisites, not a fixed ecosystem pipeline.

**The verification tiers are above the competition's standard** and honestly tiered: a deterministic fault-injection simulator (nested-loop enumeration of crash points × provider outcomes over the *real* executor, asserting receipts only when all effects landed and convergence within three clean reruns), replayed real provider fixtures with flag-contract tests against the actual tools (network-gated, explicitly outside `ci`), JSON schema guards, and a real-binary contract test of the release-PR action's jq expressions.

**The documentation system is a feature.** Behavior is specified in testable JSON contracts (`spec@1`), decisions in ADRs with rejected options, guardrails, and "revisit when" triggers, and — most impressively — [V1-FINDINGS.md](/Users/gabe/Projects/callisto/docs/projects/V1-FINDINGS.md) is an open register of *confirmed, reproduced* contract failures with evidence and consequence. It says things like: *"a fresh `callisto release` can print `Nothing to release.` without a receipt... This remains a violation of the retry contract."* The [how-callisto-works.md](/Users/gabe/Projects/callisto/docs/how-callisto-works.md) doc literally lists when *another tool may be a better fit*. That epistemic honesty is rare in tool documentation and it is a real differentiator in trust-building — provided the findings actually get fixed.

**Scale smells to watch.** `apply.rs` is 2,980 lines, `walk.rs` 2,150, `release.rs` (model) 4,386. They're well-structured (the write-classification batching with an explicit "mixed-routing data-loss hazard" exclusion set shows care), but this is where complexity will accrue fastest. The polyglot v1 model ([polyglot-v1.md](/Users/gabe/Projects/callisto/docs/architecture/polyglot-v1.md)) is sensibly scoped — four concepts (release owner, distribution, version authority, release effect), explicit non-goals (no universal package manager, no cross-registry transactions, no persisted journal) — and correctly refuses to make co-location or build inputs imply version coupling.

## 3. Feature inventory

- **Versioning**: changesets (`add`/`status`/`version`), optional conventional-commit inference, **dependency cascade with real range-coverage semantics** (caret-with-prerelease rules, PEP 440 ranges, pnpm `workspace:*`/aliases/relative paths/catalogs, Cargo workspace inheritance, `||` alternatives), fixed & linked groups, `pre` mode with cross-grammar pre-baselines, native-grammar snapshots, `--dry-run` on everything, JSON output + published JSON schemas, completions, `matrix` (native CI build-target derivation — no competitor has this).
- **Release**: local route (clean-checkout enforcement, receipts) and managed CI route: a release-PR bot that commits a version *decision* (ADR 2 — the committed decision is the release authority; CI verifies the merged diff against it and never re-derives policy), two generated workflow shapes (simple vs plan→build→publish with attestation-checked binaries), a reusable validate action, a setup action with provenance-verified installs, recovery dispatch with explicit source SHA, and platform-package (napi-rs) ordering guarantees.
- **Compatibility as a strategy**: the changeset file format is byte-compatible with `@changesets/cli` (ADR 1 guardrail), including its quote rules and `--empty` shapes. That's the migration hook for JS teams and it's the smartest adoption decision in the repo.

## 4. Competitive analysis

| | **Callisto** | **Changesets** | **Knope** | **Nx Release** | **Release-Please** |
|---|---|---|---|---|---|
| Ecosystems | Cargo + npm/pnpm + PyPI in **one tool** | npm only (JS) | ~any file format, config-listed (Cargo, Java, XML, YAML…) | npm, Docker, NuGet, PyPI, Cargo (via plugin) | The most: node, python, ruby, .NET, java, cargo, docker, helm, hcl… |
| Dependency-aware cascade | **Yes — graph + range coverage + policy modes** | Yes, but npm-only | **No** — `versioned_files` list; you declare each dependent file's `dependency` key; workspace members auto-detected, but no dependents graph | Partial — "updating any projects that depend on them" driven by the Nx project graph (build-oriented, not manifest-range semantics) | Weak — commit-path-based per component; internal dependency ranges updated, but no severity cascade |
| Change declaration | Changesets files (compatible) + opt-in commit inference | Changesets files (the standard) | Changesets **or** conventional commits, interactive | Commit messages / version plans | Conventional commits only |
| Multi-version unit | One dir, multiple canonical manifests (dual Cargo+npm) | One package = one `package.json` | **`versioned_files`: N files, one version** (close analog) | One project | One component per releaser |
| Publish | `cargo`, npm tools, `twine`, `gh` — owners keep credentials/hooks (ADR 4) | `npm publish` + config-driven multi-registry/dist-tag/access | Any shell command (your own) | Plugin publishers | release-please-action CI step (publish is a separate, clunkier phase) |
| Crash-safety / reruns | **State machine + provider observation + receipts + receipts-only-on-full-success** | Publish-then-tag; best-effort | Best-effort, user scripts | Best-effort | Tags/releases created, then publish action; known identity/atomicity awkwardness |
| CI story | Generated workflows + release-PR bot + committed decision authority + recovery | Official action, mature | Official action, mature, **visual config studio** | First-class (it *is* a build system) | The flagship: maintained release PR + action, battle-hardened at Google scale |
| Lockfiles | Cargo + pnpm aware (refresh after writes) | None | Cargo.lock via dependency keys | None meaningful | None |
| Maturity/adoption | **Pre-v1, zero known external users, 1 human** | **The de-facto standard; v2 in maintenance, v3 in active development** | Niche but real, commercial (Knope Inc), visual tooling | Large (Nx install base) | Very large (Google, broad open source) |

**Honest read per competitor:**

- **Changesets** is the 800-lb gorilla but is *categorically* single-ecosystem — it will never fix the Cargo/PyPI half of the problem. Callisto's changeset-file compatibility means a JS team can try Callisto without breaking existing `.changeset/` workflows, and a mixed repo can keep both. Changesets v3 is in active development, so the bar in its lane is moving.
- **Knope** is the closest architectural cousin in one respect (files sharing a version → it explicitly supports `Cargo.toml` + `pyproject.toml` per package, plus workspace and `Cargo.lock` handling) but its unit is a *config list of files*, not a dependency graph: no range coverage, no cascade policy, publishing is "run your shell command." It also has a business and a visual config studio — two things Callisto lacks.
- **Nx Release** is the "you must adopt our build system" play — powerful (task graph, release groups, commit-based versioning) but the Rust path is plugin-dependent and, per the project's own checked source, its Rust recipe **requires legacy versioning** because the plugin lacks the new `VersionActions` impl. It also won't touch your manifests outside the Nx model.
- **Release-Please** wins on ecosystem breadth and institutional trust but on *model*: it is commit-message-driven (no per-change impact declaration), its multi-component logic is path-based, and its completion semantics (tag/release exist, then a separate publish step) are exactly what Callisto's polyglot doc identifies as the wrong completion policy.

## 5. Where Callisto genuinely wins

1. **It is the only tool whose core model is a real dependency graph across Cargo/npm/PyPI with policy-bearing range semantics** (cascade mode, peer escalation, bump severity, npm-range preservation, per-package overrides with provenance).
2. **The release-execution model is a category first**: committed-decision authority, operation DAG with owner-level publication barriers, observe-before-effect idempotence, receipts as the only completion proof. No competitor treats a multi-provider release as a verifiable, re-runnable effect system.
3. **The napi-rs / Maturin / dual-manifest problem is its natural home**: platform-specific npm packages pinned via `optionalDependencies`, published before the owner, with owner `version` authority over a Python distribution. This is a real, frequent, *unsolved* problem in Rust tooling (Rust → JS bindings and Rust → Python bindings), and Callisto is the only tool I know addressing it with correct ordering semantics.
4. **Changeset compatibility** removes the single biggest migration cost in the category.
5. **Engineering trust signals** (safe Rust, ADRs, spec JSON, findings register, fault-injection sim, 90% coverage gate, format-preserving writes, honest "another tool may fit better" guidance) are materially stronger than anything in the competitor set.

## 6. Weaknesses, risks, and the honest gaps

1. **Adoption: zero.** This is the dominant risk. Changesets has a decade of network effects, a bot, a community, and v3 momentum; Release-Please has Google behind it; Knope has a company and a visual product; Nx has the Nx install base. Callisto has one maintainer, one company, and pre-v1 status. A single-binary Rust tool has an adoption surface, but the doc's own 10-minute first-public-release goal is **unverified** (Python artifact build blocked on sandbox network; no hosted publication exercised).
2. **It cannot yet prove its own core promise end-to-end.** The roadmap is explicit: v0.9's *immediate* priority is making the self-release actually work, because the managed release-PR path failed in the wild (E281) and release PR #113 is stale — with the instruction "do not merge stale #113 as a workaround." A release tool that cannot yet ship itself is a demo until the merge lands.
3. **Open confirmed defects hit the flagship safety story** (from [V1-FINDINGS.md](/Users/gabe/Projects/callisto/docs/projects/V1-FINDINGS.md)): 
 - `SYS-RETRY` — tag created, push fails, fresh `release` says "Nothing to release." with no receipt (violates the retry contract that is the product's headline claim).
 - `SYS-BARRIER` — a dual Cargo+npm package can get its shared tag/public release after only one distribution's publish.
 - `SYS-PYFILES` — PyPI observation accepts *any* matching file, so a partial wheel/sdist upload can be adopted as complete; yank semantics are also coarse (per-file yank vs version-level).
 - `SYS-OWNER`/`SYS-DEMOTION` — historical tag ownership breaks across renames/sibling changes.
 - `SYS-MATURIN` — a fresh co-located Cargo+Maturin repo fails discovery (E007) despite static+dynamic version support being a stated v1 target.
 The register's honesty mitigates this; the fixes (T06–T09, ~10 work units) have to land for v1 to be credible.
4. **DX is unproven with real users.** The interactive surface is thinner than Changesets' famous wizardry (add/status prompts exist, but no community stress-testing); output quality, error ergonomics in the wild, and first-run friction are self-assessed only. The generated-workflow surface (build-matrix shapes, napi rosters, Maturin non-support) is where onboarding will get jagged — `init` for a Maturin repo currently ends in a dead end.
5. **Python lockfiles are out of scope** (no `uv.lock`/`requirements.txt` refresh) while Cargo and pnpm are handled — an asymmetry a Python-heavy team will notice immediately.
6. **License strategy is a double-edged sword.** FSL-1.1-MIT on four of five crates is a reasonable open-core shape (MIT model as the wedge), but FSL triggers for internal-only use can block enterprise adoption; the 2-year MIT transition is slow.
7. **Bus factor & repo hygiene.** 653/673 commits by one person. Minor: stray `*.profraw` coverage artifacts litter the cli crate directory (properly gitignored, but noisy); `mutants.out/`, `lcov.info`, `.DS_Store` at the root; the cli `dump/` directory. None severe, but the signal matters.
8. **Scope gravity.** The v1 plan is 24 work units of *corrections* before new features; the polyglot model is the right restraint, but the identity/authority/required-output design (D01 checkpoint) is a genuinely hard modeling problem, and the current `PackageId` triple (display/locator/canonical) is an interim that carries known migration hazards.

## 7. Verdict

**As an engineering artifact: excellent, arguably the best-crafted release tool I've examined** — the type-level dry-run safety, format-preserving writes, decision-file release authority, pure state-machine executor with fault-injection verification, and the findings-register documentation discipline are all one level above the competition's bar. The architecture is coherent, layered, and its constraints are enforced rather than documented.

**As a product: a credible wedge play with an unproven engine and zero users.** It is not competing with Changesets in JS monorepos (it shouldn't); it competes in a real, underserved niche — **Rust-first organizations shipping multiple registry surfaces (crates.io + npm bindings + PyPI wheels) from one repo** — where today's answer is "Knope with a config list" or "three different tools plus prayer." The open retry/barrier/PyPI-completion defects must close for v1, because the safety guarantees *are* the product.

**Priorities I'd weigh most heavily:**
1. Land the v0.9 self-release (T01 merge + working self-release) — the tool must ship itself before any external pitch.
2. Fix `SYS-RETRY` and `SYS-PYFILES` — they undermine the two loudest claims (rerun safety, complete publication).
3. Find five design-partner repos (napi-rs and Maturin shops are the obvious beachhead) and validate the 10-minute first release against them, including the Python build path that the sandbox blocked.
4. Keep the changeset-compatibility surface strictly compatible (it's the migration asset); watch Changesets v3 for any movement toward other registries.
5. A second human maintainer or a formal sponsorship path — this much surface area under one person is the single largest existential risk.
