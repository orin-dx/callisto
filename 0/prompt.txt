### [High] `MoonProjectLocator` silently drops Python and Go packages from the workspace graph

- **Status**: CONFIRMED (`crates/callisto-moon/src/locator.rs:119-138` and `:161-175` fully traced)
- **Location**: `crates/callisto-moon/src/locator.rs:L119-138` (`projects()`), `L161-175` (`declared_edges()`)
- **Classification**: Hardcoded constant / Spec Drift
- **Root Cause**: Both `projects()` and `declared_edges()` check only `Cargo.toml` and `package.json` to infer the ecosystem for a moon project root. `pyproject.toml` (Python/PEP 440 — a live, non-stub ecosystem per the git log and FINDINGS history) and `go.mod` (Go, specified in the architecture docs) are not checked. A moon workspace project that contains only `pyproject.toml` passes the `abs_path` loop but both `has_cargo` and `has_npm` are false, so no `ProjectRoot` is pushed and the package is silently absent from callisto's graph. The same blind spot repeats in `declared_edges()`, which uses identical `Cargo.toml`/`package.json` sniffs to pick `from_eco`/`to_eco` and `continue`s on anything else.
- **Failing Scenario**: A moon workspace with `packages/py-svc/pyproject.toml` as a Python package. `callisto status` (or any other command) through the moon extension reports zero packages for that entry — no error, no warning, no graph node. Cross-ecosystem dependency edges from a Cargo package to `py-svc` are silently dropped by `declared_edges()`.
- **Severity**: High
- **Verification Strategy**: Add a `has_python = abs_path.join("pyproject.toml").exists()` check alongside the existing `has_cargo`/`has_npm` pair; assert a fixture moon project graph containing a `pyproject.toml`-only project root now appears in `projects()` output.

### [Medium] Moon version constraint string duplicated — parse string and error display can drift

- **Status**: CONFIRMED (`crates/callisto-moon/src/extension.rs:L27-35` fully traced)
- **Location**: `crates/callisto-moon/src/extension.rs:L27-35`
- **Classification**: Hardcoded constant / duplication hazard
- **Root Cause**: `check_moon_version` hardcodes the version range twice as two separate string literals: once to parse into a `semver::VersionReq` (`"&gt;=1.30.0, &lt;2.0.0"`) and once inside the returned `Err` as the human-facing `required:` field. If the `parse` string is updated (e.g., to `"&gt;=1.35.0, &lt;2.0.0"`) but the `Err` string is not (or vice versa), the error message silently lies to the user. Additionally, `.unwrap()` on a compile-time constant string means a typo in that string (invalid semver req syntax) turns into a runtime panic, not a compile-time failure.
- **Failing Scenario**: Developer updates the accepted range to `"&gt;=1.35.0"` in the `parse` call but misses the `required:` string in the `Err`; users running moon 1.31 receive `"moon &gt;=1.30.0, &lt;2.0.0 required"` as the error even though 1.31 is now accepted.
- **Severity**: Medium

### [Medium] Severity mapping entirely hardcoded with no user extension point

- **Location**: `crates/callisto-conventional/src/severity.rs:L5-13`
- **Classification**: Hardcoded constant / no configurability
- **Root Cause**: `raw_severity` is a fixed `match` with three literal arms: `"feat"` → `Minor`, `"fix" | "perf" | "revert"` → `Patch`, `_` → `None`. - **Failing Scenario**: A team tracking `"security"` commits (common in security-sensitive monorepos) as a conventional commit type. All their security commits produce `Severity::None`, so no version bump is ever inferred from them. The fix (changeset) must be placed manually every time.
- **Severity**: Medium

### [Low-Medium] `Path::display()` for git pathspec arguments produces backslash paths on Windows

- **Status**: CONFIRMED (`crates/callisto-vcs/src/shell.rs:L131` fully traced)
- **Location**: `crates/callisto-vcs/src/shell.rs:L131`
- **Classification**: OS assumption / path separator
- **Root Cause**: `pathspecs.iter().map(|p| p.display().to_string())` uses `std::fmt::Display` for `Path`, which emits backslash separators (`\`) on Windows. These strings are then appended as `-- &lt;pathspecs&gt;` arguments to `git log`. Git on Windows accepts forward slashes in pathspecs but may not correctly handle native backslash-separated paths in all invocation contexts, particularly when the repo uses a Unix-style index (common in cross-platform repos).
- **Failing Scenario**: Callisto running on Windows (or in a WSL/Cygwin hybrid environment) with a package at `crates\pkg-a`. The shell fallback's `git log` receives `-- crates\pkg-a`; git may interpret this as a file named literally `crates\pkg-a` rather than the directory `crates/pkg-a`, returning an empty commit list.
- **Severity**: Low-Medium (Low given darwin-only deployment declared in env, but a latent cross-platform defect)
