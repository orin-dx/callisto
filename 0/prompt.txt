**1. Stop running `moon_wasm_sandbox` three times per `just ci`. [safe to just do, highest impact]**
Confirmed in `.config/nextest.toml` and `Justfile`: this is the single slowest test file (wasmtime sandbox spin-up, serialized to `max-threads=1`). It currently runs three times per `just ci`: once in `test`'s `cargo nextest run --workspace`, again explicitly in `wasm-check`'s `cargo test -p callisto-moon --test moon_wasm_sandbox`, and a third time inside `coverage`'s `cargo llvm-cov --all-features` (which re-runs the whole suite under instrumentation). **2. Don't run `coverage` on every local `just ci`. [worth discussing — changes what `just ci` means]**
Real CI (`callisto-ci.yml`) already runs coverage as its own parallel job on a separate runner — locally it's tacked onto the end of a serial pipeline, recompiling the entire workspace a third time under instrumentation. **3. Upgrade `cargo-llvm-cov` 0.8.7 → 0.9.0+. [safe to just do, moderate impact]**

- Version PR automation via GitHub Action → **Yes** — callisto-action does this.
- Prerelease mode (`changeset pre enter/exit`) → **Yes** — `callisto pre enter/exit`.

**Knope** (knope-dev/knope)
- Conventional-commits + changesets combined → **Yes** — callisto's `inference` feature + changeset files, same dual-mode.
- GitHub release + changelog generation → **Yes**.
- Knope Bot draft releases **with asset attachment** → **No** — callisto has no binary/asset upload to GitHub Releases at all (see below).

**release-please** (googleapis/release-please)
- Parses Conventional Commits from git history to auto-determine bump/changelog, no manual changeset files required → **Partial** — callisto's `inference` feature does this, but it's opt-in behind a Cargo feature flag, not the primary/default flow the way it is for release-please (callisto's default flow is changeset-file-based, like changesets, not commit-parsing-based).
- Manifest-driven monorepo component tracking → **Yes** — callisto's own manifest walk does this natively, arguably more robustly (real per-ecosystem manifest editors vs release-please's config/manifest JSON).
- Zero manual intervention (merge PR → tag → GitHub release) → **Yes**.

**Nx release**
- `nx release` version/changelog/publish in one command → **Yes** — `callisto version` + `callisto publish` (split, not fused, but equivalent).
- Independent per-project vs grouped versioning → **Yes** — ungrouped packages version independently; fixed/linked groups available.
- "Version plans" (file-based bump declarations, Nx's own changesets-alike) → **Yes** — this *is* callisto's core changeset mechanism.
- Skip release if no relevant commits → **Yes** — empty-changeset diagnostic/gating.

### Genuinely missing or partial (not scope-boundary items)
1. **No binary/asset upload to GitHub Releases.** `PublishTarget::GitHubRelease` exists as an enum variant but is explicitly unimplemented (`publish.rs:358-372`) — a warning diagnostic fires and nothing publishes. callisto-action creates GitHub Release *entries* (tag + changelog notes) but never attaches build artifacts to them. Knope supports this natively (draft releases with configured assets); changesets/release-please/nx don't do this natively either (it's normally a separate `gh release upload` or `softprops/action-gh-release` step), so callisto is at parity with the npm-ecosystem tools here — the gap is specifically against Knope, not universal.
2. **Commit-parsing-only mode (release-please's core model) is secondary, not primary**, in callisto — it exists but is feature-flagged behind changeset-file-first design.
3. **No `@changesets/cli` config-migration path** (already flagged this session) — a real, still-open v0.4-committed item, unrelated to this comparison but worth repeating.

Something else for you to look into and deliberate:

Short answer on the four tools: none of them solve this natively. They're all version-bump/changelog engines; the native-binary-publish-ordering problem is universally solved by bolting napi-rs's own tooling (napi build / napi create-npm-dirs / napi artifacts / napi prepublish) onto a custom CI step, regardless of which one you use.

- Changesets: platform packages are typically listed in .changeset/config.json's ignore array — excluded from changesets' own version-bump/changelog reasoning entirely. A separate build-matrix CI step generates each platform package.json (version copied from the main package, not independently decided) and npm publishs it directly. Changesets only ever publishes the wrapper package, after that matrix step finishes.
- release-please: same shape — its manifest config only tracks "real" packages; platform dirs are generated/published by a hand-rolled matrix job release-please knows nothing about.
- Nx release: closest to first-class support, because Nx itself ships this way. It models the platform packages as real projects in the dependency graph, so nx release publish respects topological order (native packages before the wrapper) automatically. The binary build + optionalDependencies injection is still custom, but the ordering is a built-in primitive there in a way it isn't in the others.
- Knope: lower confidence, but I'm not aware of it having anything special here either — same custom-matrix pattern would apply.

The common thread: version-bump tools treat these platform packages as either invisible or as dumb publish targets whose version is copied, never independently decided. The actual "build N binaries, publish each first, then publish the thing that depends on them" choreography always lives in your own CI, not the release tool.

For your repo specifically, I checked callisto.toml — it's worse than "not sequenced," it's not tracked at all. The [[package]] list only covers 2 crates + 3 npm wrapper packages (cli, napi, vite-plugin). All 10 platform packages (5 for cli, 5 for napi) have zero entry in callisto's publish plan. So right now, even a working callisto run would never publish them — this isn't just an ordering gap, it's a missing step entirely.

Recommendation: yes, wire it into release.yml, structured as three phases:
1. Callisto does version-decision only (no publish) — it needs to run first regardless, since the platform packages' versions are copied from whatever it decides for cli/napi.
2. A new build-matrix job (per target) runs napi b/manual package.json generation with the now-knownversion → npm publish for each of the 10 platform packages, keyed off Cargo's oxc-react-docgen/oxc-react-docgen-napi versionthat callisto just decided.
3. Callisto's actual publish: true step runs last, publishing cli/napi/vite-plugin — by which point their optionalDependencies resolve cleanly.

That's a real workflow restructure (splitting call publish calls, adding a build matrix), not a small patch. Want me to check whether callisto-action/the callisto CLI even exposes a version-only vs. publish-only split before I sketch the actual release.yml changes?
