### [Critical] `parse_pre_json` hardcodes `VersionGrammar::SemVer` for all `initialVersions` — breaks any Python pre-release lifecycle

- **Status**: CONFIRMED — path fully traced.
- **Location**: `crates/callisto-format/src/pre.rs:L95`
- **Classification**: Strategy/dispatch hardcode (Pattern 1)
- **Root Cause**: `parse_pre_json` deserializes every entry in `initialVersions` via `Version::parse(v_str, VersionGrammar::SemVer)`. `write_pre_json` serializes `Version` via its `Serialize` impl which writes the raw string — so a PEP 440 initial version like `1.0.0a1` (a perfectly legal Python pre-release baseline) roundtrips through the file as the string `"1.0.0a1"`. On read-back, `Version::parse("1.0.0a1", VersionGrammar::SemVer)` fails because `a1` is not a valid SemVer pre-release token. The `Version::deserialize` multi-grammar fallback fix (in the findings ledger) does NOT help here — `parse_pre_json` does not go through serde; it calls `Version::parse` explicitly with a hardcoded grammar. Result: `Err(PreJsonError::InvalidInitialVersion)` propagates, killing any cascade or `pre exit` command for that workspace.
- **Failing Scenario**: A workspace with a Python package at version `1.2.3a1` calls `callisto pre enter next`. `write_pre_json` stores `"1.2.3a1"` in `initialVersions`. On the next `callisto version`, `parse_pre_json` returns `InvalidInitialVersion { package: "my-lib", raw: "1.2.3a1", source: ... }`. The entire version command aborts. The same failure occurs for any PEP 440–exclusive version string (`.dev`, `.post`, epoch-prefixed, etc.).
- **Fix direction**: `parse_pre_json` must try SemVer first and fall back to Pep440, exactly as `Version::deserialize` now does. Alternatively, store the grammar alongside the version in the JSON (breaking the wire format) or use `serde_json::from_value::&lt;Version&gt;` which goes through the now-correct `Deserialize` impl.
- **Verification**: Write a `pre.json` with `initialVersions: { "my-pkg": "1.2.3a1" }` and call `parse_pre_json` — observe `Err(InvalidInitialVersion)`. Confirm that `write_pre_json` round-trips `Version::parse("1.2.3a1", VersionGrammar::Pep440)` as `"1.2.3a1"`.

### [High] `PyprojectToml::update_dependency_spec` silently returns `Ok(())` when the named dependency is not found — cascade falsely believes the write succeeded

- **Status**: CONFIRMED — end-to-end path traced.
- **Location**: `crates/callisto-manifests/src/python.rs:L362-L370`
- **Classification**: Silent Fallback (Pattern 5, Hazard 4)
- **Root Cause**: After scanning both the PEP 621 array and the Poetry table, if neither contains the named package, `updated` remains `false` and the function returns `Ok(())` unconditionally. `CargoToml::update_dependency_spec` and `PackageJson::update_dependency_spec` both return `Err(ManifestError::DependencyNotFound)` when the dependency is absent. Python's implementation diverges: a silent success. The cascade graph then records the spec rewrite as applied, proceeds, and the manifest is never modified.
- **Failing Scenario**: A workspace has two Python packages; package B lists package A as a PEP 621 dependency. After cascade computes a bump for A, it calls `update_dependency_spec("package-a", DepKind::Runtime, new_spec, permit)` on package B's `PyprojectToml`. If the dependency entry name in `pyproject.toml` is `package_a` (underscore, per Python normalization) and the cascade resolved the name as `package-a` (hyphen, per the manifest's declared name), the name comparison `pkg_name.eq_ignore_ascii_case(name)` fails (underscore vs. hyphen), `updated` stays `false`, `Ok(())` is returned, and B's `pyproject.toml` is not updated. The cascade log shows success; the file on disk is stale.
- **Fix direction**: Replace the final `Ok(())` with `Err(ManifestError::DependencyNotFound { ... })` when `!updated`, mirroring `cargo.rs` and `npm.rs`. Additionally, normalize hyphens/underscores in the name comparison per PEP 503/508.
- **Verification**: Test `update_dependency_spec("nonexistent-pkg", DepKind::Runtime, ...)` against a `PyprojectToml` — expect `Err(DependencyNotFound)`, currently get `Ok(())`.

### [High] `WorkspaceCargoResolver` does not strip or restore BOM — silently corrupts workspace-root `Cargo.toml` with BOM on every write

- **Status**: CONFIRMED in findings ledger as flagged, not yet fixed.
- **Location**: `crates/callisto-manifests/src/cargo.rs:L488-L506` (`load`), `L641-L648` (`persist`)
- **Classification**: BOM/encoding handling inconsistency (Pattern 7), I/O Safety
- **Root Cause**: `CargoToml::open` records `has_bom` and restores it on `persist()`. `WorkspaceCargoResolver::load` reads the file with `fs::read_to_string` with no BOM stripping; its `persist()` calls `self.document.to_string()` with no BOM prepend. `toml_edit 0.22.27` does strip the BOM on parse internally — so the rendered output loses it. A workspace-root `Cargo.toml` with a BOM will have the BOM silently removed on the first inherited-version or inherited-dep write.
- **Failing Scenario**: Any Cargo workspace using `version.workspace = true` or `dep = { workspace = true }`, where the root `Cargo.toml` was authored on Windows (common Windows editor behavior is to emit UTF-8 BOM). After `callisto version`, the file on disk loses the BOM, making git mark it dirty with a spurious byte-level change.
- **Fix direction**: Mirror `CargoToml::open`'s BOM handling: detect `has_bom` in `WorkspaceCargoResolver::load`, prepend in `persist()`.

### [Medium] `PyprojectToml::iter_dependencies` does not iterate Poetry dev-dependencies or group-dependencies — cascade graph is blind to those edges

- **Status**: CONFIRMED — examined `python.rs:L210-L282`.
- **Location**: `crates/callisto-manifests/src/python.rs:L210-L282`
- **Classification**: Hardcoded dependency section names (Pattern 8), Spec Drift

- **Fix direction**: Extend `iter_dependencies` with the missing sections. Poetry group deps require iterating `tool.poetry.group` as a table, then each group's `dependencies` sub-table.

### [Medium] `CargoToml::iter_dependencies` ignores `[target.'cfg(...)'.dependencies]` — platform-specific Cargo deps are invisible to the cascade graph

- **Status**: CONFIRMED — `cargo.rs:L55-L77, L232-L269` iterate only the three top-level sections.
- **Location**: `crates/callisto-manifests/src/cargo.rs:L55-L77` (`open`, inherited_deps detection), `L232-L269` (`iter_dependencies`)

Cargo's `[target.'cfg(windows)'.dependencies]`, `[target.'cfg(unix)'.dev-dependencies]`, etc. are never visited. - **Fix direction**: In `iter_dependencies`, iterate `document.get("target").as_table_like()`, then for each target key iterate `["dependencies", "dev-dependencies", "build-dependencies"]` sub-tables.

### [Medium] `pre.rs` `parse_pre_json`'s `initialVersions` grammar is hardcoded; `update_dependency_spec` in Python discards `_kind` parameter entirely

- **Status**: CONFIRMED (two separate issues under one pattern).
- **Location**: `crates/callisto-manifests/src/python.rs:L285-L290`, `crates/callisto-format/src/pre.rs:L95`
- **Classification**: Discarded Parameter (Pattern 1 / Hazard 1)
- **Root Cause**: `PyprojectToml::update_dependency_spec` accepts `_kind: DepKind` (explicitly underscore-prefixed, silently dropped). PEP 621 has distinct sections for `[project.dependencies]` (runtime), `[project.optional-dependencies]` (optional), and `[tool.poetry.group.dev.dependencies]` (dev). ### [Medium] Magic strings `"*"` and `"&gt;=0.0.0"` used as sentinel/synthetic specs in `PyprojectToml::iter_dependencies`

- **Status**: CONFIRMED — `python.rs:L230-L236`.
- **Location**: `crates/callisto-manifests/src/python.rs:L230-L236`
- **Classification**: Magic strings (Pattern 3)
- **Root Cause**: When a PEP 508 dependency string has no version operator (e.g. `"requests"`), `op_idx` is `None`, `req_str` is set to the string literal `"*"`. This sentinel is then immediately replaced by the string `"&gt;=0.0.0"` to construct a parseable `VersionReq`. Neither `"*"` nor `"&gt;=0.0.0"` is a named constant. `"&gt;=0.0.0"` then appears in the `DepSpec::Range`'s raw string, meaning `round_trip` will rewrite it to a real constraint instead of leaving the entry unconstrained. A dependency like `requests` (no constraint) would become `requests&gt;=1.2.3` after cascade — changing the user's intended semantics.
- **Failing Scenario**: `pyproject.toml` contains `dependencies = ["requests"]`. After cascade updates `requests` from workspace, `update_dependency_spec` rewrites the entry to `requests&gt;=2.31.0`. The user's intentionally-unconstrained dep is silently pinned.
- **Fix direction**: Represent unconstrained deps as `DepSpec::Opaque("*")` or add a `DepSpec::Unconstrained` variant. Do not synthesize a `"&gt;=0.0.0"` Range for them.

### [Low] `CommitSha` hardcodes SHA-1 length (40) and short-SHA length (7) — git SHA-256 migration will silently break parsing

- **Status**: CONFIRMED — `identity.rs:L303-L319`.
- **Location**: `crates/callisto-model/src/identity.rs:L303-L310`, `L319`
- **Classification**: Magic numbers (Pattern 3)
- **Root Cause**: `CommitSha::parse` validates `trimmed.len() != 40`. `CommitSha::short` returns `&amp;self.0[..7]`. Both values are SHA-1 constants. Git is actively adding SHA-256 object support (OID length 64 hex chars, short SHA typically 8-12 chars). A SHA-256 repository or a future git version that defaults to SHA-256 would have every commit SHA rejected by `CommitSha::parse`.
- **Fix direction**: Accept both 40-char (SHA-1) and 64-char (SHA-256) inputs; define constants `SHA1_LEN: usize = 40`, `SHA256_LEN: usize = 64`, `SHORT_SHA_LEN: usize = 7`. Or make short length dynamic (min of 7 or the full length).

### [Low] `atomic_write` silently discards directory `sync_all` errors

- **Status**: CONFIRMED — `atomic.rs:L50-L58`.
- **Location**: `crates/callisto-manifests/src/atomic.rs:L50-L58`
- **Classification**: I/O Safety — `let _res = ...` discard (Hazard 6)
- **Root Cause**: The parent and grandparent directory `sync_all()` calls are wrapped in `let _res = parent_file.sync_all()` — the error is captured but silently dropped. The docstring claims "parent and grandparent directory journal flushing" as a durable-write guarantee. On filesystems or kernel versions where directory fsync fails (e.g., `ext3` with `data=ordered`, or EROFS on a mounted read-only path), the function returns `Ok(())` while the directory entry change is not durably committed to disk. The file content is durable (the `sync_all` on the temp file succeeds), but the directory entry pointing to it is not — a crash between persist and directory sync leaves an orphaned inode.
- **Fix direction**: Document explicitly as best-effort (not a hard durability guarantee), or propagate directory sync errors as `io::Result::Err`. Given that many common filesystems return `EINVAL` for `fsync` on directories, the pragmatic fix is documentation — but current doc text overpromises.
