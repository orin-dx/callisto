[58] assistant: Yes. We need a deliberate architectural re-evaluation before building more effects.

The P0 work exposed that our original model split was directionally right, but still too weak at the boundary between “approved intent” and “what an executor is allowed to do.”

The main conclusion: make the durable release chain explicitly four layers, not one broad “release” feature.

```text
Release decision
  → Durable intent
    → Validated private capability
      → Execution state / receipts
```

- Release decision is the policy outcome: selected packages, target versions, prerelease/group/cascade decisions. It must be a first-class, explainable graph result—not partially reconstructed from `PublishPlan`.
- Durable intent is serializable, canonical, credential-free, and approval/artifact-friendly.
- Validated capability is graph-private and non-transferable. It owns prepared inputs, the trusted root/lock, and revalidation data.
- Execution state and receipts are serializable evidence bound exactly to one intent.

What we should change now:

1. Strengthen the durable semantic model.

`RegistryKey` is not enough. A public npm registry and a private npm registry must have distinct durable operation identities even for the same package/version. We have now prototyped the right fix: `RegistryBindingId { logical registry key, normalized binding digest }`, with no raw endpoint retained.

This should be generalized as a rule: any remote target that affects operation identity needs a typed, credential-free binding identity. Registry, Git tag target/annotation policy, and forge release binding should not be hidden in generic string fingerprints.

2. Replace generic snapshot components with typed semantic projections.

`ReleaseInputComponentV1 { kind: String, fingerprint }` is too permissive: it allowed us to hash raw `callisto.toml` bytes, which can encode secret-bearing URLs and makes comments/key order affect authorization.

The intent snapshot should instead have typed, validated projections such as:

- source trust identity;
- selected `ReleasePackageId`/version/manifest-role/path fingerprints;
- effective release policy;
- typed registry binding identities;
- tag policy;
- group/cascade/prerelease inputs;
- dependency-edge projection relevant to the selected release DAG.

This improves security, reviewability, determinism, and error messages. Equivalent TOML formatting should not change an intent; a semantic policy change must.

3. Make `ValidatedReleaseIntent` a real authority object.

It currently needs to own an exact `BTreeMap<ReleaseOperationId, PreparedOperation>` built during the same fresh observation as the intent:

- Registry: package directory, qualified package/version, binding identity, parsed safe endpoint, ecosystem publish options, artifact reference/digest.
- Tag: rendered `TagName`, exact commit, annotation policy/message.
- Forge release: exact tag and target binding.
