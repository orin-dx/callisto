### Specific Blocker

**mmap is not implemented in WASI.** Both code paths fail at the same syscall:

- **Loose objects** (prior run): `Find(Loose(Io { source: Kind(Unsupported), action: "open or map", path: "/.git/objects/..." }))`
- **Packed objects** (this run): `Find(PackedOpen(Io(Kind(Unsupported))))`

`std::io::ErrorKind::Unsupported` is WASI's response to `mmap()` — it returns ENOSYS. Both `gix-odb` (loose object reader) and `gix-pack` (pack index + data reader) use memory-mapped I/O internally. There is no public API in either crate to opt into read-based I/O instead. The callisto repo's objects happen to be fully packed right now, so the pack path fails first.

The WASI filesystem preopens work correctly — the `.git` directory is visible, `gix-odb::at()` succeeds, `gix-ref::file::Store::at()` succeeds, and `ref_store.find("HEAD")` resolves the HEAD commit OID successfully. The failure is strictly in `odb.header()` / any object read.

### Verdict Summary

**NO-GO for gix-native object reads inside WASM.**

- gix-ref (ref reads, HEAD resolution, branch name resolution) — **works** in WASI via regular file I/O
- gix-odb / gix-pack (any object content or header read) — **fails** with `Unsupported` (mmap ENOSYS)

The correct approach for `callisto-moon` remains the current exec-seam design: shell out to the host's `git` binary via `warpgate_pdk::exec_command`. A hybrid (native gix-ref reads for lightweight lookups + host exec for commit data) is technically possible but adds complexity for minimal gain. The mmap blocker will not be resolved without WASI gaining mmap support or gix-odb gaining an opt-in read-fallback path, neither of which is imminent.

### [High] `apply_version_plan` crash during changeset deletion loop produces double-bump on retry

- **Status**: CONFIRMED (execution path fully traced)
- **Location**: `crates/callisto-graph/src/apply.rs:75-141`
- **Classification**: I/O Safety / Crash-Safety (Un-Transactional Disk Mutation)
- **Root Cause**: `apply_version_plan` writes version bumps to all manifests first (L75-93, each individually atomic via `atomic_write`), then enters a deletion loop for consumed changesets (L130-141, one `fs::remove_file` per changeset file). If the process is killed between changeset deletions — after manifests are fully updated to their new versions but while changeset files remain on disk — the workspace is left in a state where some changesets are deleted and some are not. On retry, `plan_version` calls `base_versions()` which reads the already-bumped version from each manifest, then finds the surviving changeset files and computes a further bump from the already-bumped base. The result is a double version bump (e.g., `1.0.0 → 1.1.0 → 1.2.0`) with no error or warning.
- **Failing Scenario**: Three packages A, B, C each with a pending minor changeset. Process is killed after A's and B's manifests are written to `1.1.0` and A's changeset is deleted, but before B's and C's changesets are deleted. Re-running `callisto version` reads base versions `[A=1.1.0, B=1.1.0, C=1.0.0]`, finds changesets for B and C, and produces `[B: 1.1.0 → 1.2.0, C: 1.0.0 → 1.1.0]`. B is double-bumped.
- **Severity**: High — version double-bumping is a release-correctness violation in a release management tool; once published to a registry, a spurious version cannot be retracted from crates.io.
- **Verification Strategy**: A test that: (1) calls `apply_version_plan` on a plan with two packages and two changesets, (2) simulates a crash by leaving one changeset file on disk while the manifest is at the bumped version, (3) calls `plan_version` again, and asserts the returned plan is empty (no further bumps). Currently, the second `plan_version` call produces spurious bumps.
