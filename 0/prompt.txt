Some further context from codex:



<pasted_content id="cd46">
Callisto is partially aligned with the e18e publishing guide (https://e18e.dev/docs/publishing.html). The largest gaps are npm build/publish isolation, token-first setup guidance, and staged publishing. Our decision to delegate authentication to native tools remains sound.

I inspected the current checkout, generated workflows, npm adapter, credential handling, and live repository rules. Callisto itself currently distributes through Cargo and GitHub Releases; it has no tracked npm package. The npm assessment therefore concerns the publishing service we provide to users.

| Area | Assessment | Evidence |
|---|---|---|
| Pinned actions | Aligned | Generated workflows use full commit SHAs; our repository has Dependabot for actions. |
| Restricted permissions | Partially aligned | Permissions are job-scoped, but generated publishing jobs also need repository writes for tags. |
| Native OIDC | Compatible, poorly documented | The runner preserves npm’s GitHub OIDC inputs, and token configuration is conditional. Our setup documentation describes tokens rather than a complete tokenless path. |
| Provenance | Partially aligned | Generated workflows request npm provenance. This does not establish that execution uploads a previously verified npm archive. |
| Build/publish separation | Significant gap | npm publishes a workspace/directory and can execute publishing hooks. We do not transport a sealed npm tarball from an isolated build. |
| Disabled lifecycle scripts | Deliberate difference | Publishing hooks explicitly retain their normal behavior. |
| npm staging | Unsupported | We invoke direct publishing and have no staged-submission lifecycle. |
| Package validation | Missing integration | Generated workflows do not run publint or validate packed npm contents. |
| Review protection | Partially aligned | Live main rules require one review and dismiss stale approvals, but latest-push approval is disabled and bypass actors exist. |
| Immutable releases | Not currently demonstrated | The latest release, callisto@0.21.1, reports immutable: false. |

The most useful changes are the following.

1. Make “build once, publish those exact bytes” available for npm.

The npm adapter currently ignores its artifact-manifest argument and publishes from the checkout. That allows prepublishOnly, prepack, and other native hooks to execute with publishing authority. This is documented behavior, so silently disabling hooks would break our existing contract. See npm adapter (crates/callisto-graph/src/commands/release/provider/registry/npm.rs:197) and publishing-hook policy (docs/releasing.md:64).

I recommend an explicit prepacked publishing route:

- Build and pack without npm publishing authority.
- Use the appropriate native packer so workspace dependency transformations remain correct.
- Validate the packed package’s identity, version, contents and dependency references; run publint there.
- Record the archive’s digest in our existing artifact contract.
- Upload that verified archive without rebuilding or running package hooks.

This fits our current architecture. It needs an npm artifact model and adapter support, not a new execution framework.

2. Treat OIDC permission as publishing authority—even without an npm token.

Our generated matrix build job has id-token: write for attestations. If an npm package trusts that same workflow without an environment restriction, build code can also request credentials for npm publication. Keeping NPM_TOKEN out of the build job does not isolate that authority. This is conditional on the package’s trusted-publisher configuration; I did not attempt a live token exchange. See matrix permissions (crates/callisto-graph/src/templates/matrix_workflow.tmpl:101) and npm’s trust configuration (https://docs.npmjs.com/trusted-publishers/).

For generated npm workflows, we need a deliberate trust boundary: for example, a customer-configured environment restriction or a separate publishing workflow identity. A branch if: condition alone is insufficient when a writer can modify the workflow on another branch.

Our own repository explicitly forbids GitHub Environment/reviewer gates. I have preserved that policy. The guide identifies a tradeoff to document and address in customer workflows; it does not authorize changing our release approval model.

3. Improve OIDC setup while continuing to let npm own authentication.

The existing runner largely gets out of npm’s way. The action only creates token configuration when NPM_TOKEN is nonempty. Those are useful foundations.

The missing work is operational:

- Document tokenless trusted publishing as a first-class path.
- Generate a tested Node/npm setup instead of relying on the runner image.
- Keep token authentication available for unsupported providers and registries.
- Explain separate read authentication for private dependencies and registry observations.

Current npm documentation requires npm 11.5.1+ and Node 22.14+ for trusted publishing, while staging requires npm 11.15+. We should test an explicit toolchain combination. We do not need to implement token exchange ourselves. Trusted publishing (https://docs.npmjs.com/trusted-publishers/), staging requirements (https://docs.npmjs.com/staged-publishing/).

Our publishing documentation (docs/publishing.md:42) currently presents two token patterns and a Node 20 example; it needs a distinct modern OIDC recipe.

4. Staging needs a separate completion model.

e18e recommends submitting packages with npm stage publish, followed by maintainer approval. A staged package is not yet publicly available. npm staged publishing (https://docs.npmjs.com/staged-publishing/).

Simply changing our command would be incorrect. Callisto currently waits for public registry visibility before completing publication and permitting announcements. A staged submission could succeed, then our confirmation window would expire while it awaits human approval.

Proper support must distinguish:

- Submitted for approval.
- Publicly published.
- Rejected or conflicting submission.

It also needs rerun handling for versions already staged. npm’s OIDC credentials cannot perform stage inspection or approval, which constrains reconciliation. Approval should remain with npm and the maintainer. This deserves a focused design before adding a staging flag.

5. Tighten the supporting practices without making everything a release gate.

publint belongs in a configurable, credential-free validation step. Account 2FA, npm trusted-publisher permissions and organization Actions restrictions need operator guidance; I could not verify those account-level settings.

The live main ruleset (https://github.com/orin-dx/callisto/rules/22292852) and mutable latest release also differ from the guide’s stricter recommendations. Whether to tighten bypasses, require latest-push approval, or enable immutable stable releases is an owner policy decision.

One caution about copying examples: e18e’s standard template (https://github.com/e18e/setup-publish/blob/main/templates/default.yml) separates packing and stages a tarball, but its linked Changesets template (https://github.com/e18e/setup-publish/blob/main/templates/changesets.yml) builds in the publishing job and does not explicitly invoke staging. The templates themselves provide different guarantees.

My priority order is OIDC documentation/toolchain setup, publishing-authority isolation, verified npm archives, then optional staging support. Native authentication should stay native; Callisto should own the artifact and release semantics around it.

Three focused tests passed for publisher arguments, credential routing and descendant credential inheritance. No live publishing or OIDC exchange was attempted, and no files or settings changed.
