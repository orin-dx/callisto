- schema version;
- workspace root and Git commit SHA;
- digest of relevant config and input changesets;
- expected `from` versions and intended `to` versions;
- ordered mutations and publish operations;
- the diagnostics observed during planning.

Before applying, Callisto would re-check that the workspace still matches the plan’s preconditions. If it does not, it refuses instead of silently applying a stale plan.

This is not a database or hidden mutable state. The plan can be a CI artifact, a checked-in release-PR artifact, or an ignored local file. Its value is human review, reproducibility, and recovery after a partial failure.

For example, if npm publish succeeds, PyPI fails, and the job dies before tags are created, a resume command can report exactly what is already done and retry only what is safe. That is materially better than rerunning a broad release command and hoping every downstream CLI is idempotent.

I would make this opt-in at first. Normal `callisto version` remains ergonomic; production automation uses plans.

## 3. SHA verification vs signed tags

These solve different problems.

A tag name is a pointer:

```text
callisto-cli@0.5.0  ──► commit 627039c4
```

A SHA is the immutable identity of the commit content:

```text
627039c4…  = exactly one Git object
```

Verifying a release tag resolves to the expected SHA ensures the release job acts on the same source that was versioned and approved. It prevents mistakes such as checking out one commit, creating/reading a tag that resolves elsewhere, then publishing mismatched source.

But SHA verification does not answer: “who authorized this tag?”

A cryptographic tag signature, such as GPG or SSH signing, answers that identity question if CI verifies it against trusted keys. Current Callisto code intentionally disables GPG signing while generating tags, so the documentation should not imply signed-tag enforcement exists.

There are three valid policies:

1. SHA-anchored, unsigned tags

   Best default for ease of use. CI verifies tag-to-commit consistency and protected branches/tags control who can push. Documentation says exactly that.

2. Optional trusted signatures

   A `require-signed-tags` policy for security-sensitive repositories. CI verifies the tag signature against an allowlist. This is stronger, but key distribution, rotation, bot signing, and local developer UX become product responsibilities.

3. GitHub-native provenance

   Rely on protected tags plus GitHub Actions identity, artifact attestations, and immutable/draft GitHub releases. This is often more practical than individual GPG keys for modern CI releases.

My recommendation is policy 1 now, with a clean extension point for policy 2. Correct the docs immediately; do not impose signing before there is a real customer/security requirement.

## 4. Release trains / group priority

Fixed and linked groups answer:

> Which packages must align their versions?

They do not answer:

> Which release should proceed when multiple release streams are pending?

Example:

```text
stable releases:     cli, graph
prerelease releases: moon beta, native bindings beta
```

A group-priority policy can say:

```text
If beta train has pending work, prepare only beta.
Otherwise prepare stable.
```

Release Please exposes this as `group-priority`. Nx solves related concerns with release groups and group-specific behavior. This prevents a single release PR from mixing a beta line with a stable line when that would confuse consumers or registry channels.

For Callisto, there are three choices:

- Explicitly reject the feature for now: one release flow at a time; document that fixed/linked groups are not release lanes.
- Add lightweight lanes later: a named lane selects packages, version channel, tag template, registry dist-tag, and exclusivity/priority.
- Build a general scheduler now: flexible but much more configuration, testing, and operational complexity.

I recommend the first choice now, while writing down the boundary clearly. The second becomes worthwhile only when Callisto has a real multi-channel user—not merely because competitors expose it.

Priority order: durable plans are a genuine near-term reliability advantage; SHA/signing clarification is a low-cost security/documentation correction; release lanes are a deliberate future product decision.

[88] user: When the plan is running in CI how do we best handle this? Is there a problem to checking in files that we can forget to clean up? Should it be cached by GH instead?

[89] assistant: Use GitHub Actions artifacts, not Git-tracked plan files and not the GitHub cache.

A cache is the wrong primitive: it is evictable, mutable, optimized for speed rather than integrity, and can be unavailable exactly when a release needs recovery. A checked-in `release-plan.json` is durable but creates cleanup debt and makes ordinary release PRs noisy.

The clean model is:

```text
Version PR
  └─ computes VersionPlan
  └─ applies it
  └─ commits manifests, changelogs, consumed changesets
  └─ uploads plan.json as a CI artifact for review/debugging

Merged version commit / release tag
  └─ verifies exact commit SHA
  └─ computes PublishPlan
  └─ uploads publish-plan.json immediately as an artifact
  └─ publishes in order
  └─ creates tags/releases
```

The committed versioned files are already the durable cross-workflow record. The plan artifact is supporting evidence: it explains exactly why those files changed and lets reviewers inspect the proposed operations before side effects begin.

For partial publish failure, do not rely on a cached or committed “success checkpoint.” Query the authoritative systems on retry:

- registry state: is `package@version` already published?
- Git state: does the release tag point to the expected SHA?
- GitHub state: does the release/release asset already exist?

Then retry only the unfinished idempotent operations. This aligns with Callisto’s existing design principle: state may be a hint, but correctness comes from disk, Git, registries, and GitHub.

The plan artifact should be uploaded immediately after planning—not only at workflow end—so it survives a later failure. It should contain a digest and source commit SHA, and later stages should reject it if either no longer matches.

For normal CI:

- Use job outputs only for small values: plan SHA-256, source SHA, artifact name/run ID.
- Use `upload-artifact` / `download-artifact` for the full JSON plan between jobs.
- Set a moderate retention period, such as 30–90 days.
- Put a concise plan summary and digest into the GitHub job summary or release PR body.

For a manual recovery days later, regenerate the plan from the already-versioned commit, then reconcile it with registry/tag/release reality. That is safer than trusting an old artifact or cache.

So: artifacts for observability and intra-run handoff; committed manifests/changelogs for release intent; external systems for recovery truth.

## Core release binding

Every generated release plan should carry:

```json
{
  "sourceCommit": "627039c4...",
  "configDigest": "sha256:...",
  "inputDigest": "sha256:...",
  "schemaVersion": 1
}
```

At every side-effect boundary, Callisto verifies:

1. The checked-out `HEAD` equals `sourceCommit`.
2. `callisto.toml` and release inputs match their expected digests.
3. A newly created package tag resolves to `sourceCommit`.
4. A pre-existing tag either resolves to that same SHA or fails closed.

This works everywhere Git works. It protects against stale plans, checkout/ref confusion, and tag/commit mismatches. It does not prove who authorized the release.

## GitHub setup

For GitHub Actions, I would use:

- A protected `main` branch and protected release-tag patterns, such as `*@*`.
- A protected GitHub Environment named `release`, with required reviewer approval and scoped secrets.
- Least-privilege `GITHUB_TOKEN` permissions; grant `contents: write` only in the release job.
- Pin every third-party action to a commit SHA.
- Trigger releases only from a protected branch, protected tag, or explicit manual dispatch.
- Check out the exact planned SHA, not a moving branch name.
- Upload the plan and its digest as an artifact before publishing.
- Create a draft release, attach artifacts, then publish it after all assets are present.

Conceptually:

```yaml
release:
  environment: release
  permissions:
    contents: write
    id-token: write
  steps:
    - checkout exact sourceCommit
    - verify HEAD == sourceCommit
    - download and verify publish-plan.json
    - publish packages
    - create tags and verify each resolves to sourceCommit
    - create draft release, upload assets, publish release
```

`id-token: write` enables GitHub OIDC. Use it for keyless artifact provenance/signing where the registry or artifact format supports it; do not put a long-lived signing key in repository secrets.

## Signed tags: optional, not the default

Signed tags are useful only when you have a credible trust policy:

```text
Require tag signature
  → verify tag against a configured trusted key/identity set
  → then verify tag resolves to the planned SHA
```

For human-operated releases, GPG or SSH Git signatures work well.

For CI-created tags, forcing GPG signing is often awkward: you must operate and rotate a bot key, secure it, and make all environments trust it. In that case, GitHub OIDC-backed provenance is generally a better signal than a bot-owned GPG key.

So I would support policy modes:

```toml
[release.provenance]
source-sha = "require"          # portable core behavior
git-signature = "optional"      # verify if present, do not require
```

Later, a security-sensitive organization could set:

```toml
git-signature = "require"
trusted-signers = ["ssh:...", "gpg:..."]
```

Callisto would invoke standard Git verification rather than inventing cryptography.

## Non-GitHub / Bazel

The portable contract stays the same:

```text
CI obtains a trusted source SHA
→ Callisto plans/releases only that SHA
→ CI signs or attests the built artifacts
→ registry/Git release state is reconciled on retry
```

Examples:

- GitLab: protected branches/tags, protected environments, OIDC workload identity.
- Buildkite/Jenkins: restricted release pipeline, short-lived cloud credentials, signed build provenance.
- Bazel: build with an explicitly pinned source revision; produce a provenance statement tying artifact digest, build command, and source SHA together.
- Local release: require an explicit SHA and optionally a Git-signature verification command.

The right abstraction is a `sourceCommit` requirement in Callisto plus forge-specific policy in the workflow. That gives every environment the same correctness guarantees without making GitHub’s model part of the release engine.
