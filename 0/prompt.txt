## New bug found (not just missing coverage)

### [Medium] `apply_version_plan` silently discards git staging failures, then reports success anyway
- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/apply.rs:182` and `:191` (`drop(runner.run("git", &amp;args, root));`)
- **Classification**: Silent Fallback (Taxonomy 4)
- **Root Cause**: `CommandRunner::run` returns `Result&lt;CommandOutput, CommandError&gt;`, and `CommandOutput` can itself report non-zero `exit_code` without being an `Err`. Both call sites (`git add --`, `git rm --cached --ignore-unmatch --`) pipe the result straight into `drop(...)`, discarding process-spawn errors and non-zero exits alike. Immediately after, `outcome.staged = modified_paths;` is set unconditionally — the caller has no way to know staging actually failed.
- **Failing Scenario**: workspace root is not a git repo (or `git` binary missing, or a permission/lock error) during `callisto version`/`apply`; manifests/changelog are written to disk correctly, but `outcome.staged` still reports every path as staged. A caller that trusts `staged` to decide whether to run `git commit` would commit nothing (or commit only some files) while believing the full set succeeded.
- **Verification Strategy**: mock `CommandRunner` to return `Ok(CommandOutput{exit_code: Some(1), ..})` (or `Err`) for the `git add` call; assert `apply_version_plan` either propagates an error or omits/flags the affected paths in `ApplyOutcome`, rather than silently reporting them as staged.
