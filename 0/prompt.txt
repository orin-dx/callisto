  ## Real bugs found: none
  
  The simulator found no production defect. That is the honest result, and I did not weaken anything to get there. What it did surface were two behaviors that are pre-existing deliberate design, which I encoded as explicit, commented exceptions rather than as violations:
  
  **Exception 1 — E173 stranded attempt (254 scenarios).** Whenever a run is interrupted with an operation persisted as `Attempting` while the provider holds nothing (crash after the Attempting save but before the effect, or `EffectFailsBeforeLanding`), a **same-runner** rerun never converges: `recover_interrupted_operations` sees `Absent` and raises `ReleaseRecoveryUnresolved` forever, because `Attempting` is never downgraded to `Pending`. This is exactly what `release_execution.rs:160-164` documents and what E173 says ("Do not retry the effect"). The exception is encoded observationally (`stranded_attempt`), applies **only** to `Mode::SameRunner`, and the test additionally asserts `fresh_unresolved == 0` — a fresh-journal recovery runner resolves *every* non-conflict scenario. If the design ever changes to allow same-runner convergence, that assertion pins the fresh-runner guarantee and the exception becomes dead.
  
  **Exception 2 — registry-lag duplicate (`excused_duplicate`).** A recovery run whose journal was lost, facing an index still serving the pre-publication answer, has only ever seen `Absent` for that operation and re-issues the effect. No executor-level information distinguishes lag from absence there; refusing it is the provider's job, and the simulator asserts the refusal (the world records exactly one landing per operation, checked by the `SecondLandingRecorded` guard). The exception is narrowed to *that operation having actually been lagged* — a provider that merely lies is not excused, which is what the vacuity test below proves.
