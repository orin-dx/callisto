### [Critical] `[[fixed-group]]` and `[[linked-group]]` config blocks are parsed, validated, then silently discarded — group-based version convergence never fires

- **Status**: CONFIRMED (end-to-end traced)
- **Location**: `crates/callisto-graph/src/config/resolve.rs:265-269,327`
- **Classification**: Discarded Parameter / Silent Fallback
- **Root Cause**: `config::load()` constructs `raw_groups` from the parsed TOML and calls `GroupTable::validate_syntactic(&amp;raw_groups)` — but then sets `groups: GroupTable::default()` in the returned `ResolvedConfig`, discarding every resolved group. `GroupTable::resolve()` (`groups.rs:136-221`) is `#[allow(dead_code)]` and is never called from any production code path. Every downstream consumer that reads `ws.config.groups` (including `run_cascade` via `version.rs:70`, `aggregate.rs:341,344`, `groups.rs:26`, `napi.rs:16`) receives an empty table regardless of what is written in `callisto.toml`.
- **Failing Scenario**: A `callisto.toml` with `[[fixed-group]] name = "platform" members = ["pkg-a", "pkg-b"]` — running `callisto version` produces no group union, no divergence check, and no `FixedGroupDivergent` error even when `pkg-a` and `pkg-b` have different on-disk versions. The syntactic validation fires (`EmptyGroup`, `DuplicateGroupName`), so malformed group config is rejected — but valid, well-formed group config is silently dropped.
- **Severity**: Critical (the entire groups feature — including fixed-group convergence and linked-group bumping, both of which have dedicated code paths and tests — is unreachable through the public config interface)
- **Verification Strategy**: Write a `callisto.toml` with a valid `[[fixed-group]]` block, call `config::load()`, assert `result.groups.fixed.is_empty()` — it will always pass today, falsifying the intent. Fix: call `GroupTable::resolve(&amp;raw_groups, &amp;index)` after `ManifestWalkResolver::build` returns the identity index, and store the result. Since `GroupTable::resolve` requires an `IdentityIndex`, this must happen in `Workspace::load` after graph construction, not inside `config::load`.

### [Medium] Unknown and misspelled keys in `callisto.toml` are silently ignored — typos take defaults with no warning

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/config/raw.rs:4-22` (no `#[serde(deny_unknown_fields)]` on any struct), `resolve.rs:167`
- **Classification**: Silent Fallback
- **Root Cause**: `toml::from_str::&lt;RawConfig&gt;` uses serde's default behavior, which ignores unknown keys. No struct in `raw.rs` carries `#[serde(deny_unknown_fields)]`. A `callisto.toml` with `[cascase]` (typo for `[cascade]`), `bump_severity = "minor"` (underscore instead of hyphen), or any other structural typo deserializes successfully with all fields `None`, silently applying defaults.
- **Failing Scenario**: `callisto.toml` containing `[cascade]\nbump_severity = "minor"` (underscore form) — the key does not match `#[serde(rename = "bump-severity")]` in `RawCascadeConfig`, so it is discarded. `cascade.bump_severity` resolves to the default `Patch` with no error or diagnostic. The `provenance` map records `Patch` as `Default`, not `Explicit`, so even the provenance API gives no signal.
- **Severity**: Medium (common class of user error; affects `cascade`, `validation`, and all per-package overrides)
- **Verification Strategy**: Load a `callisto.toml` with `[cascade]\nbump_severity = "minor"` and assert `resolved.cascade.bump_severity == CascadeBumpSeverity::Minor`. It will be `Patch`.

### [Medium] BOM (`\u{FEFF}`) in `callisto.toml` produces a cryptic `ParseToml` error instead of actionable guidance

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/config/resolve.rs:163-169`
- **Classification**: Boundary Condition
- **Root Cause**: `fs::read_to_string` preserves the UTF-8 BOM as the leading three bytes of the returned `String` (`"\u{FEFF}..."`). The `toml` crate does not strip BOM before parsing. The result is `ConfigError::ParseToml { message: "unexpected character '\u{FEFF}'" ... }` — the error message names the character by its Unicode code point rather than saying "the file has a byte-order mark, please remove it."
- **Failing Scenario**: Any editor that saves files with a BOM (common on Windows, some cross-platform tools) produces an unactionable error. This is particularly likely for `callisto.toml` since users author it by hand. Compare: `callisto-manifests/cargo.rs` already strips BOM on `CargoToml::open` (per the findings ledger) and `python.rs` does the same.
- **Severity**: Medium (UX regression; the fix is one line — strip BOM before passing to `toml::from_str`, matching the pattern already established in manifests)
- **Verification Strategy**: Call `config::load()` on a `callisto.toml` whose contents begin with `\xEF\xBB\xBF`. Observe `ConfigError::ParseToml` with an opaque message. After stripping BOM, observe successful parse.

### [Medium] `is_workspace_root` uses text substring match for `[workspace]` — false positives from TOML comments and string values

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/locate/root.rs:28-31`
- **Classification**: Boundary Condition / Spec Drift
- **Root Cause**: `content.contains("[workspace]")` matches the literal substring anywhere in the file — including inside TOML comments (`# used to be a [workspace] root`), string values (`description = "replaces [workspace] root behavior"`), or multiline strings. A `Cargo.toml` that is a plain `[package]` manifest but contains such a comment would be incorrectly identified as the workspace root, causing `find_workspace_root` to return the wrong directory.
- **Failing Scenario**: A `crates/my-lib/Cargo.toml` containing `# This crate was split out from the [workspace] root Cargo.toml` would halt upward search at that crate's directory, returning it as the "workspace root" instead of the actual root.
- **Severity**: Medium (silent misdirection of all subsequent discovery; the correct fix is to parse the TOML and check for a `[workspace]` table key, not scan raw bytes)
- **Verification Strategy**: Create a `Cargo.toml` containing only a `[package]` section and a comment with `[workspace]`, call `is_workspace_root`, assert it returns `false`. Today it returns `true`.

### [Low] Dangling `callisto.toml` symlink treated as absent — silently uses all defaults

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/config/resolve.rs:162`
- **Classification**: Silent Fallback
- **Root Cause**: `callisto_toml.exists()` uses `fs::metadata()`, which follows symlinks. A dangling symlink (`callisto.toml -&gt; /missing/target`) returns `Err(NotFound)`, so `exists()` is `false`. The entire config is silently defaulted with no error, no diagnostic, and no indication to the user that a config file was expected but unreadable.
- **Failing Scenario**: `ln -s /nonexistent callisto.toml` at the workspace root — `callisto version` runs with all defaults, ignoring whatever config the broken symlink was meant to point to.
- **Severity**: Low (requires a misconfigured symlink, but the silent behavior is hard to debug — `file callisto.toml` shows "broken symbolic link" while Callisto behaves as if no config exists)
- **Verification Strategy**: Detect the broken symlink explicitly: `symlink_metadata()` returns `Ok` for a dangling symlink even when `metadata()` returns `Err`. Use `try_exists()` or check both metadata results to distinguish "does not exist" from "exists but is unreadable/dangling."

### [Low] `entries.flatten()` in `load_changesets` silently drops directory entry I/O errors

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/aggregate.rs:57`
- **Classification**: Silent Fallback
- **Root Cause**: `fs::read_dir` returns an iterator of `io::Result&lt;DirEntry&gt;`. `.flatten()` discards all `Err` variants — a directory entry that cannot be read (e.g., due to a permissions error on a subdirectory entry) is silently skipped. The changeset is never loaded and never causes a version bump, with no user-visible warning.
- **Failing Scenario**: A changeset file whose directory entry cannot be read (permissions issue, stale NFS mount) is silently treated as absent. The version plan omits the bump that changeset would have triggered.
- **Severity**: Low (requires an unusual I/O condition, but the consequence is a missed version bump, not just a degraded experience)
- **Verification Strategy**: Replace `.flatten()` with an explicit `for entry in entries { let entry = entry.map_err(...)? ; ... }` loop that propagates entry errors.

### [Low] `changesets.dir = "."` causes parse failures on every `.md` file in the workspace root

- **Status**: CONFIRMED
- **Location**: `crates/callisto-graph/src/aggregate.rs:46`, `crates/callisto-graph/src/config/resolve.rs:177-182`
- **Classification**: Boundary Condition
- **Root Cause**: `changesets_dir` is a relative `PathBuf` stored without validation. `load_changesets` computes `dir = root.join(&amp;cfg.changesets_dir)`. If `changesets_dir` is `.`, `dir` is the workspace root. `fs::read_dir` then enumerates all root-level files — every file named `*.md` except `README.md` is fed to `parse_changeset`, which will fail on `CHANGELOG.md`, `CONTRIBUTING.md`, etc.
- **Failing Scenario**: `callisto.toml` with `[changesets] dir = "."` — `callisto version` fails immediately with `GraphError::ParseChangeset` on the first non-changeset `.md` file in the workspace root.
- **Severity**: Low (accidental misconfiguration, clear error, but the error message blames the `.md` file rather than the config value)
- **Verification Strategy**: Add a validation step in `config::load()` that rejects `changesets_dir` values that are `.` or `..`, or that resolve to the workspace root.

- **Verification Strategy**: Assert that `IdentityIndex.bare` collision detection emits `GraphError::DuplicatePackage` or `AmbiguousName` instead of silently overwriting.
