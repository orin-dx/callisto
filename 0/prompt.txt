## P0 — root-discovery fallback has no repository boundary, silently binds to an unrelated ancestor manifest

`crates/callisto-graph/src/locate/root.rs:9-21`, `find_workspace_root`'s new `nearest(is_package_root)` fallback walks `canonical.ancestors()` with **no stopping bound** — not the git toplevel, not even the .git directory it's sitting in. It just returns the nearest ancestor holding a Cargo.toml `[package]`/package.json/pyproject.toml, however far up the filesystem that is.

Two confirmed repros (built binary, not just reasoning):

1. **Vendored/nested package picked instead of the real root.** Single-package cargo repo, run from inside `vendor/some-dep/` (its own `Cargo.toml [package]`, no `[workspace]` anywhere): `callisto status` reports only `some-dep 0.1.0`, ignoring the real `myapp` package entirely. `callisto --dry-run init --yes --versioning independent` run from that same directory detects only `some-dep`, and would write `vendor/some-dep/callisto.toml` — inside the vendored tree — on a real run. Before this diff, this case had no fallback and would correctly error `WorkspaceRootNotFound`; now it silently succeeds with the wrong root.

2. **Escapes the git repository boundary entirely.** Directory layout: `homelike2/package.json` (unrelated, e.g. simulating a stray `$HOME/package.json`) → `homelike2/proj/` (real git repo, `origin` set, no manifest anywhere inside it) → `homelike2/proj/docs/`. Running `callisto status` from `proj/docs/` climbs straight past the actual git root and binds to `homelike2/package.json`, reporting package `home-global-scripts 1.0.0` — a completely unrelated package outside the repository — with exit 0 and no warning (git's own "not a git repository" stderr leaks but doesn't block anything). `callisto init` in the same spot fails with E191 "not a Git repository" naming the *wrong* (outer) path, which is at least safe, but any read command (`status`, `release --dry-run`, etc.) silently succeeds against the wrong project.

This affects every command, not just `init` — `crates/callisto-cli/src/workspace.rs` routes both `load_workspace` and the new `workspace_root` (used by `init`) through the same `find_workspace_root`. It's a correctness bug for reads and a real filesystem-safety concern for `init` specifically, since a non-dry-run could scaffold `callisto.toml` into a directory the user never intended (a vendored dep, node_modules, or an unrelated ancestor).

Fix direction: bound the package-root fallback (and arguably the workspace-root search too) to the git repository's toplevel — e.g. resolve `git rev-parse --show-toplevel` first and never climb past it — and within that bound prefer the outermost matching manifest over the nearest, so a nested vendor/node_modules manifest can't shadow the real project root.
