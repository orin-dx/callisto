### 5. `callisto-graph/src/manifest_cache.rs`

**Gap 5a — The write path in `apply.rs` bypassing the cache is architecturally asserted only in a comment, not in a test.**
Files: `/Users/gabe/Projects/callisto/crates/callisto-graph/src/manifest_cache.rs` (lines 20–28), `/Users/gabe/Projects/callisto/crates/callisto-graph/src/apply.rs` (lines 72, 91)

`manifest_cache.rs` documents: "apply.rs intentionally keeps calling `callisto_manifests::open` directly for every write." `apply.rs` confirms this — it imports `open` directly. But no test verifies the invariant. After a write in `apply.rs`, `open_call_count()` should be higher than after read-only discovery. A test that: (1) resets the counter, (2) loads the workspace, (3) records the count, (4) applies a version plan, (5) asserts the count increased by exactly the number of manifests written — would pin this behavioral contract. Without it, a future refactor that accidentally routes writes through `open_cached` (reusing a stale in-memory copy) would not be caught until silent data corruption was observed in production.

**Gap 5b — The existing cache test (`base_versions_reuses_manifests_opened_during_graph_discovery`) is process-global and fragile.**
File: `/Users/gabe/Projects/callisto/crates/callisto-graph/tests/manifest_cache_test.rs` (line 83)

The comment on line 81 says: "This test must not run concurrently with other tests in this binary that also open real manifests." This is a real isolation hazard — `OPEN_CALL_COUNT` is a `static AtomicUsize`. There is no `#[serial]` or mutex guard; the test merely documents the assumption. Any future test added to that binary that opens manifests and runs concurrently will corrupt the counter silently. The test should either use a per-test counter mechanism or use `cargo-serial-test` to serialize access.
