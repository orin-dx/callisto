## CRITICAL

**1. §7.5/G.6.7 linked-group version convergence is entirely unimplemented.**
Spec (docs/01-spec.md:6795-6819, G.6.7) mandates: after a linked group's members are jointly named (≥2 severities assigned) and initial targets computed, but *before* the cascade fixpoint starts, all named members' target versions must converge to `max(targets, by Version::compare)` — erroring with `GraphError::GroupGrammarMismatch` on incomparable grammars. `crates/callisto-graph/src/aggregate.rs:211` (`union_linked`) only unions *severity* (correctly implements G.6.6), but the version-convergence step (G.6.7) is nowhere in the codebase — I grepped `winner`/`GroupGrammarMismatch`/version-convergence logic across cascade.rs, groups.rs, plan.rs, and traced the actual pipeline in `crates/callisto-graph/src/commands/version.rs:38-58` (`aggregate()` → `run_cascade()` directly, nothing between). `GroupGrammarMismatch` (error.rs:73) is only ever raised for *fixed* groups (groups.rs:65), never linked.
**Failing scenario:** two linked packages `1.4.0` and `2.7.3`, both named `minor` in one changeset. Per spec they must land on the same version (`2.8.0` per the worked example at line 6798). Actual code independently bumps each: `1.5.0` and `2.8.0` — divergent, violating linked-group semantics entirely.

## HIGH

**2. Stale dependency-spec rewrite on re-cascade — `crates/callisto-graph/src/cascade.rs:239`.**
`out.rewrites.entry(key.clone()).or_insert(SpecRewrite{...})` — first-write-wins. The cascade worklist is a `BTreeSet<PackageId>` popped in lexicographic order (toposort.rs/cascade.rs:173), *not* topological order. If package `pkg`'s own severity/target is escalated a second time (via `raise()`, cascade.rs:300-357, triggered by some other package processed *after* `pkg`'s first pass — plausible whenever the alphabetically-later package is `pkg`'s dependency), `pkg` is re-inserted into the worklist and reprocessed with its new, higher target version. On the second pass it recomputes rewrites for the same dependent edges, but the `RewriteKey` (manifest+name+kind, no version) is identical to the first pass, so `.or_insert` silently keeps the *stale, lower* version and discards the correct final one.
**Failing scenario:** package A depends on B; B also depends on C. C is processed first (raises B's severity), then B is processed and generates a rewrite of A's dependency spec on B using B's *current* (still low) target; then B gets re-escalated via C and re-processed with a higher target — A's manifest ends up pointing at B's stale, pre-escalation version instead of B's final released version. This is a real byte-output-correctness bug (wrong version written into a manifest), should be `.insert()` (or an explicit max-by-version merge) not `.or_insert()`.
