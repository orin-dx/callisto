| Technique | What it speeds up | Relevance to Callisto |
| --- | --- | --- |
| **Git commit-graph** stores parents, generation numbers, and root tree IDs without inflating each commit. | Ancestry and history walks. | Useful for finding commits reachable from `HEAD` or a tag. Check that the gix spike actually uses its commit-graph path. It does not remove the measured tree inflation cost. [Git documentation](https://git-scm.com/docs/commit-graph). |
| **Changed-path Bloom filters** can rule out a change to a *specified path* without reading trees. They describe changes against the first parent. | `log -- path` and similar queries. | A worthwhile gix feature for path-specific history; Gitoxide [lists it as performance work](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md). [GitHub’s explanation](https://github.blog/open-source/git/gits-database-internals-iii-file-history-queries/). |
| **Reachability bitmaps and generation pruning** avoid repeatedly traversing large portions of the commit graph. | Set and ancestry queries. | Promising for the `HEAD` versus tag commit set, particularly with many tags. Benchmark separately from path extraction: improving this step will not cure the 4,000-entry tree regression. [GitHub’s explanation](https://github.blog/open-source/git/gits-database-internals-iv-distributed-synchronization/). |
| **Pack base caching** keeps decompressed delta bases available. Git’s default budget is 96 MiB per thread. | Repeated reads from delta chains. | This is the closest match to the profile showing inflate and copy time. Compare cache *hits, misses, bytes inflated, and peak memory* across Git and gix on the identical pack. [Git configuration](https://git-scm.com/docs/git-config). |

**Anthropic’s most transferable idea is an exact changed-path index.** Scion records the paths changed by each changeset, then builds separate path-history and ancestry indexes as derived data; it computes those indexes eagerly or lazily according to demand. Its clients also request only the trees and blobs they need and share content-addressed caches across jobs. [Anthropic’s design](https://www.anthropic.com/research/redesigning-source-control).

A Git-compatible gix cannot put a path list into existing commit objects, but an **optional, incrementally maintained index of commit → changed paths** could give repeated Callisto-style queries that benefit. It would need a measured build cost, bounded storage, invalidation rules, and explicit handling for every merge parent. On a fresh clone queried once, building the index may cost more than the walk it saves. That is a research proposal, not a demonstrated speedup.

Meta offers a related lesson: Sapling’s segmented changelog answers graph questions from a compact graph representation, while dedicated file-history structures serve repeated path queries. Its virtual working copy and server support address clone and checkout costs at monorepo scale; those are valuable ideas for gix’s broader roadmap, but they do not explain Callisto’s local tree-diff profile. [Meta’s account](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/). Microsoft’s Scalar shows the operational side: maintain commit-graphs and multi-pack indexes incrementally in the background so reads benefit without paying the full indexing cost on each command. [Scalar’s design](https://devblogs.microsoft.com/devops/introducing-scalar/).

I would pursue gix contributions in this order:

1. **Reproduce and instrument the wide-tree regression in `gix-pack`.** Use the same repacked fixture for Git and gix. Record delta depth, cache hit rate, inflate count, bytes copied, time, and peak memory at several cache budgets. This directly tests the current bottleneck.
2. **Make the all-paths walk use existing graph information efficiently.** Verify commit-graph use, avoid commit inflation where its root tree ID suffices, and skip identical trees before decoding them. Measure whether either matters on real repositories.
3. **Prototype an exact changed-path index for repeated queries.** Compare first-run cost, subsequent-run time, index size, and update cost. Include merge and hotfix histories as correctness fixtures.
4. **Add Bloom-backed path queries as a separate upstream capability.** That would help many gix consumers, even if it does little for Callisto’s current all-paths operation.

Anthropic’s reported gains came from changing the source-control architecture for an enormous, online-first workload. The contribution to gix is the **query and measurement discipline**—choose an index for a specific question, account for its maintenance cost, and verify the whole workload—rather than copying Scion’s server architecture into a local Git library.

fn try_lookup<'graph, 'cache>(
    id: &gix_hash::oid,
    objects: &dyn gix_object::Find,
    cache: Option<&'cache gix_commitgraph::Graph>,
    buf: &'graph mut Vec<u8>,
) -> Result<Option<LazyCommit<'graph, 'cache>>> {
    if let Some(cache) = cache
        && let Some(pos) = cache.lookup(id)
    {
        return Ok(Some(LazyCommit {
            object_hash: id.kind(),
            backing: Either::Right((cache, pos)),
        }));
    }
    Ok(match objects.try_find(id, buf)? {
        Some(data) => data.kind.is_commit().then_some(LazyCommit {
            object_hash: data.object_hash,
            backing: Either::Left(buf),
        }),
        None => None,
    })
}

/// Information about a commit that we obtained naturally as part of the iteration.
#[derive(Debug, Clone)]
pub struct Info<'repo> {
    /// The detached id of the commit.
    pub id: gix_hash::ObjectId,
    /// All parent ids we have encountered. Note that these will be at most one if [`Parents::First`][gix_traverse::commit::Parents::First] is enabled.
    pub parent_ids: gix_traverse::commit::ParentIds,
    /// The generation number if this commit was read from a commit-graph.
    pub generation: Option<gix_revwalk::graph::Generation>,
    /// The time at which the commit was created. It will only be `Some(_)` if the chosen traversal was
    /// taking dates into consideration.
    pub commit_time: Option<gix_date::SecondsSinceUnixEpoch>,

    repo: &'repo Repository,
}

/// Access
impl<'repo> Info<'repo> {
    /// Provide an attached version of our [`id`][Info::id] field.
    pub fn id(&self) -> crate::Id<'repo> {
        self.id.attach(self.repo)
    }

    /// Read the whole object from the object database.
    ///
    /// Note that this is an expensive operation which shouldn't be performed unless one needs more than parent ids
    /// and commit time.
    pub fn object(&self) -> Result<crate::Commit<'repo>> {
        Ok(self.id().object()?.into_commit())
    }

    /// Provide an iterator yielding attached versions of our [`parent_ids`][Info::parent_ids] field.
    pub fn parent_ids(&self) -> impl Iterator<Item = crate::Id<'repo>> + '_ {
        self.parent_ids.iter().map(|id| id.attach(self.repo))
    }

    /// Returns the commit-time of this commit.
    ///
    /// ### Panics
    ///
    /// If the iteration wasn't ordered by date.
    pub fn commit_time(&self) -> gix_date::SecondsSinceUnixEpoch {
        self.commit_time.expect("traversal involving date caused it to be set")
    }
}

        }
    }

## 1. Investigate repeated pack delta work first

Git’s `unpack_entry()` caches intermediate base objects as it applies a delta chain. In the [published gix-pack decoder](https://docs.rs/gix-pack/latest/src/gix_pack/data/file/decode/entry.rs.html), the visible `cache.put()` stores the requested result after the chain is complete. That difference could cause repeated inflation when successive historical trees depend on overlapping chains. It fits Claude’s profile, but the fixture’s actual base relationships have not been checked. [Git’s decoder](https://github.com/git/git/blob/master/packfile.c), [cached gix 0.90 decoder](/Users/gabe/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gix-pack-0.77.0/src/data/file/decode/entry.rs:492).

There is a second measurement trap. In gix 0.90, the default pack cache has **64 entries**. Configuring `core.deltaBaseCacheLimit` selects a different, memory-capped hash-map implementation; `gitoxide.core.deltaBaseCacheLimit` limits the fixed cache instead. Thus a 1 GB result may reflect a change in cache policy as well as capacity, depending on how Claude configured it. The fixed cache can also clear all entries when its memory limit is exceeded. [Cache selection](/Users/gabe/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gix-0.90.0/src/repository/init.rs:72), [fixed cache](/Users/gabe/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gix-pack-0.77.0/src/cache/lru.rs:105).

**First experiment:** on the *same pack and access order*, compare no pack cache, fixed 64-entry cache, and dynamic caches at equal 96 MiB, 256 MiB, and 1 GiB budgets. Record cache hits, deltas actually resolved per requested tree, bytes inflated, elapsed time, and peak resident memory. `git verify-pack -v` supplies object bases and delta depths. [Output format](https://git-scm.com/docs/git-verify-pack). Run it on both flat and directory-sharded fixtures.

If overlapping chains are repeatedly decoded, a gix PR could cache selected intermediate results. It needs care: gix’s current cache API copies from a byte slice, so caching *every* intermediate 150 KB tree could trade inflation for substantial copying and memory use. Git’s implementation transfers ownership of a materialized base into its cache. A benchmark should guide admission policy or an ownership-aware API before changing the decoder. The gix decoder also identifies avoidable buffer copies in its own comments; those are a separate experiment. [gix decode path](https://docs.rs/gix-pack/latest/src/gix_pack/data/file/decode/entry.rs.html).

**Confidence:** high that the implementations differ; moderate that this explains the 4,000-package gap; unverified until the fixture’s chains and cache misses are measured.

## 2. Expose tree IDs during a revision walk

A Git commit-graph entry contains the root tree ID, and `gix-commitgraph` exposes it. Yet gix 0.90’s high-level revision-walk `Info` exposes the commit ID, parents, generation, and date; obtaining its tree currently calls `Info::object()`, which reads the commit object. [Commit-graph entry](/Users/gabe/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gix-commitgraph-0.42.0/src/file/commit.rs:93), [walk information](/Users/gabe/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gix-0.90.0/src/revision/walk.rs:71). Gitoxide’s [roadmap calls out getting trees from the commit-graph into traversal information](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md).

A useful small contribution would expose an optional root tree ID during traversal, with an object-read fallback for commits absent from the graph. It would let an all-paths walker skip identical parent/child trees and avoid separate commit reads. The high-level walk already uses commit-graph data when available; the gap is making its tree ID available to the caller. The profile suggests this will be a smaller win than pack decoding, so I would measure commit-object reads before assigning it higher priority.

## 3. Treat Bloom filters as a separate contribution

Git’s changed-path Bloom filter answers “**definitely unchanged** or **possibly changed** for this path against the first parent.” It cannot return the changed path list. Git stores these filters in optional commit-graph chunks; commits with more than 512 changed paths get an all-ones filter. [Git’s format](https://git-scm.com/docs/gitformat-commit-graph), [GitHub’s explanation](https://github.blog/open-source/git/gits-database-internals-iii-file-history-queries/).

The cached `gix-commitgraph` source has no Bloom reader, and Gitoxide lists Bloom data and path-aware traversal as future work. A well-scoped contribution sequence would be:

1. Read and validate Git’s Bloom index and data chunks, including versions 1 and 2, split commit-graphs, empty filters, and all-ones filters.
2. Expose a result such as `DefinitelyUnchanged | MaybeChanged | Unavailable`; “maybe” must still trigger a tree comparison.
3. Integrate it into path-limited history with merge tests.

That would benefit gix broadly. It would not materially accelerate Callisto’s measured **all-changed-paths** walk. First-parent-only data also cannot supply Callisto’s full merge result by itself.

## 4. Prototype Anthropic’s indexing idea at the application boundary

Scion records changed files in each changeset and maintains derived path-history and ancestry indexes. Meta’s Sapling likewise uses compact graph data and dedicated file-history structures. Their common lesson is to pay an indexing cost once when many later queries reuse the answer. [Anthropic](https://www.anthropic.com/research/redesigning-source-control), [Meta](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/).

For Callisto, the testable version is a disposable exact index keyed by commit and parent, containing changed paths under fixed diff rules. Existing commit IDs remain stable across repacks, but replace refs, shallow boundaries, merge-parent semantics, and index cleanup need explicit handling. Measure **first query, repeat query, update cost, disk size, and correctness**. I would prototype this in an application benchmark before proposing a persistent index in gix: Claude’s one-pass history redesign may already have removed most repeated work.
