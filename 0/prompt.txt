The key defect in #29 is in `filter_plan_by_report`: package publish lists are retained only when a successful attempt exists, but `releases` are retained whenever no failed attempt matches. “Not attempted” therefore incorrectly counts as release-safe. The semantic rule must be:

> A release entry is eligible for tagging only if every planned publish operation for that release has a matching successful or already-published attempt, at the planned version.

No attempt, mismatched version, duplicate contradictory attempts, or failed attempt must all make it ineligible.

Architecturally, this should not remain a set of parallel vectors plus shell/jq interpretation. `PublishPlan` currently has crate/npm/PyPI vectors and a separate `releases` vector; the relationship is inferred from package names. That is why the filter bug exists.

I recommend introducing a model-owned release unit:

```text
ReleaseUnit
  id
  package identity
  source SHA
  version
  required publish operations [operation IDs]
  tag operation
  changelog/release metadata
```

`PublishReport` should report outcomes by `operation_id`, not reconstruct identity from bare package names. Then `callisto-graph` owns one deterministic projection:

```text
PublishPlan + PublishReport -> ReconciledReleasePlan
```

The GitHub Action should only execute that projection and perform adapter-side actions. It should not decide what shipped with jq.

Immediate release behavior should be:

- A tag failure is fatal; do not create a GitHub Release afterward.
- A tag push failure is fatal; do not create a GitHub Release afterward.
- `gh release create` failure is fatal unless an explicit idempotent “already exists and targets expected tag” result is verified.
- A successful package publish with an incomplete release unit is recorded for reconciliation, not silently treated as a completed release.
- Release output must distinguish `planned`, `published`, `tagged-local`, `tagged-remote`, `release-created`, `failed`, and `reconcile-required`.
