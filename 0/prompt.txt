[153] assistant: Yes. The important design is to separate two dimensions that are currently being mixed:

1. Is this document authoritative?
2. Has its implementation been completed and proven?

W3C and IETF both distinguish document maturity from implementation evidence. W3C’s useful pattern is: working draft → candidate recommendation (stable enough to gather implementation experience) → recommendation. Its current process explicitly treats the candidate stage as technically complete enough for implementation validation, not merely “some code was written.” [W3C Process](https://www.w3.org/policies/process/) The IETF similarly treats drafts as evolving review artifacts and requires demonstrated implementation/operational experience for mature standards. [RFC 2026](https://datatracker.ietf.org/doc/html/rfc2026.html)

For Callisto, I’d use this simpler model:

| Specification status | Meaning | May authorize production implementation? |
|---|---|---:|
| `draft` | Active design; details can change freely. | No |
| `in_review` | Proposed for formal architectural/process review. | No |
| `accepted` | Approved, normative source of truth. Changes require a spec revision. | Yes |
| `superseded` | Replaced by a named newer specification. | No |
| `withdrawn` | Deliberately abandoned; retained for history. | No |

Then add a separate implementation field:

| Implementation status | Meaning |
|---|---|
| `not_started` | No implementation has begun. |
| `in_progress` | Work is underway against the accepted spec. |
| `implemented` | Required code/docs/workflows are present. |
| `verified` | Traceability, tests, CI, and acceptance criteria have been independently checked. |

This avoids the misleading linear lifecycle `draft → accepted → implemented`, because acceptance and implementation are different facts. A spec can be accepted but not implemented; code can exist while a spec remains draft, but that should be flagged as a process exception—not silently treated as acceptance.

For 007–013 specifically, I would:

- Keep them `draft` until the formal review actually occurs.
- Perform a traceability review from each acceptance criterion to code/tests/workflows.
- Record any deviations or clarifications in the spec itself.
- Change them to `accepted` once that review approves their normative wording.
- Set implementation to `verified` only after the independent validation Claude described.

I would avoid importing W3C’s full “candidate recommendation” state unless you genuinely want to permit implementation before acceptance to gather evidence. Your stated process is clearer and safer: accepted specs authorize implementation; implementation evidence validates the accepted spec afterward.
