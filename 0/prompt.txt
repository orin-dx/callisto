  > "pip cannot prove a PyPI version absent: an unreachable index and a project that does not exist produce the same message and the same exit code, `pip index versions` is experimental and hides yanked releases, and a pinned yanked release installs with only a warning. ## 5. Where a shelling-out ecosystem-capability trait would live

Confirmed via `crates/callisto-model/Cargo.toml` (license=MIT, no process/exec deps) and `crates/callisto-manifests/Cargo.toml` (license=**FSL-1.1-MIT**, so it's an FSL *product* crate, not one of the three MIT foundation crates — despite living conceptually "close to manifests"). Grep confirms `callisto-manifests` shells out to nothing (`grep -rn "Command::new|std::process|CommandRunner"` = empty).

Pattern already established, twice:
- `CommandRunner` trait itself (`crates/callisto-model/src/exec.rs:11`) is defined in the MIT-foundation `callisto-model` crate but is a **pure interface** (no actual subprocess code there) — real spawn/poll/kill implementations (`CliCommandRunner` etc.) live in FSL crates (`callisto-cli`, `callisto-graph`, `callisto-vcs`, `callisto-moon`) per `grep -rln "struct CliCommandRunner|impl CommandRunner for"`.
- `callisto-vcs` (an MIT foundation crate, ARCHITECTURE.md:264-296) itself shells out to `git` via its `ShellGit` backend using `CommandRunner` — so **shelling out is not itself restricted to FSL crates**; the CLAUDE.md rule is specifically "MIT foundation crates must never depend on FSL *product* crates," not "must do no I/O."
- **Closest direct precedent for an ecosystem-capability resolver that shells out**: `RegistryEcosystem` trait, `crates/callisto-graph/src/commands/release/provider/registry.rs:172-192` (trait) with adapters `CargoRegistry`/`NpmRegistry`/`PypiRegistry` (registry.rs:423 for Pypi) each shelling out through `context.runner()` (a `CommandRunner`) to do per-ecosystem capability queries (`can_observe_versions`, `observe_once`, `publish`, `classify`). This is a **product-crate** (`callisto-graph`, FSL) trait, sitting in `commands/release/provider/`, one adapter per `Ecosystem`, selected via `adapter_for(ecosystem: Ecosystem)` (registry.rs:203).

**Recommendation**: a new capability resolver that runs e.g. `rustc --print cfg` belongs in `callisto-graph` (FSL product crate), most naturally as a sibling trait to `RegistryEcosystem` under `commands/release/provider/` (or a new adjacent module if it's not release-specific) — same shape: one trait, per-`Ecosystem` adapters, shelling out via the existing `CommandRunner` (from `callisto-model`) rather than raw `std::process::Command`. Do NOT put it in `callisto-manifests` (FSL but currently I/O-free by convention/precedent — every existing manifest editor is pure CST manipulation, no subprocess) or in `callisto-model`/`callisto-vcs` (MIT foundation; only acceptable there if the trait is a pure interface with zero product-crate knowledge, mirroring `CommandRunner` itself).
