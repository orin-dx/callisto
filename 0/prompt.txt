What we keep from the implementation already landed:

- Exact ecosystem-qualified release identities.
- Canonical intent/digest and strict serialization.
- Clean detached-commit trust.
- Prepared private capability plus release lock.
- Exact registry, Git remote, tag annotation, and forge identity checks.
- Crash-safe operation state and terminal-success semantics.
- Artifact manifest model, streaming digest, and attestation policy.
- Legacy CLI commands restricted to previews.
- Atomic writes and the tests added around these boundaries.

What goes away or changes:

- No checked-in standalone `ReleaseDecisionV1` file.
- No normal CI invocation where someone supplies an arbitrary `--package` roster after merge.
- No requirement that a decision survive independently of the release PR.
- We should eventually remove the public “manual selection” route from the primary workflow, though it can remain for an explicitly manual/local release mode if useful.
- The existing `ReleaseDecisionV1` type does not need immediate deletion. Keeping it as the graph’s internal deterministic result is useful and avoids churning working safeguards; it simply stops being an operator-facing durable artifact.

The key new implementation is a release-PR-delta reader. On the merged release commit it compares the release commit with its parent, verifies:

- only the intended changesets were deleted;
- version/changelog/manifest changes match those changesets and release policy;
- no unexpected package is added to the roster;
- the current checkout is exactly that merged commit.

Then it builds the intent. That is simpler for users, while still preventing the dangerous case where a later retry silently releases a different workspace state.

[312] user: Why is ReleaseDecisionV1 versioned? Should we adjust it to better suit its new role?

[313] assistant: It is versioned because it currently crosses a persistence boundary: it is serialized inside `ReleaseIntentV1`, whose plan artifact may be created in one CI job and executed or resumed later. Any serialized contract needs a schema version.

But its role should change.

Today it implies: “an operator-selected release roster is separately approved and carried forward.”

The better role is: “a deterministic explanation of the merged release commit.”

I’d adjust it to something like `ReleaseCommitDecisionV1`:

- `source_commit`: the merged release PR commit.
- `base_commit`: its release baseline/parent.
- `entries`: exact package/version roster.
- `consumed_changesets`: exact deleted changeset paths and content digests from the base side of the diff.
- `reasons`: existing typed explanations, now derived from that immutable release delta.
- `digest`: retained, as a concise integrity/audit identifier.

Then:

- It is generated internally from the merged release-PR delta.
- It is embedded in the intent for auditability.
- It is not written as a separately managed repository file.
- It is not supplied by users or CI inputs.
- Its version remains useful because it is still durable wire data inside the intent.

An alternative is making it entirely transient and storing only operations in the intent. I would not choose that: we would lose the compact explanation of why each package/version is there, making recovery and audits harder for little practical simplification.

So: keep the versioning and typed structure; change the provenance and remove its operator-facing persistence.
