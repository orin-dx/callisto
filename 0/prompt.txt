[83] user: Why do we need the complexity of this durable decision? Is that something that release please does? nx release?? changeset or knope?

[84] assistant: Not necessarily. We should not copy a stronger architecture than the problem needs.

Most release tools use a simpler invariant:

- Changesets keeps one up-to-date version PR; after merge, it runs publish based on the freshly versioned commit and assumes nothing intervened. [Changesets automation](https://github.com/changesets/changesets/blob/main/docs/automating-changesets.md)
- Release Please stores release state in its manifest and creates releases from the last merged release PR. [Release Please manifest flow](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md?plain=1)
- Nx separates versioning/changelog/publishing, but does not provide this kind of durable intent/receipt protocol. [Nx Release](https://nx.dev/docs/features/manage-releases)
- Knope is similarly oriented around release PRs and conventional release automation, not a cryptographically bound execution plan.

Your clarified workflow means we can use the standard release-PR model:

1. On `main`, independently recompute pending changesets and create/update one release PR.
2. That PR contains version/changelog updates and deletes the consumed changesets.
3. On merge, release from that exact merged release PR commit.
4. New changesets remain on `main`; the next run regenerates the still-open release PR to include them.

The extra durable-decision file is only needed if we require an executor to prove the exact roster/reasons independently after merge, even across retries and CI job boundaries. It is not required merely to achieve correct Changesets-style release PR behavior.

My recommendation: preserve the durable intent/state/receipt and artifact-attestation protections, but simplify the decision handoff. Bind the intent to the merged release-PR commit and derive the release set from that immutable version-PR change, rather than committing a separate decision file. That is closer to Changesets/Release Please DX while keeping the protections that matter for publishing credentials, tags, artifacts, and retries.

[85] user: What benefit is it providing or are we just satifying an engineering interest here?

[86] assistant: Mostly safety and recovery—not an engineering trophy.

A durable decision/intent helps when publishing is no longer one short command:

- It proves exactly what CI was authorized to release before registry credentials are used.
- It prevents a retry from silently publishing a different set after config, dependencies, or package selection changed.
- It gives interrupted releases a precise state record: “this crate published; this tag exists; this asset was not uploaded.”
- It makes plan/build/execute job separation safe: the build cannot substitute a different package/version or artifact.
- It creates a useful audit trail for an incident or compromised CI run.

But for your normal release-PR flow, a separate checked-in decision file has limited practical value. The merged release PR already supplies a strong, reviewable boundary: it contains the exact version changes and consumed changesets.

My recommendation is to keep the durable machinery only where it earns its keep:

- Keep: immutable merged-commit binding, exact tag/remote checks, crash-safe execution state, registry postconditions, artifact digests and attestations, environment-gated credentials.
- Simplify: derive the release roster from the merged release PR rather than requiring a separate durable decision file.
- Avoid: another permanent “plan” file purely to satisfy internal architecture.

That gives us a safer version of the familiar Changesets workflow without making everyday releases feel bureaucratic.

    workspace: &Workspace<'_, R, D>,

    Ok(source_from_trust(&observe_git_trust(workspace, trust_profile)?))

fn observe_git_trust<R: CommandRunner, D: DependencyResolver>(
    workspace: &Workspace<'_, R, D>,
    trust_profile: ExecutionTrustProfileV1,
) -> Result<GitCommitTrustEvidence, GraphError> {
    if !matches!(trust_profile, ExecutionTrustProfileV1::GitCommit) {
        return Err(GraphError::ReleaseIntentStale);
    }
    let evidence = workspace.git_access().observe_git_commit_trust()?;
    if evidence.canonical_root() != workspace.root || evidence.head_disposition() != GitHeadDisposition::Detached {
        return Err(GraphError::ReleaseIntentStale);
    }
    Ok(evidence)
}

fn source_from_trust(evidence: &GitCommitTrustEvidence) -> SourceIdentity {
    SourceIdentity::GitCommit {
        sha: evidence.head().clone(),
    }
