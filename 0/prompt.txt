## What I would correct in our scope

### 1. One authoritative version does not mean one universal version grammar

Maturin can derive the Python distribution’s version from Cargo and convert SemVer to PEP 440. A normal configuration uses `dynamic = ["version"]`; Callisto should not manufacture a second static version field. [Maturin metadata rules](https://www.maturin.rs/metadata)

I tested co-located `Cargo.toml` and `pyproject.toml` with:

- Matching static `1.0.0` versions.
- A Cargo version and a dynamic Python version.

**Both `init` and `status` fail with E007.** The current model rejects mixed canonical-manifest grammars outright. [Current check](/Users/gabe/Projects/callisto/crates/callisto-model/src/package.rs:44)

That means our earlier Rust/Python coverage was incomplete: separate-directory fixtures do not establish support for this common layout.

Recommendation: support the concrete Cargo-owned Maturin case, preserving native version representations and checking built metadata. Do not attempt arbitrary bidirectional conversion between every SemVer and PEP 440 version.

### 2. PyPI completion is an artifact-set question

PyPI creates a release when its **first file** uploads. Further wheels and the sdist are additional uploads under that version. [Upload API](https://docs.pypi.org/api/upload/)

Callisto builds a wheel and sdist, but currently accepts any matching non-yanked file as evidence that the publication is complete. The release preflight then treats that evidence as already satisfied. [Observation](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/release/provider/registry.rs:499), [preflight](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/release/provider/mod.rs:325)

Consequently, a partial upload can be skipped on retry. This is source-confirmed; I have not run a live partial-upload experiment.

**This is more important than optional checksum hardening.** We need to know which files this release intended to publish, then confirm that set—not every conceivable wheel platform. PyPI’s index exposes individual filenames, hashes and yank status. [Simple API](https://packaging.python.org/en/latest/specifications/simple-repository-api/)

### 3. Native dependency syntax must survive normalization

Callisto currently collapses recognized `workspace:` specifications into one generic workspace reference. [Parser](/Users/gabe/Projects/callisto/crates/callisto-manifests/src/npm.rs:517)

But pnpm distinguishes:

- `workspace:*` from an explicit constraint such as `workspace:^1.5.0`.
- A dependency’s alias from its actual package name.
- Relative workspace paths.
- Catalog references whose authoritative value lives elsewhere.

An explicit workspace constraint can fail resolution. pnpm also transforms workspace and catalog references during packing/publication. [Workspace semantics](https://pnpm.io/workspaces), [catalog publishing](https://pnpm.io/catalogs)

Recommendation: retain the resolved distribution, original reference and effective constraint. Let pnpm perform its packing transformations. Where Callisto cannot safely update a reference, disclose that limitation rather than silently treating it as unconstrained.

Canonical IDs still need ecosystem-specific normalization: Python, for example, treats several punctuation/case spellings as the same project. [Python normalization](https://packaging.python.org/en/latest/specifications/name-normalization/)

### 4. Publication ordering needs explicit ownership

I would retain registry-before-public-announcement as Callisto’s default for today’s ecosystems, but retract any suggestion that it is universally required. Nx’s combined release implementation can create tags and remote releases before publishing. [Nx implementation](https://github.com/nrwl/nx/blob/master/packages/nx/src/command-line/release/release.ts)

A second complication matters now: NAPI’s `prepublishOnly` integration can itself publish platform packages and create/upload GitHub releases. Callisto and those hooks must not independently own the same effects. [NAPI publication behavior](https://napi.rs/docs/cli/pre-publish)

The rule should be:

> Each irreversible effect has one owner. Release completion means all required effects are confirmed—not that a tag exists.

There is no cross-registry transaction to roll back. Recovery should finish missing effects using the original intent and artifacts.

### 5. Future ecosystems need escape room, not implementation now

Two concrete architectural checks are enough to expose major future assumptions:

- **Go:** publishing uses repository tags, and v2+ normally changes the module path. A tag cannot always be placed behind every publication as a completion marker. [Go versioning](https://go.dev/doc/modules/version-numbers)
- **NuGet:** version normalization differs from ordinary SemVer, including removal of build metadata. One package can contain assets selected by runtime identifier and target framework—not just a Rust target triple. [Version rules](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning), [native assets](https://learn.microsoft.com/en-us/nuget/create-packages/native-files-in-net-packages)

Also, registry identity must not imply one endpoint serves every operation. Callisto currently reuses the configured Python endpoint for observation and upload; those are distinct APIs on public PyPI. Private-registry support needs an explicit boundary here. [Index API](https://docs.pypi.org/api/index-api/), [upload API](https://docs.pypi.org/api/upload/)

## The smallest architecture I recommend

Keep four concepts:

1. **Release owner:** what versions/releases together.
2. **Distribution:** canonical ecosystem-qualified identity and native package name.
3. **Version authority:** where the version comes from, with each distribution’s native representation.
4. **Release effects:** required publications/assets/tags/announcements and their prerequisites.

Reuse the existing dependency graph and operation DAG. **Do not introduce five public graph types or a general plugin framework.**

Distinguish these meanings without making them elaborate configuration systems:

- A native package dependency affects native constraints.
- An embedded/build input affects the produced artifact; it does not automatically require publishing that input to its registry.
- Shared versioning is an explicit release policy, not an inferred consequence of either relationship.

Canonical distribution IDs should be used consistently in new machine contracts and authored references. Preserve old references through a deliberate migration path; adding another ecosystem must not silently change historical ownership.

Build tools and CI remain responsible for compiling and packaging. Services, arbitrary interoperability discovery, universal dependency resolution and Go/NuGet publishers stay outside this scope.

## Checks still needed before calling it complete

I would validate a bounded set of representative fixtures:

- Cargo workspace inheritance, renamed dependencies and registry visibility delays.
- npm/pnpm aliases, explicit workspace ranges, catalogs and actual packed metadata.
- Python markers/extras, prereleases, wheel/sdist selection and failure after the first upload.
- NAPI platform packages, lifecycle ownership and clean consumer installation.
- Co-located Maturin projects, Cargo-owned versions and built Python metadata.
- Failure/retry at publication, tag, push, GitHub release and asset-upload boundaries.

Use Go v2 and a multi-runtime NuGet package as **design examples**, not implemented adapters or new release gates.

My recommendation is to proceed with the scoped architecture, amended for **version authority, required artifact sets and single-owner effects**. Those address real problems in today’s systems. Everything more general should wait for a concrete supported use case.
