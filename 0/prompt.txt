The underlying architectural issue is that workspace ownership is inferred independently by membership, lockfile refresh, npm publishing, and registry observation. Lockfile presence is useful for choosing a tool, but it is not a reliable definition of workspace membership. Resolve an npm package’s owning workspace once from its workspace declaration, then use that result for command directory, tool selection, observation, and publication. Pin or explicitly validate the registry endpoint so both effects use the same destination. Add cross-layer tests with a lockfile-free nested npm workspace and a nested .npmrc; the current tests cover the pieces separately.

My release-notes choice: generate notes when no changelog is configured; fail release planning when a configured changelog is missing, unreadable, or has no nonempty section for the version. A configured changelog is an authored release input, so silently replacing it changes the announcement. That policy would require updating the current release specification (.claude/worktrees/leftovers2/docs/specs/release.json:284), which explicitly requires the fallback today.

The root Cargo workspace continuing to govern native/ through its members and exclude rules is coherent with the stated contract. I found no reason to change that policy in this stack.
