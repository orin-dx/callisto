<result>## Audit Verdict: `platform_writes`/`optional_dep_updates` dispatch loops in `apply_version_plan` (commit `2d53001`)

### Context that changes the risk calculus

Before the specific findings: `plan.platform_writes` and `plan.optional_dep_updates` are **never populated with real data anywhere in the codebase today**. The only real producer of a `VersionPlan`, `plan_version` in `crates/callisto-graph/src/commands/version.rs:246-258`, hardcodes:
```rust
platform_writes: Vec::new(),
optional_dep_updates: Vec::new(),
```
Same for `commands/snapshot.rs:132-133` and `commands/pr_body.rs:282-283/303-304`. The only place these fields are ever populated with non-empty data is the one new test added in `2d53001` (`apply.rs:2240`). So **this is currently dead code in production** — the loops added in `2d53001` cannot execute with real content via any CLI command today. This matters: it means nothing below is exploitable *yet*, but it's exactly the kind of gap that becomes live the moment someone wires a producer (e.g. a future "platform package" cascade step) into `platform_writes`/`optional_dep_updates` without re-auditing `apply_version_plan`.

### 1. Data-loss/clobber risk from the two independent open→persist cycles

**Not real, given today's structure — verified by tracing `open()`.** `crates/callisto-manifests/src/lib.rs:155-181` (`open()`) does no caching: every call does `CargoToml::open`/`PackageJson::open`/`PyprojectToml::open`, each of which reads the file fresh from disk (confirmed no in-memory cache, no shared mutable state across calls — only a test-observability `AtomicUsize` counter). `apply_version_plan` is fully synchronous, single-threaded, with no deferred/lazy writes — `classify_manifest_writes`'s batched loop (`apply.rs:140-179`), the excluded-bump loop (`181-215`), the excluded-rewrite loop (`217-242`), then `platform_writes` (`244-252`), then `optional_dep_updates` (`254-262`) run strictly in that order, each `persist()` (`callisto-manifests` `atomic_write`) completing before the next loop's `open()` runs. So if the same manifest path appeared in both a batched write and `platform_writes`, the second `open()` would read the first loop's already-persisted bytes — no clobber. The `classify_manifest_writes` invariant (open-once-per-batch) exists to prevent multiple writes *within a single classify group* interleaving on one handle; it says nothing about, and is not violated by, two temporally-sequential open/persist cycles on the same file, because re-opening always re-reads truth from disk.

### 2. Unsafe interleaving relative to batched writes

None found. There is no threading, no async, no reordering of `plan.platform_writes` vs `plan.bumps` — the four loops execute in fixed source order every time. This part of the original architectural worry is not present in the current code.

### 3. Partial-failure behavior

Consistent with (not worse than) the rest of `apply_version_plan` — none of the loops in this function have transactional/rollback semantics; every one (`classify_manifest_writes`'s batched loop, the excluded-bump loop, the excluded-rewrite loop, and now `platform_writes`/`optional_dep_updates`) propagates the first error via `?` and returns early, leaving whatever was already `persist()`ed on disk and skipping git staging entirely (the staging code at `apply.rs:433-470` never runs on early return). This is the established, accepted design in this file (see the `apply_is_idempotent_when_manifest_already_at_target_version` test at `apply.rs:934` — recovery is via re-running `apply_version_plan`, not rollback). One real divergence: the sibling bump loops validate a precondition (`current == bump.from` / `current == bump.to`, else `GraphError::UnexpectedManifestVersion`) before writing, giving crash-recovery detection of "is disk in the state I expect." The new `platform_writes` loop has no `from` field on `PlatformWrite` at all and unconditionally calls `write_version` every time regardless of current on-disk content — it can silently overwrite a manifest version that drifted from the plan's expectation (e.g. a manual edit made between plan computation and apply) with no error, whereas every sibling loop in this same function would catch that and refuse. This is a genuine but currently-dormant (only reachable once the field is wired up) weakening of an established invariant — worth a Medium finding, not urgent given the dead-code status.

### 4. Missing input validation / error-case coverage

- `ManifestFormat::from_path` (`crates/callisto-model/src/package.rs:216-234`) only recognizes a fixed allow-list of filenames (`Cargo.toml`, `package.json`, `pyproject.toml`, `setup.cfg`, `go.mod`, `pom.xml`, `deno.json(c)`); anything else — malformed path, no filename, or a lockfile-named path — returns `Err(UnknownManifestFormat)`, propagated cleanly via `?`. Not silent.
- `open()` only actually constructs handles for `CargoToml`/`PackageJson`/`PyprojectToml`; every other recognized format hits the `other =&gt;` arm and returns `Err(ReadOnlyFormat)`. Also visible, not silent.
- The `Manifest` trait (`callisto-manifests/src/lib.rs:26-63`) requires `write_version` and `update_optional_dependencies` as non-default methods on every implementor — so "manifest format doesn't support this operation" cannot happen for any openable format today; this specific worry from the task brief doesn't materialize given the trait's design.
- `npm.rs`'s `update_optional_dependencies` (`npm.rs:353-373`) auto-creates the `optionalDependencies` section if missing and inserts/overwrites unconditionally for every `(name, version)` pair — it never errors on an unknown/new dependency name (unlike `update_dependency_spec`, which does error via `DependencyNotFound`). This is a real asymmetry but is arguably intentional (adding a brand-new optional dep is exactly what a platform-package flow needs) — flagged as undertested, not a bug.
- All of the above are genuinely untested for `platform_writes`/`optional_dep_updates` specifically (only the one happy-path test exists) but none is a live silent-wrong-data-written bug given the trait/format guarantees already in place.

### 5. Does `modified_paths`/staging correctly reflect what happened

Yes for the paths themselves — in both new loops, `modified_paths.push(...)` is the last statement, reached only after `write_version?` and `persist?` both returned `Ok`. No partial-failure-then-staged scenario for the manifest paths.

**However, a real bug exists one layer up:** the `active_ecosystems` computation (`apply.rs:325-349`) that drives both lockfile *refresh* (`354-408`) and lockfile *staging* (`412-431`) is derived **exclusively from `plan.bumps`** — it never inspects `plan.platform_writes` or `plan.optional_dep_updates`. Concretely: a plan containing only `platform_writes`/`optional_dep_updates` entries (exactly the shape of the new happy-path test, which has no `bumps` at all) produces an empty `active_ecosystems` set, so:
- `opts.refresh_lockfiles: true` will never trigger `npm`/`cargo`/`uv`/`poetry` lockfile regeneration for these writes, and
- the corresponding lockfile (`package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`, etc.) will never be added to `modified_paths`/`staged` even if it exists on disk and is now stale relative to the optionalDependencies change just written.

This is a confirmed, code-traced correctness gap in the new feature (Silent Fallback / Spec Drift class) — currently dormant only because nothing populates these plan fields yet.

**[Medium] `platform_writes`/`optional_dep_updates` are excluded from `active_ecosystems`, so their writes never trigger lockfile refresh or lockfile staging**
- Status: CONFIRMED (code-traced, currently dormant — no production producer populates these fields yet)
- Location: `crates/callisto-graph/src/apply.rs:244-262` (the new loops) vs. `apply.rs:325-349` (`active_ecosystems`, sourced only from `plan.bumps`)

- Failing scenario: a `VersionPlan` with only `optional_dep_updates` touching `package.json`'s `optionalDependencies`, `refresh_lockfiles: true`, and a real `pnpm-lock.yaml` on disk — `pnpm-lock.yaml` is neither regenerated nor staged, silently drifting from `package.json`.

- Status: CONFIRMED (code-traced, currently dormant)
