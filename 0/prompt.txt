## NEW BLOCKING ISSUE (introduced by this revision)

**`ManifestWriteGroup`'s persist-trigger condition is ambiguously worded, and its most natural literal reading silently drops a successful rewrite's mutation from disk.**

The api_surface text says: *"Only if `mutated` is true after the bump step and every rewrite in rewrite_indices has succeeded does the pass call handle.persist(permit)"*

But `mutated` is described as a cumulative flag that can be set true in TWO places: during the bump step (`current == from` → `write_version` called, `mutated = true`) AND during the rewrite step (*"calling handle.update_dependency_spec(...) for each and setting `mutated` true on the first one applied"*). The persist-trigger sentence checks `mutated` "after the bump step" — read literally, that's a snapshot taken BEFORE the rewrite loop runs, not the flag's final value after both steps complete.

Concretely: if `bump` is `Some` and skipped (current already == target, so `mutated` stays `false` after the bump step) but the group also has one or more `rewrite_indices` that DO successfully mutate the document (setting `mutated = true` during the rewrite step), the literal reading of the persist condition — "mutated is true after the bump step" — is false, so persist would never be called. The rewrite's in-memory mutation would be silently lost, never written to disk. This is a real correctness regression, not just an inefficiency, and it's exactly the class of silent-data-loss bug that caused the original combined spec to be split into two in the first place.

No acceptance criterion exercises this scenario either way: AC-001/AC-002's N-entries fixture doesn't specify whether the bump component is a skip or a real mutation; AC-003's byte-correctness fixture has a real (non-skip) bump; the existing `apply_is_idempotent_when_manifest_already_at_target_version` test (required to keep passing per AC-009) has a bump-only fixture with zero rewrites. So a "skip-bump + real-rewrite" implementation bug — in either direction — would currently pass every stated AC.

**Suggested fix:** Reword the persist-trigger sentence to unambiguously check the flag's cumulative/final state, e.g.: *"After the bump step and the full rewrite_indices iteration both complete without an early return, the pass calls handle.persist(permit) if and only if `mutated` is true at that point (having possibly been set during either the bump step or the rewrite step) — exactly once, never more."* Additionally, add (or extend AC-002/AC-010) a test fixture covering "bump present but skipped (current==target) + one or more rewrites that do apply" to lock in that persist fires exactly once in that specific combination — this is the one case that would silently fail under the ambiguous reading and today has zero test coverage either way.
