### 2. Hardcoded registry URLs

The GitHub org+repo `orin-dx/callisto` is hardcoded in four URL constructions across both setup actions. ### 3. Hardcoded tool paths

**`setup-callisto/action.yml:65`**: `cargo build -p callisto-cli` — builds in **debug mode** (no `--release`). When the action bootstraps itself from source, the callisto binary being installed for all subsequent steps is a debug build, which is substantially slower on large workspace analysis. This is the only path where callisto itself is built from source (i.e., when CI runs against this repo).

**`callisto-action/action.yml:177`**: `cargo publish -p "$crate" --no-verify --allow-dirty`. The `cargo` binary is assumed on PATH (installed by the setup action upstream). `--no-verify --allow-dirty` are hardcoded flags that differ from how `callisto publish` invokes cargo (`cargo publish -p &lt;name&gt; --locked`, no `--no-verify`). This means the bash path skips the package-builds-cleanly verification that `--locked` enforces, allowing a broken crate to be published.

**`callisto-action/action.yml:214,219`**: `npm publish "$PKG" --access public`. The `npm` binary is assumed on PATH, but there is no `setup-node` step anywhere in the action or workflow. See Bug 1 below.

**`callisto-action/action.yml:228`**: `callisto tag --plan "$PLAN_JSON"` — passing the full plan JSON inline as a shell argument. `tag.rs:43` detects leading `{` and handles this correctly, so there is no parsing bug here, but for very large plans (hundreds of packages) the argument size could approach OS shell limits (~2 MB on Linux).

No `pip`, `python`, or `twine` path is referenced in the action at all — PyPI publishing is entirely absent from the bash path.

### 4. Hardcoded retry counts and delays

**`callisto-action/action.yml`**:

- `max_attempts=12` (line 165) — hardcoded, not an action input
- `delay=15` seconds between index-propagation retries (line 166) — hardcoded
- `sleep 600` (line 189) — hardcoded 10-minute wait when crates.io rate-limiting is detected

None of these are exposed as inputs. A workspace that publishes many crates and consistently hits the index-propagation window would benefit from a configurable delay. The 600-second forced sleep on a rate limit is particularly impactful in a time-bounded CI runner.

### 5. Hardcoded output field names

`callisto-action/action.yml` outputs block:
- `hasChangesets` — boolean string `"true"/"false"`, written via `echo "hasChangesets=true" &gt;&gt; $GITHUB_OUTPUT`
- `published` — same pattern
- `publishedPackages` — multiline heredoc containing the raw JSON from `callisto plan-publish --format json`

The third output is the critical one: `publishedPackages` is set to the **plan** JSON (what Callisto intends to publish), not a report of what actually published. There is no second assignment to `publishedPackages` after the publish loop completes. Downstream workflows that read `publishedPackages` receive the pre-publish plan regardless of which packages succeeded or failed.

`setup-callisto-wasm/action.yml` output `path`: the value expression is `${{ steps.download-wasm.outputs.path || inputs.dest }}`. When the cache hits, `steps.download-wasm` is skipped and its output is empty string, making the `|| inputs.dest` fallback the operative value. This works correctly but is subtle — the output is not stable to inspect mid-pipeline.

### 7. Hardcoded ecosystem-specific publish logic

The action's `INPUT_PUBLISH == "true"` branch (lines 159–223) implements three ecosystem branches:

**Cargo branch** (lines 207–209): `cargo publish -p "$CRATE" --no-verify --allow-dirty` with a 12-attempt retry loop.

- This logic is partially duplicated with `callisto publish` → `SubprocessRegistryClient::cargo_publish`, which uses `cargo publish -p &lt;name&gt; --locked`. The flags differ materially: `--no-verify --allow-dirty` (bash) vs. `--locked` (CLI).
- The bash retry loop manually detects `"already exists"`, `"429 Too Many Requests"`, `"rate-limits"` substring matches — the same classification logic implemented more robustly in `classify_cargo_output()`.
- Disposition: **MOVE TO CALLISTO** — `callisto publish` already exists, is tested, and handles cargo with proper retry/idempotency. The bash loop is a stale duplicate.

**NPM platform/main branch** (lines 212–222): `npm publish "$PKG" --access public || true`

- **Bug**: `$PKG` is a bare package name (e.g., `"@my-org/my-pkg"`), but `npm publish [&lt;folder&gt;]` expects a directory path. `SubprocessRegistryClient::npm_publish` correctly uses `npm publish --workspace &lt;name&gt;` — the workspace flag selects a package by name within an npm workspace. The bash path omits `--workspace`, causing npm to treat the name as a relative path that almost certainly doesn't exist. The failure is silently suppressed by `|| true`.
- No retry logic. No idempotency check (no `npm view` pre-check).
- Disposition: **MOVE TO CALLISTO** — and the npm bug disappears in the process.

**PyPI branch**: entirely absent. No `twine upload`, no `TWINE_*` environment variables, no jq extraction of `pypiPackages`. Python packages are scheduled in the plan but never published.

- Disposition: **ALREADY IN CALLISTO** (`SubprocessRegistryClient::pypi_publish` uses `twine upload --skip-existing`). This branch should be deleted from the action and the cutover to `callisto publish` completed.

### 9. Hardcoded branch names or tag patterns

**Version PR source branch**: `callisto/version-packages` is hardcoded in five places (`callisto-action/action.yml:91,113,116,122,130`). This is not an action input. Users cannot change the branch name the version PR is opened from.

**Base branch**: `main` is the default for `INPUT_BRANCH` (`callisto-action/action.yml:34`), and is hardcoded as the trigger branch in both workflows (`callisto-ci.yml:5,9`, `callisto-release.yml:5`).

**Prerelease tag detection regex** (`callisto-action/action.yml:240`):
```bash
if [[ "$TAG" =~ -(alpha|beta|rc|pre|next) ]]; then
  EXTRA_FLAGS="--prerelease"
fi
```
This pattern requires a hyphen separator. PEP 440 pre-release tags have no hyphen: `1.0a1`, `1.0b2`, `1.0rc1`. If a Python package tag renders as `my-pkg@1.0rc1`, the regex does not match, and the GitHub Release is published without `--prerelease`, making a pre-release appear as a stable release on GitHub. The `callisto` tag template for PEP 440 packages would produce exactly this format.

## Confirmed Bugs

### [High] Bug 1: `npm publish "$PKG"` uses positional-path syntax instead of `--workspace &lt;name&gt;`

- **Status**: CONFIRMED — path traced through jq extraction (`.npmPlatformPackages[]?.name` → bare package name string) and `npm publish` documentation.
- **Location**: `.github/actions/callisto-action/action.yml:213-222`
- **Classification**: Silent Fallback / Incorrect Tool Invocation
- **Root Cause**: `npm publish [&lt;folder&gt;]` expects a directory path or tarball. The action passes the npm package name (e.g., `@my-org/my-pkg`) as a positional argument, which npm interprets as a relative filesystem path. The `|| true` on every publish call suppresses the ENOTDIR or ENOENT failure, so npm platform and main packages are never published on the `publish: "true"` path.
- **Contrast**: `SubprocessRegistryClient::npm_publish` in `publish_client.rs:104-116` correctly uses `npm publish --workspace &lt;name&gt;`.
- **Failing Scenario**: Any workflow with `publish: "true"` and npm packages in the plan — all npm publishes fail silently, `published=true` is emitted, `publishedPackages` is set to the plan JSON, and no package reaches npm.
- **Fix**: Replace the bash publish loop with `callisto publish`.

### [High] Bug 2: `pypiPackages` in plan JSON is never consumed — PyPI packages silently skipped

- **Status**: CONFIRMED — `PublishPlan.pypi_packages` serializes as `pypiPackages` (camelCase via `rename_all`); the action extracts `rustCrates`, `npmPlatformPackages`, `npmMainPackages` but not `pypiPackages`. No `twine` call anywhere in the action.
- **Location**: `.github/actions/callisto-action/action.yml:159-223`
- **Classification**: Silent Fallback
- **Root Cause**: The PyPI ecosystem was added to `PublishPlan` and `SubprocessRegistryClient` but the corresponding extraction and publish step was never added to the action's bash loop.
- **Failing Scenario**: A workspace with one or more `publish_to: [pypi]` packages — `callisto plan-publish` schedules them, the jq loop extracts nothing, no `twine upload` is called, the action emits `published=true`, and the packages remain unpublished.
- **Fix**: Replace the bash publish loop with `callisto publish`, which already handles PyPI.

### [High] Bug 3: `NPM_TOKEN` is set in the workflow but never read by the action

- **Status**: CONFIRMED — `callisto-release.yml:71` sets `NPM_TOKEN: ${{ secrets.NPM_TOKEN }}` in the job env. The action's bash code contains `npm publish "$PKG" --access public` with no npm auth setup step, no `.npmrc` configuration, and no reference to `$NPM_TOKEN`.
- **Location**: `.github/actions/callisto-action/action.yml:212-222`, `.github/workflows/callisto-release.yml:71`
- **Classification**: Silent Fallback / Discarded Parameter
- **Root Cause**: npm auth in CI must be pre-configured (via `.npmrc`, `npm config set //registry.npmjs.org/:_authToken=`, or a `setup-node` step with `registry-url`). None of these are present. The token is set in the environment but no tool reads it.
- **Failing Scenario**: CI run with npm packages to publish — `npm publish` exits `ENEEDAUTH`, `|| true` suppresses it.
- **Fix**: Either add a `setup-node` step with `registry-url: https://registry.npmjs.org/` (which makes `setup-node` write the auth token to `.npmrc` automatically), or replace the bash path with `callisto publish` (which inherits the runner environment and relies on npm's own `.npmrc` resolution — still requires the token to be in the environment in a form npm reads, but at least the `--workspace` flag is correct and errors propagate rather than being suppressed).

### [Medium] Bug 4: `callisto tag ... || true` and `git push origin --tags || true` suppress all tag creation and push failures

- **Status**: CONFIRMED — both commands on action.yml:228-229 are `|| true`.
- **Location**: `.github/actions/callisto-action/action.yml:228-229`
- **Classification**: Silent Fallback
- **Root Cause**: If `callisto tag` fails (e.g., git not configured, workspace error, version plan parse error), the step succeeds. `git push origin --tags` then pushes nothing (or partial tags). The GitHub Release creation loop (lines 234-246) then calls `gh release create "$TAG"` for tags that were never pushed — GitHub creates orphan releases pointing at the commit directly, not at any tag, which defeats the purpose of the tag-based release workflow.
- **Failing Scenario**: Any transient git error during `callisto tag` — the error is swallowed, the release step runs, and GitHub creates releases without corresponding tags.
- **Fix**: Remove the `|| true` on both lines. The `set -e` at the top of the script will then correctly abort on tag failure.

### [Medium] Bug 5: `publishedPackages` output is the publish **plan**, not the publish **result**

- **Status**: CONFIRMED — action.yml:149-151 sets `publishedPackages` immediately after `callisto plan-publish`, before the publish loop runs. There is no second write to this output after publishing completes.
- **Location**: `.github/actions/callisto-action/action.yml:147-151`
- **Classification**: Spec Drift
- **Root Cause**: `publishedPackages` is named as the set of packages that were published, but its value is the pre-publish plan. Failed publishes are indistinguishable from successful ones from the output's perspective. The existing ledger entry notes this was identified and partially fixed in the Rust orchestrator (which now produces a `PublishReport`), but the action's output was not updated.
- **Fix**: Replace the publish loop with `callisto publish --format json` and pipe its JSON output to `publishedPackages`. The `PublishReport` JSON contains per-package `result: Published | AlreadyPublished | Failed { error }` entries.

### [Medium] Bug 6: PEP 440 prerelease tags not detected — Python prereleases published as stable GitHub Releases

- **Status**: CONFIRMED — regex `-(alpha|beta|rc|pre|next)` requires a hyphen separator; PEP 440 pre-release identifiers (`a`, `b`, `rc`) attach directly to the version number with no separator.
- **Location**: `.github/actions/callisto-action/action.yml:240`
- **Classification**: Spec Drift (PEP 440 vs. SemVer assumption)
- **Root Cause**: The regex was written for SemVer-style pre-release identifiers. PEP 440 prereleases look like `1.0a1`, `1.0b2`, `1.0rc1`. A Python package tagged `my-pkg@2.0rc1` does not match `-(alpha|beta|rc|pre|next)` and is released on GitHub without `--prerelease`, appearing as a stable release.
- **Failing Scenario**: Any workspace with a Python package in pre-release mode (`callisto pre enter rc`), with a bumped version like `1.0.0rc1` — the GitHub Release is created as stable.
- **Fix**: Add PEP 440 pre-release detection: `[[ "$TAG" =~ [0-9](a|b|rc|alpha|beta)[0-9] ]] || [[ "$TAG" =~ -(alpha|beta|rc|pre|next) ]]`. Or, better, have `callisto plan-publish` emit a `prerelease: bool` field on `ReleaseEntry` and use that instead of regex-guessing from the tag string.
