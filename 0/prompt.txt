[101] assistant: The core implementation has a strong security posture; the biggest residual risk is release-pipeline trust, not ordinary Rust memory safety or manifest handling.

## What is strong

- Safe Rust is enforced workspace-wide.
- Write-capable operations require an `ApplyPermit`, so dry-run paths cannot accidentally mutate disk.
- Manifest/config paths are constrained to the workspace; TOML/JSON edits preserve structure; writes use temp-file replacement plus file sync.
- Apply is guarded by expected `from`/`to` versions, preventing a stale plan from overwriting an unexpected manifest state.
- Registry publishing is unusually well defended:
  - `publishConfig.registry` must be HTTPS and exactly match an operator-configured registry;
  - publish-target ecosystem mismatches fail closed;
  - subprocess output has a 10 MiB capture cap;
  - known credentials and URL userinfo are redacted from live output and diagnostics.
- The dependency audit completed successfully: no active RustSec advisory was reported for the resolved lockfile, and unknown registries/Git sources are denied in [deny.toml](/Users/gabe/Projects/callisto/deny.toml).

## Confirmed security concerns

1. Release credentials run automatically on every push to `main`.

The release job has `contents`, PR, check, and status write permissions and receives Cargo/npm tokens; it triggers on every push to `main` with no GitHub Environment approval gate. See [callisto-release.yml](/Users/gabe/Projects/callisto/.github/workflows/callisto-release.yml).

That can be acceptable only if branch protection is exceptionally strong. Otherwise, any malicious or compromised merged code can execute with registry credentials.

Recommendation: move actual publishing to a protected `release` Environment requiring approval, and trigger publishing from a protected tag or explicit dispatch—not every ordinary `main` push.

2. Third-party GitHub Actions are tag-pinned, not SHA-pinned.

Examples include `actions/checkout@v4`, `taiki-e/install-action@v2`, and toolchain setup actions. Tags are convenient but mutable pointers. A compromised action release can compromise CI, and in the release workflow that means credentials.

Recommendation: pin actions to immutable commit SHAs; use Dependabot/Renovate to maintain them. This is the highest-value supply-chain hardening change.

3. Advisory policy is permissive and not reproducible enough.

The audit passes, but [deny.toml](/Users/gabe/Projects/callisto/deny.toml) has a broad advisory-ignore list for Wasmtime-related test dependencies and explicitly describes advisory DB results as unstable. Today’s run says those ignored advisories were not encountered, which is good; however, the policy makes future review harder. The lockfile also contains yanked `bisync 0.3.0`, transitively through `gix`.

Recommendation: update/remove the yanked dependency when upstream permits it, pin the advisory database revision or otherwise make CI’s advisory input reproducible, and give every advisory exception an owner and expiry/review date.

## Important design risks, not confirmed vulnerabilities

- Release tags are SHA-related but not signature-enforced. The docs should say “SHA-anchored” unless CI verifies trusted Git signatures.
- File writes are atomically durable per file, but a multi-file version operation is not one filesystem transaction. The idempotency checks make retries safe, but a durable plan/outcome model would improve recovery and auditability.
- Per-crate coverage is currently warning-only; security-sensitive crates should not rely solely on the aggregate 90% threshold.

## Recommended order

1. Protect publishing with a GitHub Environment, approval, and least-privilege release permissions.
2. Pin every external action by commit SHA.
3. Make release plans SHA-bound and upload them as artifacts before side effects.
4. Clarify unsigned-vs-signed tag policy; add optional signature verification later.
5. Tighten dependency/audit reproducibility and retire the yanked `bisync` path.
6. Add fault-injection tests for partial release recovery and failed directory sync.

I would rate the code-level posture as strong, the dependency posture as acceptable but needing cleanup, and the current release workflow as the main high-impact hardening target.
