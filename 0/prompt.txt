## Findings

**1. Untested interaction: AC-16 hybrid-root exemption × AC-11c malformed-pnpm fallback (missing-error-case)**
Per the new arm (d), the AC-16 exemption fires "only when arm (c)...is what would otherwise govern," and per AC-11c arm (c) *does* govern whenever pnpm-workspace.yaml is malformed. So a hybrid-root package.json sitting next to a broken pnpm-workspace.yaml must still get its root entry — but no criterion or AC-13 fixture proves it; AC-16's own fixture explicitly says "no pnpm-workspace.yaml anywhere." Suggested fix: add `AC-16b` (is_error_case: true) with the exact combined fixture (hybrid-root package.json + malformed pnpm-workspace.yaml → root entry still returned via arm c/d), and extend AC-13's group.

**2. AC-10 was never updated to carve out AC-16, unlike its own sibling AC-10c (ambiguous / internal contradiction)**
AC-10c already anticipated exactly this interaction on the Cargo side: "returns zero Cargo-ecosystem entries **besides any AC-07-style hybrid root package**." AC-10 (its npm mirror) says only "returns zero Npm-ecosystem entries" — no exception. AC-10's fixture never states the root package.json lacks a "name" field, so a root satisfying both AC-10 (`"workspaces": []`) and AC-16 (`"name"` + `"workspaces"` present) is a literal contradiction: AC-10 mandates zero entries, arm (d) mandates the root entry always survive. Suggested fix: rewrite AC-10's criterion text to add the same "besides any AC-16-style hybrid root package" carve-out AC-10c already has, and add `AC-10d` as a concrete proving fixture (root has both `"name"` and `"workspaces": []` → exactly one entry, path `"."`).

**3. The deferred pnpm-hybrid-root non_goals entry is a judgment call I'm overriding: it should be fixed now, not deferred (incomplete)**
The non_goals entry's reasoning — "pnpm-workspace.yaml carries no name/hybrid marker" — is true but irrelevant. AC-07/AC-16's actual principle is "the root directory's own package identity is never dropped by its own governing membership list," not "the identity field and the governing list must live in the same file." npm's root identity always lives in `package.json`'s `"name"` field regardless of which file governs membership (its own `"workspaces"` array, or a sibling `pnpm-workspace.yaml`). A pnpm monorepo with a named root `package.json` and a separate `pnpm-workspace.yaml` — an extremely common, arguably the *most* common pnpm layout — will silently lose its root package under the current text, which is externally indistinguishable from the bug AC-07/AC-16 exist to close. This is exactly the kind of "plausible-sounding, quietly-deferred" language this audit exists to catch. Suggested fix: delete the deferring non_goals entry; add `AC-17` (is_error_case: false) proving the pnpm-governed hybrid-root case; broaden api_surface arm (d) to `"the root package.json declares a 'name' field and dir is the workspace root itself, regardless of whether arm (b) or arm (c) governs the rest of npm membership filtering... (see AC-07, AC-16, AC-17)"`; and give `AC-10b` the same "besides any AC-17-style hybrid root package" carve-out AC-10 needs per finding 2.
