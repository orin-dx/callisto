  **Findings (none is a hard bypass of a correctly produced manifest)**
  
  **F1. Sealed bytes are verified once, then trusted at upload (Medium, CONFIRMED by trace).**
  - `release_artifacts.rs:139-153` hashes the files at the start of `execute`.
  - `registry.rs:916-960` (`publish`) uploads `file.path` and never re-hashes.
  - Between the two, the executor runs earlier operations, including propagation waits and retries. The sealed `BuiltFile.sha256` comes from the manifest, not from the file on disk.
  - Failing scenario: a file in `release-assets` is swapped or edited after verification, and twine uploads the new bytes.
  - The only detector is `confirm` (`registry.rs:975-1011`), which runs after the irreversible upload and only fires if the index serves a sha256 (F2).
  - Fix: re-hash and re-check for symlinks inside `publish` right before building the upload argv. Alternatively, copy the verified files into a private temp dir at verify time.
  
  **F2. A missing sha256 passes the strict compare as "equal" (Low-Medium, CONFIRMED).**
  - `pypi_files.rs:221-224` uses `held.sha256().is_some_and(|d| d != file.sha256)`. An index entry with no `sha256` key never counts as differing. PEP 691 only requires some hash, so an index that serves only sha512 qualifies.
  - For a sealed set, a same-name file with unknown bytes is accepted as `AlreadySatisfied` in preflight and as exact in `confirm`. That contradicts the sealed guarantee.
  - Fix: for a sealed set, treat a missing sha256 as Indeterminate or as differing.
  
  **F3. Sealing is opt-in on the execute side (Medium as a design gap).**
  - `validate_distributions` (`artifact.rs:282`) accepts an empty list. Nothing in the intent or envelope requires a seal.
  - Scenario 1: an intent with slots and a Python publish, with a manifest from `artifact-manifest` run without `--seal-python`. `built_set` (`registry.rs:766-795`) falls back to building in the credentialed job, with only an `eprintln` warning.
  - Scenario 2: a Python-only intent run with no `--artifact-manifest` gets `(true, None, None) => None` in `release.rs:~570`. It builds silently, with no warning at all.
  - Scenario 3: the generated workflow's `has_python` switch is the only thing that turns sealing on. A stale or edited workflow downgrades the release with no error.
  - Fix: make the execute-side requirement explicit, for example a `--require-sealed-python` flag, or record sealing in the intent or envelope. If the opt-out is intentional, it needs a record under AGENTS.md ("deliberately deferred" rule).

### Engineering judgment

The architecture is thoughtful. The release intent, provider observation, preflight, publish, and confirmation stages have distinct responsibilities. #232 removes the unsafe dist/* style upload and makes recovery operate on an explicit file inventory. #233 binds downloaded Python files to a manifest, verifies their bytes, and keeps the matrix build job free of registry credentials. The code also removes known credential variables from Python build subprocesses. Those are meaningful security and maintainability improvements.

The cost is considerable complexity: roughly 2,900 changed lines across the stack, with another durable manifest field and more provider state. I think that complexity is justified for partial-upload recovery, but it raises the value of end-to-end evidence. Both PRs currently have 12 passing GitHub checks. Their tests cover partial uploads, reruns, yanks, index lag, altered bytes, and manifest validation. The repository also enforces a 90% workspace coverage gate. The remaining limit is that the hosted generated workflow has not run; the existing real-registry tests do not exercise every production binding and observation path.

For publishing practice, Cargo metadata and dependency direction are sound, and Cargo performs package verification during publish; its own guide additionally recommends a pre-publish dry run and package-content inspection. Cargo publishing guide (https://doc.rust-lang.org/cargo/reference/publishing.html). For npm and PyPI, the generated workflows still use long-lived secrets. Both registries now document trusted publishing with short-lived OIDC credentials; that is a worthwhile future security improvement, especially for a release tool, rather than a defect introduced by these PRs. npm trusted publishing (https://docs.npmjs.com/trusted-publishers/), PyPI trusted publishing (https://docs.pypi.org/trusted-publishers/). Python-only generated releases also remain unsealed and build inside the write-capable release job, as #233 clearly discloses.

My merge recommendation: fix the hashless-confirmation contract and stale docs, then merge #232 before #233. Treat #233’s generated workflow as promising but not fully validated until one representative hosted build, partial upload, and rerun has succeeded. I made no repository changes.
