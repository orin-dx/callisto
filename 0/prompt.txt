## Executive verdict

Callisto’s core idea is sound, and substantial parts of the implementation are strong. The immediate problem is not that the project needs more release machinery. It has too many partially overlapping release concepts, while basic operational guarantees—resume, recovery, exact-version installation, and truthful success reporting—are incomplete.

The central failure pattern is:

```text
Strong local abstractions
        ↓
Complex release authorization and handoff
        ↓
Weak cross-job recovery and external-state observation
        ↓
Tests pass locally
        ↓
Real release fails in a new way
```

The right correction is to make Callisto a smaller, clearer release engine:

1. A reviewed release PR records exactly what will be released.
2. Merging that PR authorizes the release.
3. Rust owns versioning, dependency propagation, publish ordering, and provider semantics.
4. CI supplies credentials and schedules execution.
5. Registry, Git, and GitHub state—not transient runner files—determine whether an operation needs to run.
6. A release only exits successfully if every planned operation is observably complete.

The extra environment approval should be removed. It duplicates PR approval, adds latency, and does not solve the actual safety problems.

I made no repository changes.

## What Callisto should be

Based on the design documents, code, history, and competitor research, the product north star should be:

> Callisto is a crash-safe release engine for Cargo, npm, and Python monorepos, using Changesets-compatible intent and providing first-class coordination for native npm packages backed by Rust crates.

Its distinctive wedge is not merely “Changesets in Rust.” It is:

- Changesets-compatible authoring.
- Cargo, npm, and Python versioning through one dependency graph.
- Correct handling of npm native packages, platform packages, and underlying crates.
- Format-preserving manifest edits.
- Crash-safe local writes.
- Deterministic plans that can be executed or resumed in CI.
- One semantic engine usable from the CLI, Moon, and automation.

Pre-v1 non-goals should include:

- Becoming a general-purpose supply-chain attestation platform.
- Supporting every package ecosystem.
- Building a bespoke approval bureaucracy around GitHub Actions.
- Maintaining two complete release engines for compatibility.
- Advertising binary distribution until the pipeline genuinely creates and publishes those binaries.

The current design document already contains most of these ideas, especially the native-package cases and “release semantics in core, thin wrappers outside” principle. The implementation and workflow have drifted from that simplicity.

## What the reference tools teach us

The relevant tools differ in implementation, but they converge on several principles:

- Changesets divides the flow into versioning and publishing. Its GitHub Action can maintain a version PR and publish after merge; `changeset publish` uses actual registry state when deciding what remains to be published. [Changesets action](https://github.com/changesets/action/blob/main/README.md), [Changesets versioning and publishing](https://changesets.dev/guide/versioning-and-publishing)
- Knope continuously maintains a release PR; merging that PR initiates the release, and downstream workflows can perform additional publication. [Knope bot workflow](https://knope.tech/tutorials/bot-workflow/)
- Nx models version, changelog, and publish as explicit phases, and its CLI uses the same programmatic release functions rather than maintaining a second semantic implementation. [Nx release documentation](https://nx.dev/docs/features/manage-releases), [Nx programmatic API](https://nx.dev/docs/guides/nx-release/programmatic-api)
- release-please separates the release PR from release creation. It explicitly treats release creation as non-transactional and makes rerunning safe. [release-please manifest releaser](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md), [release-please CLI](https://github.com/googleapis/release-please/blob/main/docs/cli.md)

The shared lesson is important: these tools rely on a reviewed source state, separable phases, and rerunnable observation. None requires a custom signed handoff plus a second human approval for an ordinary release-PR workflow.

Callisto should keep its Rust executor, but simplify what that executor considers authoritative.

## 1. The executor can falsely report success after a failed attempt

This is the most serious correctness defect.

The execution flow marks an operation `Attempting`, writes the state, and then dispatches it. If dispatch fails, the operation remains `Attempting`.

On a rerun:

- Reconciliation only selects `Pending` operations whose prerequisites succeeded.
- The abandoned `Attempting` operation is not selected.
- No operation is eligible.
- The executor exits its loop.
- The CLI returns `ExitCode::SUCCESS`.
- No terminal receipt is constructed to prove that the release actually completed.

The receipt implementation already rejects nonterminal states, but the production CLI does not require a receipt before returning success.

Relevant code:

- [release_execution.rs](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/release_execution.rs)
- [release CLI command](/Users/gabe/Projects/callisto/crates/callisto-cli/src/commands/release.rs)
- [release model](/Users/gabe/Projects/callisto/crates/callisto-model/src/release.rs)

This is worse than a loud failure because automation can treat an incomplete release as successful.

Required correction:

- Every `Attempting` operation must be externally observed on resume.
- It must resolve to `Succeeded`, `Pending`, or `Conflict`.
- The CLI must only return zero after successfully constructing a terminal `ReleaseReceipt`.
- “No eligible operation” must not imply completion.

## 2. Durable state is not durable across the real workflow boundary

The release workflow writes execution state under:

```text
${RUNNER_TEMP}/callisto-release-state/${GITHUB_RUN_ID}/execution-state.json
```

That state is lost with the runner. It is not uploaded after each operation or restored on rerun.

Relevant files:

- [release workflow](/Users/gabe/Projects/callisto/.github/workflows/callisto-release.yml)
- [release store](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/release_store.rs)

More importantly, even uploaded state should be an audit journal—not the sole source of correctness. The executor must be capable of rebuilding its understanding from registries, tags, releases, and immutable plan data.

## 3. `release reconcile` is not reconciliation

The current command reads local state and identifies eligible pending operations. It does not query:

- crates.io
- npm
- PyPI
- Git tags
- GitHub Releases
- uploaded release assets

It therefore cannot answer the essential recovery question:

> Did the last attempt finish remotely before the process or network failed?

That question must be answered for every provider using a common contract:

```text
observe(operation) -> Missing | Exact | Conflict
apply(operation)
verify(operation)  -> Exact | Conflict
```

Interpretation:

- `Missing`: safe to execute.
- `Exact`: already complete; mark successful.
- `Conflict`: something exists, but it does not match the planned source/version/digest; stop loudly.

This is the heart of crash-safe release execution.

---

## 4. There is no practical manual recovery target

The workflow has no meaningful `workflow_dispatch` inputs, and release planning is tied to `GITHUB_SHA`.

Once `main` advances, artifacts expire, or the original run becomes unusable, an operator cannot cleanly say:

> Resume the release plan from commit X with digest Y.

A recovery workflow needs an explicit immutable target:

- release commit SHA
- plan path or plan digest
- optional expected release identifier

It must validate that these agree before doing anything.

This is one reason the recent release sequence became a chain of workflow reruns instead of a controlled resume operation.

## One correction to Claude’s proposed path

The rehearsal should not preserve the current sequence simply because it exists:

```text

```

That sequence embeds two unsettled choices:

- The extra approval should be removed.
- Build/attestation should only exist when the release plan actually contains binary artifacts.

The more accurate target is:

```text
plan → [build and attest planned artifacts] → observe → execute → verify → receipt
```

The bracketed phase is conditional. Merge of the reviewed release PR is the approval.

It should also be checked into the repo, required in CI, and tied to every release-workflow change. Otherwise the same failure mode can recur: good analysis, local patch, green unit tests, then production reveals the next boundary defect.
