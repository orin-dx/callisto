No, not for this workload. Of the Rust git libraries, gix is the better one, but neither beats the git binary where it matters most for us.

I measured the three operations that dominate Callisto's time on the 4000-package fixture (8002 commits), release builds, same machine:

┌────────────────────────────┬────────────────────┬───────────────┬─────────────────────┐
│         operation          │ system git (today) │   gix 0.90    │ git2 0.21 (libgit2) │
├────────────────────────────┼────────────────────┼───────────────┼─────────────────────┤
│ tags with their commits    │             ~65 ms │        ~80 ms │          ~90–120 ms │
├────────────────────────────┼────────────────────┼───────────────┼─────────────────────┤
│ manifest at every tag      │            ~255 ms │       ~200 ms │       ~1100–1600 ms │
├────────────────────────────┼────────────────────┼───────────────┼─────────────────────┤
│ history with changed paths │            ~730 ms │ ~3300–3600 ms │   ~20,000–22,000 ms │
└────────────────────────────┴────────────────────┴───────────────┴─────────────────────┘

- gix vs git2: gix is far better, about 6× faster on the history walk and 5–8× on blob reads. It's pure Rust, actively developed, and what cargo itself is moving toward. If we use a Rust library, it's gix.
- gix vs the git binary: git wins the history walk by about 4.5×. gix is only ahead on manifest reads, and by about 25%. That's roughly 50 ms at 4000 packages and about 6 ms at 500.
- Tuning: I tried an object cache and the repository's own tree diff, and neither changed the history result. gix has no combined-diff support either, so merge commits would still need the binary.
- Caveats: These are naive single-threaded spikes, not tuned production code, and another process was compiling on the machine, so expect noise of about ±15%. The history gap is too large for that to change the conclusion.

My recommendation is to keep system git for all of it. Adopting gix for the manifest reads would add 100+ crates, an ADR reversal and a second code path, for about 6 ms on a realistic workspace. That is not a good trade. I'd revisit if gix's tree diff gets much faster. The spike is in the job's temp directory, not the repo, so nothing needs reverting.

The remaining time is git log itself and the sequential directory walk. The walk (~230 ms at 4000 packages) is ours to speed up, so that is what I'll do next: read manifests in parallel during workspace load.

Here is what the profile shows, with the caveats:

At 4000 packages and 8000 commits, status is about 2.2 s, and 74% of it is waiting on git. My first profile was misleading: it missed the start of the run and showed a git-dominated picture that was incomplete. The corrected one found two problems in code I had just written, and I've fixed both:
- The aggregation was quadratic (about 640 ms): it cloned paths per tag and tested every path against every package. It's now linear, with each package getting a list of the commits that touched it.
- A tag on an unmerged branch was treated as "everything after it". The old code counted a package as changed when its files differ from the tag, which includes a hotfix that HEAD lacks. The rule is now exact: a commit counts if it is reachable from HEAD or the tag, but not both. Tests cover a merge and a hotfix branch, each checked against the old per-tag walk.

I also fixed the tag-glob matching (a sorted index replaces testing every glob against every tag, worth about 220 ms), and I retracted my earlier claim that commit hashes would make the manifest batch 5× faster: measured, it's about 25%, so I dropped it.

What's left is git doing real work (git log over 8000 commits, 730 ms) and the sequential directory walk (230 ms). The timings are noisy, because another process on this machine is compiling. I'll push the redesign onto PR #330 once CI reports exit=0.

From claude:

I now have a fair comparison, and it changes the answer: gix wins at realistic sizes and loses at extreme ones. On repacked repositories (like real clones), the history walk with changed paths:

┌────────────────────┬────────────────┬──────────────────────────────────────────┬─────────────┐
│ packages / commits │ system git log │              gix low-level               │     gix     │
├────────────────────┼────────────────┼──────────────────────────────────────────┼─────────────┤
│ 500 / 1000         │          60 ms │                                    17 ms │ 3.5× faster │
├────────────────────┼────────────────┼──────────────────────────────────────────┼─────────────┤
│ 2000 / 4000        │         304 ms │                                   253 ms │ 1.2× faster │
├────────────────────┼────────────────┼──────────────────────────────────────────┼─────────────┤
│ 4000 / 8000        │       ~1020 ms │ 3380 ms (2000 ms with a 1 GB pack cache) │ 3× slower   │
└────────────────────┴────────────────┴──────────────────────────────────────────┴─────────────┘

- The diff resource cache wasn't the lever. Reusing it moved 4000 packages from 3.3 s to 3.0 s. The sample showed 75% of the time in zlib inflate and memmove, which is delta-chain resolution. The 150 KB crates tree is rewritten 8000 times in that fixture. That is the pathological case: one flat directory with 4000 entries and deep history.
- Manifest reads: gix is about 25% faster at 4000 packages (~200 ms vs 255 ms). Tag listing is a wash (~80 ms vs ~65 ms).
- Where gix can't do it: it has no combined-diff for merge commits (--cc). A path differs from every parent exactly when it appears in each parent's diff, so I can intersect per-parent diffs. It also has to fall back to the system git on any error.

My plan, keeping the binary as the fallback exactly as you asked:
1. Add a native read backend (tags with commits, blob reads, history with changed paths) inside GitAccess, with the same results as the CLI path. Writes, signing, trust checks and the worktree diff stay on git.
2. Fall back to the CLI on any gix error, an unusual repository (shallow, repository root not the workspace root), or a runtime switch (CALLISTO_GIT_BACKEND=system) so I can keep benchmarking both.
3. Test equivalence against the CLI on the same merge and hotfix histories, and keep the process-count gate.
4. Write ADR 13, which supersedes ADR 5, with these numbers and the 4000-entry regression as the revisit trigger. You'd need to accept it, per AGENTS.md.

The one open question is the flat 4000+-entry case, where the CLI is 3× faster. My default is to take gix anyway and set a pack cache of a few hundred MB, because it is rare, and real monorepos spread packages over directories. If you'd rather not regress it, I can read the first tree's size and pick the backend per repository. Starting stage 1 on a new branch off #330.
