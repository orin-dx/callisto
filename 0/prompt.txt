Yes. The recurring problem is that Callisto builds a release decision from a workspace that has never been proven complete.

Release execution (docs/architecture/release.md) has explicit Absent, Exact, Conflict, and Indeterminate states. Earlier in the pipeline, discovery returns a list of projects (crates/callisto-graph/src/locate/mod.rs:13), while failed reads, invalid membership, and failed manifest opens can all reduce that list or its graph. A smaller graph still looks valid to the planner.

I see five architectural gaps behind the defects:

1. No release-ready workspace boundary. Workspace loading (crates/callisto-graph/src/lib.rs:93) returns a Workspace after graph construction, but does not establish that every admitted manifest was read and every package’s publish targets and edges were resolved. Add a validation step that produces a distinct release-ready workspace; version and release planning should require it. status could still display an incomplete scan with diagnostics.
2. Absence and failure share the same representations. Option, .ok(), exists(), and admit-all defaults are used for both legitimate absence and failed observation. OpenContext (crates/callisto-manifests/src/lib.rs:206) is a clear example. Use Result<Option<T>, E> for optional files and explicit states for membership: absent, valid, invalid. A helper can standardize filesystem reads, but it cannot decide the policy for malformed TOML or YAML.
3. Filesystem paths are assumed to be Git paths. Discovery permits directory symlinks, while apply stages workspace-relative paths (crates/callisto-graph/src/apply.rs:509). A package path needs validation against the Git checkout and staging rules before it enters a writable plan. This is a distinct property from being readable or inside the apparent workspace path.
4. Write authorization does not establish a valid write set. ApplyPermit effectively enforces dry-run behavior. VersionPlan (crates/callisto-graph/src/plan.rs:14) is a mutable collection of paths and edits, and apply performs sequential writes before Git staging. That design intentionally permits partial runs, but it makes late path and I/O failures expensive. A preflight should validate every target, path relationship, and required input before the first write; the existing recovery rules remain necessary.
5. Tests and specs sometimes preserve the unsafe fallback. The workspace spec (docs/specs/workspace.json:77) explicitly says malformed membership input admits broadly, and tests assert it. More tests of that behavior will reinforce it. The owner first needs to choose the desired failure policy, then the spec and tests can enforce that policy. Fault injection should cover read errors and incomplete graph construction, alongside the existing release-executor simulator.

I would address these in that order. The key design change is a validated boundary before planning, backed by typed “missing versus failed” results. That makes an incomplete package roster an error the planner cannot accidentally treat as an empty or smaller release. It is more effective than a blanket lint against .ok() or Path::exists(), which would flag harmless uses without proving release completeness.
