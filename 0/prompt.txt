## Recommendations per design question

### Q1: Where to build the createCommitOnBranch payload -&gt; (B) Rust `callisto release-pr commit-plan`

Rationale:
- Spec 014 architecture.execution says the shell "does not independently choose" anything and AC-004 forbids caller-controlled jq filtering. Deciding which paths are additions vs deletions, what to do with mode changes, renames, `.github/workflows/` paths, non-UTF-8 paths, and size limits is file-semantics policy; it belongs in typed Rust with unit tests, not in `git status --porcelain` parsing in bash (which cannot handle paths with spaces/newlines/quotes robustly).
- createCommitOnBranch cannot express modes (100755, 120000 symlink, 160000 submodule) or renames/type changes. A Rust builder can fail closed with typed miette errors; bash would silently strip the executable bit.
- Payload bytes must be read from the worktree as raw bytes (`std::fs::read`), not via `CommandRunner` whose `CommandOutput.stdout` is `String` (lossy UTF-8; see `crates/callisto-cli/src/runner.rs:39`). CRLF and binary files round-trip only if bytes are never decoded.
- Testability: pure `ReleasePrCommitPlanV1::from_changes(...)` in `callisto-model` is unit-testable; the Git observation goes through `CommandRunner` and is testable with the recording runner pattern already used in `crates/callisto-vcs/src/shell.rs` tests.
- Provider neutrality: the plan is `{baseCommit, message, additions[{path, contentsBase64}], deletions[{path}]}`; the shell does one mechanical jq mapping to GraphQL `FileChanges`. That mapping is covered by the real-binary contract test (the exact class of bug that shipped before).

Layering: plan types + builder + base64 in `callisto-model` (add `base64 = "0.22"`, MIT/Apache-2.0, already in `Cargo.lock`); raw-diff parsing and worktree reads in `callisto-vcs` (`ShellGit`, permissive); CLI wiring in `callisto-cli`.

Add a byte-fidelity invariant that makes the encoding question moot: the executor computes `local_tree=$(git write-tree)` after staging and, after createCommitOnBranch, compares it with `gh api repos/.../git/commits/&lt;new_sha&gt; --jq .tree.sha`. Equal tree OIDs prove the API commit is byte-identical to what Git would have committed (modes, CRLF, binary, everything). Fail before moving the real branch if they differ.

### Q2: Executor sequence and race safety

Snapshot gains `headCommit` per PR (`gh pr list --json headRefOid`) and drops `workflowDeltaFromBase` (which also removes the per-PR `git fetch` + `git diff` loop). Callisto names the staging branch in the decision so the shell never invents a branch name.

Sequence (`create-or-update-release-pr.sh`):
1. `base_commit=$(git rev-parse HEAD)`; `snapshot=$(release_pr_snapshot)`.
2. `decision=$(callisto --format json release-pr decide ...)`; branch on `kind` (noop|create|update). Read `.action.branch`, `.action.stagingBranch`, `.action.expectedHeadCommit` (update only), `.action.pullRequestNumber`.
3. Compose body (unchanged).
4. `$INPUT_VERSION_COMMAND`; `git add -A` (parity for custom version commands).
5. `callisto --format json release-pr commit-plan --base-commit "$base_commit" --message "$INPUT_COMMIT_MESSAGE" --out "$RUNNER_TEMP/release-pr-commit-plan.json"` (replaces the `git status --porcelain` emptiness check: empty plan is a typed error).
6. `local_tree=$(git write-tree)`.
7. Register `trap` that deletes the staging ref (`gh api -X DELETE .../git/refs/heads/&lt;staging&gt;`, tolerate 422/404 with a `::warning::`).
8. Verify #1 (`release-pr verify`) with a fresh snapshot.
9. Staging ref at base: `gh api -X PATCH .../git/refs/heads/&lt;staging&gt; -f sha=$base_commit -F force=true`, falling back to `POST .../git/refs` when the PATCH returns 422 (ref missing).
10. `new_sha=$(gh api graphql --input body.json --jq .data.createCommitOnBranch.commit.oid)` where `body.json` is built by jq from the plan: `expectedHeadOid: .baseCommit`, `branch: {repositoryNameWithOwner, branchName: &lt;staging&gt;}`, `fileChanges: {additions: [.additions[] | {path, contents: .contentsBase64}], deletions: .deletions}`.
11. `remote_tree=$(gh api .../git/commits/$new_sha --jq .tree.sha)`; require `== $local_tree`.
12. Verify #2 with a fresh snapshot (the `headCommit` field makes this the compare-and-swap surrogate for the PR head).
13. Move the real branch: update -&gt; `PATCH .../git/refs/heads/&lt;branch&gt; -f sha=$new_sha -F force=true`; create -&gt; `POST .../git/refs`, falling back to PATCH-force if it already exists (an orphan from a failed prior run; no PR exists on it by construction). Then GET the ref and require `.object.sha == $new_sha` (detects a lost race after the fact; fail loudly).
14. Verify #3, label, `gh pr create` / `gh pr edit` (unchanged).
15. Trap deletes staging branch (also runs on failure). Run to completion; report but do not fail on cleanup failure since the next run force-updates the deterministic staging name anyway.

Staging branch name: deterministic, derived by Callisto: `format!("{release_branch}--staging")`. Deterministic beats random because leftover refs from crashed runs are reclaimed rather than accumulating, and the workflow's `concurrency` group (`durable-release-${{ github.ref }}`, `cancel-in-progress: false`) already serializes runs. `managed_branch_shape` today returns `MalformedManagedBranch` for `--staging` (suffix is not 40-hex), so a PR opened from it already fails closed; add an explicit `ReleasePrDecisionError::StagingBranchPullRequest { number }` so the diagnostic is clear. Also update the `release-candidate` job regex? Not needed: `--staging` does not match `--[0-9a-f]{40}`.

Race safety honesty: REST `updateRef` has no CAS. The window between verify #2 and step 13 is milliseconds; the workflow concurrency group excludes the only automated racer; the post-move GET catches a human push in that window. That is acceptable and should be stated in the spec as the residual.

### Q3: Model changes -&gt; remove Supersede and workflowDeltaFromBase; bump to V2 types; no runtime fallback

- Remove, do not reserve. A "fall back to supersede on 403" would make the shell branch on an HTTP status to choose an operation, which is exactly the policy-in-shell the spec forbids, and it keeps the branch-fetch/diff machinery alive for a path the spike either proves unnecessary or proves the whole plan dead. If NO-GO, nothing ships; the current code stays.
- Schema honesty: `ReleasePrSnapshotV1` is `deny_unknown_fields` and consumed by binaries that can be installed independently of the action script (`setup-callisto` with `source: auto` downloads the latest release), so field changes must be a real version bump. Introduce `ReleasePrPullRequestV2 { number, head_repository, head_branch, head_commit: CommitSha }`, `ReleasePrSnapshotV2` (schema 2), `ReleasePrActionV2 { Noop{reason}, Create{branch, staging_branch}, Update{pull_request_number, branch, expected_head_commit, staging_branch} }`, `ReleasePrDecisionV2` (schema 2), and delete the V1 types. Old action script + new binary fails closed with "unsupported release PR snapshot schema version"; new script + old binary fails the same way. Keep `#[non_exhaustive]`, `deny_unknown_fields`, the `Wire` schema-version check, and the `rename_all_fields = "camelCase"` fix.
- Keep `managed_branch_shape` accepting `canonical--&lt;40hex&gt;` so PR #48 stays managed and is updated in place (AC "retained replacement"). Keep the `release-candidate` regex unchanged.
- New `ReleasePrCommitPlanV1` (schema 1) with `ReleasePrFileAdditionV1 { path, contents_base64 }`, `ReleasePrFileDeletionV1 { path }`, `total_content_bytes`; input `StagedChangeV1 { path, kind: Added|Modified|Deleted|Renamed|Copied|TypeChanged|Unmerged, new_mode: Option&lt;u32&gt;, contents: Option&lt;Vec&lt;u8&gt;&gt; }`. Errors (new codes; E141-E148 are taken, `DIAGNOSTIC_CODE_SOURCE_FILES` in `crates/callisto-model/src/lib.rs` already scans `release_pr.rs` for uniqueness): `EmptyCommitPlan` (E149), `UnsupportedFileMode { path, mode }` (E150), `UnsupportedChangeKind { path, kind }` (E151), `CommitPlanTooLarge { bytes, limit }` (E152), `ForbiddenCommitPlanPath { path }` (E153: rejects `.github/workflows/`, `.git/`, `..`, absolute, non-UTF-8 -- the plan must never carry workflow content), `StagingBranchPullRequest { number }` (E154).

### Q6: Risks and edge cases
- Payload size limit unknown: measured in spike E; `MAX_COMMIT_PLAN_BYTES` constant set from the result; today's payload is ~200 KB.
- PR auto-close: never point the real branch at base; only the staging branch equals base, and it has no PR. Spike F checks reruns.
- `release-candidate` `verification.verified` check is on the merge commit on `main`, not the PR head; unaffected. Bonus: the PR head becomes GitHub-signed. Note rebase-merge would drop that signature; the existing check already requires a verified merge commit, unchanged.
- Rulesets: none today; a future rule on `callisto/version-packages` requiring linear history or blocking force pushes would break `updateRef(force)` exactly as it broke `git push --force` (Aug 6 "pre-receive hook declined" runs). Document.
- Forks: snapshot still rejects foreign head repositories; API calls target `$GITHUB_REPOSITORY` only.
- `gh` availability: already required by the current script; add an explicit `command -v gh` check with a clear error.
- Staging cleanup failure: warn, do not fail; deterministic name means the next run reclaims it.
- Idempotent reruns: create a fresh commit each run (same as today's force push); acceptable.
- `commit-plan` reads worktree bytes after `git add -A`; if a custom `version_command` leaves index and worktree divergent, the tree check catches it.
- Custom `version_command` that touches `.github/workflows/` now fails closed (E153) instead of being force-pushed; this is intended and documented.
