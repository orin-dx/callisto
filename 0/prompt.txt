## Real risks found

1. **None in the npm/pip/cargo/twine publish path.** Every real ecosystem-CLI invocation is behind `CommandRunner`, and every unit test for that path uses a scripted fake — confirmed by reading `publish_client.rs` in full. No test hits a real registry, no test depends on `~/.npmrc`, `~/.pypirc`, `CARGO_HOME`, or auth env vars. The one place that reads ambient env (`known_credential_env_values(std::env::vars())` in `redact_stderr`, `publish_client.rs:653`) is redaction logic, and its own test (`cargo_publish_error_redacts_url_userinfo_from_stderr`, line 954) explicitly notes it must work "regardless of which credential env vars happen to be set in the test process" — the authors already designed around this.

2. **Locale-dependent output classification (low-severity, production, plausible not confirmed).** `classify_cargo_output`/`classify_npm_publish_output`/`classify_twine_output`/`npm_is_published`/`detect_rate_limit`/`detect_auth_failure` (`publish_client.rs:607-763`) all do case-lowered English substring matching (`"already exists"`, `"rate limit"`, `"not logged in"`, `"forbidden"`, etc.) against real subprocess stdout/stderr, and the subprocess is spawned without forcing `LANG=C`/`LC_ALL=C`. If the operator's real publish machine has a non-English locale that changes npm/cargo/twine's message text, classification could misfire (e.g. treat a genuine already-published/rate-limit condition as an unclassified `Other` error). In practice cargo and npm don't localize their CLI error text today and twine's is minimally localized, so likelihood is low — flagging as plausible, not confirmed, since I can't observe real subprocess output from code alone.

3. **`moon_wasm_sandbox.rs` git commits lack a signing guard, unlike its own tag calls (git — out of scope per your framing, noted only because it's the identical bug class in a file you haven't touched yet).** The file already disables tag signing per-call (`&amp;["-c", "tag.gpgSign=false", "tag", ...]`, lines 407 and 679) but its `git commit -q -m "..."` calls (lines 404, 676, inside the shared `run_git` helper at line 300-308) do **not** pass `-c commit.gpgsign=false` or set `GIT_CONFIG_*` env isolation. On a machine with `commit.gpgsign=true` set globally, these `#[tokio::test(flavor = "multi_thread")]` tests would hang the same way the original bug report described (no TTY under nextest). This is a separate, unfixed instance of the exact defect class this session is already fixing elsewhere — I'm not touching it since you scoped git out, but you'll likely want it in the same pass.
