### [Low] Concurrent `callisto add` invocations can silently overwrite each other's changesets

- **Status**: CONFIRMED — traced `generate_human_slug()` through `atomic_write` → `NamedTempFile::persist` → POSIX `rename(2)`
- **Location**: `crates/callisto-cli/src/commands/add.rs:250-276` (slug generation); `crates/callisto-manifests/src/atomic.rs:48` (`temp.persist(path)`)
- **Classification**: Boundary Condition / Concurrent Invocations
- **Root Cause**: `generate_human_slug()` derives the entire slug from a single `SystemTime::now().duration_since(UNIX_EPOCH).as_nanos()` sample, modulo three arrays of 20 elements each (20 × 20 × 20 = 8000 distinct slugs). Two processes launched in the same nanosecond window produce the same slug, targeting the same `.changeset/{slug}.md`. `NamedTempFile::persist(path)` calls `rename(2)` under the hood; `rename` is atomic on POSIX and the last caller wins without error. Both processes exit 0.
- **Failing Scenario**: `callisto add --package a:patch --summary "fix a" &amp; callisto add --package b:patch --summary "fix b"` — parallel CI scripts or developer tooling; both succeed but one changeset entry is silently lost.
- **Verification Strategy**: A test that calls `generate_human_slug()` twice from the same nanosecond (mock `SystemTime`) and asserts distinct slugs — will fail today because the function has no per-process entropy source.

### [Low] `callisto snapshot --tag ""` produces a spec-violating double-dash version without error

- **Status**: CONFIRMED — traced `plan_snapshot` format string through `Version::parse`
- **Location**: `crates/callisto-graph/src/commands/snapshot.rs:23`; no guard in `crates/callisto-cli/src/commands/snapshot.rs`
- **Classification**: Boundary Input / Missing Validation
- **Root Cause**: `plan_snapshot` constructs `format!("0.0.0-{tag}-{sha_short}")` with no empty-string guard on `tag`. With `--tag ""`, this produces `"0.0.0--{sha_short}"`. Semver permits hyphens inside a pre-release identifier, so `Version::parse("0.0.0--abc1234", SemVer)` succeeds. Snapshot versions with a leading hyphen in the pre-release identifier are applied to all manifests without error. Compare: `pre enter` has an explicit guard at `pre.rs:59` (`if tag.trim().is_empty() { return Err(...) }`). `snapshot.rs` has none.
- **Failing Scenario**: `callisto snapshot --tag ""` → all manifests get version `0.0.0--abc1234`, the git tag (if subsequently created) is named `v0.0.0--abc1234`. Process exits 0.
- **Verification Strategy**: Assert that `callisto snapshot --tag ""` exits non-zero and produces an actionable error.

### [Low] `callisto validate --since ""` silently matches all changesets

- **Status**: CONFIRMED — traced the empty-string case through `validate.rs:42-70`
- **Location**: `crates/callisto-graph/src/commands/validate.rs:42-70`
- **Classification**: Boundary Input / Missing Validation
- **Root Cause**: The guard at line 43 only rejects `since` values that start with `-`. An empty string passes the guard. `format!("{since}..HEAD")` → `"..HEAD"`, which git interprets as "all reachable commits". The result is identical to running `validate` with no `--since` flag: all changesets are returned and validated.
- **Failing Scenario**: A CI script uses `--since "$(git rev-parse HEAD^)"` but variable expansion fails, passing `--since ""`. Instead of a validation error or "no changesets in range", all changesets are validated and the result is silently misleading.
- **Verification Strategy**: Assert that `callisto validate --since ""` exits non-zero with an error about invalid ref. Currently exits 0 or 1 depending on changeset validity, never on the invalid input.

### [Low] `--format json --dry-run` output is indistinguishable from a real run in `version`, `snapshot`, `tag`, and `init`

- **Status**: CONFIRMED — traced all seven command JSON output paths
- **Location**: `crates/callisto-cli/src/commands/version.rs:42-43`; `snapshot.rs:48-49`; `tag.rs:62-63`; `init.rs:49-50`; contrast with `add.rs:189-197` (`"dryRun": true` explicitly set) and `pre.rs:23-30` (same)
- **Classification**: Spec Drift / Output Format Inconsistency
- **Root Cause**: `add` and `pre` include a `"dryRun": true` field in their `--format json --dry-run` output. `version`, `snapshot`, `tag`, and `init` do not — they emit the same JSON schema in both real and dry-run modes. A JSON consumer cannot distinguish a version plan that was applied from one that was only computed.
- **Failing Scenario**: A release automation script runs `callisto version --dry-run --format json` to preview, parses the JSON plan, proceeds believing the versions were bumped, and calls `git commit`. The versions were never written because it was a dry run, but the script had no signal to distinguish the two cases.
- **Verification Strategy**: Assert that `callisto version --dry-run --format json` output contains `"dryRun": true`. Currently it does not.

### [Low] `write_json` to stderr in `main.rs` silently discards write failure

- **Status**: CONFIRMED
- **Location**: `crates/callisto-cli/src/main.rs:85`
- **Classification**: Silent Fallback / I/O Safety
- **Root Cause**: `let _res = callisto_cli::output::write_json(&amp;mut std::io::stderr(), &amp;report);` — the `_res` binding explicitly drops the `io::Result`. If stderr is a broken pipe (e.g. `callisto status --format json 2&gt;&amp;1 | head -n 0`), the EPIPE is silently eaten and the structured JSON error is never delivered. The process exits 1, but the consumer sees no output to parse.
- **Failing Scenario**: `callisto status --format json 2&gt;&amp;1 | head -n 0` → the pipe reader exits, writing to stderr returns EPIPE, the error is dropped, the exit code is 1 with no output. A JSON consumer has no structured error to parse.
- **Verification Strategy**: Assert that a write failure to stderr propagates as a secondary error or is at minimum logged. A one-line fix is replacing `let _res =` with a `let _ = ... ;` with an `eprintln!` fallback, or propagating as an additional exit code annotation.
