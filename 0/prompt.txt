# 1. release-please

## Inferred with zero config
Essentially nothing about *which* packages exist. A config file must exist on the default branch; minimum content is one package path:

```json
{ "packages": { "path/to/pkg": {} } }
```
plus `.release-please-manifest.json` containing `{}`. There is **no workspace/package auto-discovery** — paths are always declared. (docs/manifest-releaser.md, "Configfile"; schemas/config.json has no required keys but `packages` is the only functional entry point.)

Once a package is listed, these are inferred:
- **release-type** defaults to `"node"` (which also does package-name lookup from package.json). For Rust you must set `"release-type": "rust"`.
- **Version**: next version derived from conventional commits since the last release PR/tag. `bump-minor-pre-major` and `bump-patch-for-minor-pre-major` both default false → pre-1.0 breaking change goes 0.x → 1.0.0 unless you opt out.
- **Changelog path**: `CHANGELOG.md` (`DEFAULT_CHANGELOG_PATH` in src/strategies/base.ts:46).
- **Changelog host**: `https://github.com`.
- **Changelog sections**: none configured → falls through to the `conventional-changelog-conventionalcommits` preset defaults (src/changelog-notes/default.ts calls `presetFactory({})`). Literal preset table (`DEFAULT_COMMIT_TYPES`): `feat`/`feature` → `Features`, `fix` → `Bug Fixes`, `perf` → `Performance Improvements`, `revert` → `Reverts`, all effect `bump`; `docs`→`Documentation`, `style`→`Styles`, `chore`→`Miscellaneous Chores`, `refactor`→`Code Refactoring`, `test`→`Tests`, `build`→`Build System`, `ci`→`Continuous Integration`, all effect `hidden`.
- **Tag format**: `TagName` renders `${component}${separator}${'v'}${version}`, with `DEFAULT_SEPARATOR = '-'` (src/util/tag-name.ts:19) and `includeComponentInTag` defaulting to **true** (src/strategies/base.ts:152). So default manifest-mode tag is `my-pkg-v1.2.3`; setting `"include-component-in-tag": false` gives `v1.2.3`.
- **PR title**: `DEFAULT_PR_TITLE_PATTERN = 'chore${scope}: release${component} ${version}'` (src/util/pull-request-title.ts:22) → e.g. `chore(main): release foo-bar v1.2.3`. Notably the *same* pattern string is compiled into a parse regex (`generateMatchPattern`), and it warns if a custom pattern omits `${scope}`, `${component}` or `${version}`. Manifest-wide (grouped) PR title constant is `MANIFEST_PULL_REQUEST_TITLE_PATTERN = 'chore: release ${branch}'`.
- **Labels**: `['autorelease: pending']`, release `['autorelease: tagged']`, snapshot `['autorelease: snapshot']`, snooze `'autorelease: snooze'`.
- **separate-pull-requests** false, **plugins** `[]`, **draft** false, **skip-github-release** false.
- Search depths (internal): release 400, commit 500, batch 10.

## Must always be declared, and why
- **Package paths** — release-please reads repo content over the GitHub API, not a local checked-out workspace, so it has no `cargo metadata`/project-graph equivalent to enumerate from.
- **release-type** for anything non-node.
- **`.release-please-manifest.json`** — the record of current versions; it's state, not inference.
- **`bootstrap-sha`** for the first run (bounds how far back commits are parsed); ignored once one release PR exists.
- **Cross-package behavior**: the `cargo-workspace` plugin must be enabled explicitly to build the crate graph, bump dependents, and update `Cargo.lock`. Docs say explicitly: in manifest mode the Rust releaser does *not* update dependencies itself, so `cargo-workspace` "is the recommended way of managing a Rust monorepo with release-please". `linked-versions` likewise must be declared to lock a group to one version.

## Binary release assets
**No.** release-please creates the GitHub release from the tag; it does not build or upload binaries and does not publish to package registries. Asset upload is left to your own workflow step gated on its `release_created` output. No asset-naming templates exist.

# 2. nx release

Config lives under `release` in nx.json; all of it is optional — the defaults below are from `packages/nx/src/command-line/release/config/config.ts`.

## Inferred with zero config
- **Projects**: `getDefaultProjects()` = all projects matching `'*'` filtered to `type === 'lib'` **and** not `"private": true` in package.json. The comment is explicit that `private: true` is treated as "not intended for release" and users override by listing projects.
- **Relationship**: `projectsRelationship` defaults to `'fixed'` (everything released in lockstep).
- **Tag pattern** (literals): fixed `'v{version}'`; independent `'{projectName}@{version}'`; fixed *group* `'{releaseGroupName}-v{version}'`. Chosen automatically from the relationship. `requireSemver` true, `strictPreid` true, `preferDockerVersion` false.
- **Changelog**: workspace changelog on by default at `'{workspaceRoot}/CHANGELOG.md'`, `createRelease: false`, `entryWhenNoChanges: 'This was a version bump only, there were no code changes.'`, renderOptions `{authors: true, applyUsernameToAuthors: true, commitReferences: true, versionTitleDate: true}`. It is **auto-disabled** when there's >1 group, or the single group / workspace is `independent` — i.e. the sensible thing is derived from relationship, not declared. **projectChangelogs default `false`** unless you set any config for them, then defaults `'{projectRoot}/CHANGELOG.md'` with `entryWhenNoChanges: 'This was a version bump only for {projectName} to align it with other projects, there were no code changes.'`.
- **Git**: base defaults `{commit: false, commitMessage: 'chore(release): publish {version}', tag: false, tagMessage: '', stageChanges: false, push: false}`. Version stage overrides `stageChanges: true`. Changelog stage overrides `commit: true, tag: true`, and `push` is **derived**: true iff `createRelease` is enabled anywhere ("We have to perform a git push in order to create a release"). Setting `git.push: false` together with `createRelease` is a hard config error (`GIT_PUSH_FALSE_WITH_CREATE_RELEASE`).
- **Version semantics**: `conventionalCommits` defaults **false**; `specifierSource` default is `'prompt'` (interactive) per nx-schema.json. Turning on `version.conventionalCommits: true` *implies* `currentVersionResolver: 'git-tag'` + `specifierSource: 'conventional-commits'`; setting `versionPlans: true` implies `specifierSource: 'version-plans'`. So you flip one switch and the dependent knobs follow.
- Other version defaults: `updateDependents: 'always'`, `preserveLocalDependencyProtocols: true`, `preserveMatchingDependencyRanges: true`, `logUnchangedProjects: true`, `adjustSemverBumpsForZeroMajorVersion: true`.
- **Conventional-commit type table** ships as `DEFAULT_CONVENTIONAL_COMMITS_CONFIG` (config/conventional-commits.ts) with per-type `semverBump` + changelog title/hidden: `feat` minor "🚀 Features"; `fix` patch "🩹 Fixes"; `perf` none "🔥 Performance" (visible); `refactor`/`docs`/`build`/`types`/`chore`/`examples`/`test`/`style`/`ci`/`revert` all `semverBump: 'none'` and `hidden: true`; plus an `__INVALID__` bucket. User config is merged over this table, so you declare only deltas.
- **Per-ecosystem**: handled by pluggable `versionActions`, default `'@nx/js/src/release/version-actions'` (i.e. npm/package.json is the default implementation; non-JS ecosystems supply their own versionActions module). Docker support is opt-in; `docker: true` expands to `preVersionCommand: 'npx nx run-many -t docker:build'` and versionSchemes `{production: '{currentDate|YYMM.DD}.{shortCommitSha}', hotfix: '{currentDate|YYMM.DD}.{shortCommitSha}-hotfix'}`.

## Must always be declared
- `independent` versioning (default is fixed), and any release groups.
- `conventionalCommits: true` or `versionPlans: true` — otherwise nx prompts interactively, which is useless in CI.
- `projectChangelogs` if you want per-project changelogs.
- `createRelease` if you want GitHub releases; git commit/tag/push flags for the version stage.
- `versionActions` for any non-JS ecosystem — nx cannot infer how to read/write a version out of an arbitrary manifest format.
- **Unconfirmed**: the default `currentVersionResolver` when conventionalCommits is off. The nx schema lists the enum (`registry|disk|git-tag|none`) with no `default`, and I could not locate the fallback in `@nx/js` version-actions. Do not quote a value for this.

## Binary assets
nx release publishes to registries via project `nx-release-publish` targets; GitHub release creation is `changelog.createRelease`. I found **no** binary-artifact naming feature — treat nx as no prior art for asset names.

# 3. Binary artifact naming defaults

## cargo-dist (axodotdev/cargo-dist)
**No name template exists — the convention is hardcoded.** Archive name = release id + variant, where release id is the app (package) name and the variant is `{release_id}-{target_triple}` (`tasks.rs`: `let id = app_name.clone();`, `let variant_id = format!("{release_id}-{target}");`, `let artifact_name = ArtifactId::new(format!("{artifact_dir_name}{artifact_ext}"));`). Extension: `.zip` on Windows, `.tar.xz` elsewhere (docs: "By default we make .zip on windows and .tar.xz elsewhere", configurable only via `windows-archive`/`unix-archive`).

Verified against the real v0.33.0 release assets: `cargo-dist-aarch64-apple-darwin.tar.xz`, `cargo-dist-x86_64-pc-windows-msvc.zip`, each with a sibling `.sha256`, plus `cargo-dist-installer.sh`, `cargo-dist-installer.ps1`, `cargo-dist.rb`, `source.tar.gz`, `sha256.sum`, `dist-manifest.json`. Note: **no version in the asset name** — the tag carries it. (A stale doc-comment in tasks.rs:702 still shows `cargo-dist-v0.1.0-x86_64-pc-windows-msvc.zip`; the shipped artifacts prove the version was dropped.)

Auto-included archive contents are discovered, not declared: README = `package.readme` else `README*`; LICENSE = `package.license-file` else `LICENSE*`/`UNLICENSE*`; CHANGELOG = `CHANGELOG*`/`RELEASES*`, searched in the package dir then inherited from the workspace root.

What cargo-dist *does* require declared: `targets`, `ci`, `installers`, `cargo-dist-version` (`default = <none>`).

## goreleaser
Literal defaults (internal/pipe/archive/archive.go:30-32):
```go
defaultNameTemplateSuffix = `{{ .Version }}_{{ .Os }}_{{ .Arch }}{{ with .Arm }}v{{ . }}{{ end }}{{ with .Mips }}_{{ . }}{{ end }}{{ if not (eq .Amd64 "v1") }}{{ .Amd64 }}{{ end }}`
defaultNameTemplate       = "{{ .ProjectName }}_" + defaultNameTemplateSuffix
defaultBinaryNameTemplate = "{{ .Binary }}_" + defaultNameTemplateSuffix
```
(`.Binary` variant used when `formats` includes `binary`.) Other defaults: `formats: ["tar.gz"]`, archive `id: "default"`, binary name defaults to the project name, and auto-included files default to the globs `license*`, `LICENSE*`, `readme*`, `README*`, `changelog*`, `CHANGELOG*`. Checksums (internal/pipe/checksums/checksums.go): algorithm `sha256`; name template `"{{ .ProjectName }}_{{ .Version }}_checksums.txt"` for the aggregate file, `"{{ .ArtifactName }}.{{ .Algorithm }}"` when split per-artifact. Exposed template vars include `.ProjectName`, `.Binary`, `.Version`, `.Os`, `.Arch`, `.Arm`, `.Mips`, `.Amd64`, `.ArtifactName`, `.Algorithm`.

# 4. Transferable ideas for Callisto

1. **Discover crates from `cargo metadata`; use `publish = false` as the exclusion signal.** nx derives its project set as "all lib projects with a package.json, minus `private: true`" and tells users to override by listing projects explicitly. `publish = false` is the exact Cargo analogue. release-please cannot do this only because it never has the workspace locally — Callisto does, so listing packages in callisto.toml should never be required.
2. **Derive the tag pattern from the versioning mode instead of asking.** nx ships `'v{version}'` for fixed and `'{projectName}@{version}'` for independent, plus `'{releaseGroupName}-v{version}'` for fixed groups. Callisto's existing `callisto@{version}` is already the nx independent convention — make it the computed default, keyed off fixed/independent, not a declared string.
3. **Ship the commit-type → semver + changelog-section table as a built-in that user config patches.** Both tools do this (release-please inherits the conventionalcommits preset; nx ships `DEFAULT_CONVENTIONAL_COMMITS_CONFIG` and merges user deltas). Users should only ever declare the types they want to *change*.
4. **Make the release-PR title one pattern string that both renders and parses.** release-please's `'chore${scope}: release${component} ${version}'` is compiled into a match regex by `generateMatchPattern`, which is how it recovers component/version from an existing PR — and it warns when a custom pattern drops a required placeholder. That gives you PR-state recovery with zero extra config, plus a real guardrail on overrides.
5. **Derive dependent flags rather than requiring consistent pairs.** nx computes `git.push` as "true iff a GitHub release was requested" and hard-errors on the contradictory combination; and `versionPlans: true` / `conventionalCommits: true` each imply the matching `specifierSource`/`currentVersionResolver`. Callisto should apply the same rule: one declared intent expands to its implied switches, contradictions become config errors, not silent no-ops.
6. **Auto-disable things that don't make sense in the chosen mode.** nx turns the workspace changelog off automatically for independent/multi-group setups. Same idea for a fixed-vs-independent Callisto workspace — no flag needed.
7. **Decide the zero-major policy in the tool, not in config.** nx defaults `adjustSemverBumpsForZeroMajorVersion: true`; release-please defaults `bump-minor-pre-major: false` (0.x + breaking → 1.0.0). Pick one and ship it as a default with an override; don't make it a required declaration.
8. **Bump dependents and update `Cargo.lock` by default.** release-please requires the `cargo-workspace` plugin to do this and its own docs call that "the recommended way of managing a Rust monorepo" — i.e. the recommended setup is a non-default. nx defaults `updateDependents: 'always'`. Callisto should make the recommended behavior the default.
9. **Hardcode the binary asset convention; make templates the escape hatch, not the interface.** cargo-dist exposes no naming template at all and ships `{app-name}-{target-triple}.tar.xz` / `.zip` (no version — the tag carries it) with a sibling `.sha256` per asset. goreleaser's template exists, but its default (`{{ .ProjectName }}_{{ .Version }}_{{ .Os }}_{{ .Arch }}…`) is fully derivable. Recommend cargo-dist's shape as Callisto's default since the audience is Rust and target triples are already what `--target` produces.
10. **Auto-include README/LICENSE/CHANGELOG in archives by discovery.** cargo-dist: manifest field first (`package.readme`, `package.license-file`), then glob `README*`, `LICENSE*`/`UNLICENSE*`, `CHANGELOG*`/`RELEASES*`, inheriting from the workspace root when absent in the crate dir. goreleaser globs the same set. Zero declaration.
11. **Support a first-release path instead of requiring pre-seeded version state.** release-please needs `.release-please-manifest.json` plus a `bootstrap-sha` to bound history on the first run. If Callisto reads current versions from `Cargo.toml` (nx's "disk"-style resolution), it avoids that state file entirely — worth being explicit that this is a deliberate advantage.
