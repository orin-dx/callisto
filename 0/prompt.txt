## 1. Public API Consistency

`RegistryClient::is_published` (callisto-model/src/registry.rs:42) and the tag-resolution pair in callisto-graph/src/tags.rs illustrate genuine "looks-alike, behaves-differently" traps:

- `last_tag_for` (tags.rs:85) returns `Result&lt;LastTagSelection, GraphError&gt;` — errors on failure — while `TagIndex::last_tag` (tags.rs:135) returns `Option&lt;&amp;LastTag&gt;` for the *same conceptual lookup*, silently swallowing "no tag found" into `None` with no error path. A contributor extending tag resolution has to read both implementations to know which failure mode applies where; the doc comment at tags.rs:77-84 partially compensates but only for `last_tag_for`.
- Error typing is inconsistent even within one crate: `callisto-model/src/registry.rs` has a proper `thiserror` enum `RegistryError` (RateLimited/AuthFailed/Network/Other), but `Other(String)` is used as an escape hatch in `publish_client.rs` for genuinely distinct failure classes — e.g. line 97 (`Err(RegistryError::Other(format!("npm view failed ambiguously...")))`), line 155 (`unsupported package identity`), and line 180 (`no subprocess publisher configured`). These are three semantically different situations (ambiguous CLI output, unimplemented ecosystem, config gap) all collapsed into the same catch-all variant a caller can't `match` on distinctly, unlike `CommandError`/`ManifestError`/`VcsError` which use precise, matchable variants throughout.

## 4. Error Message Actionability
