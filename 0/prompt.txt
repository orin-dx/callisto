### Claim 1 — silent-empty matrix + validate blind spot: **CONFIRMED**

**Matrix returns nothing, with zero diagnostic, for an undeclared napi-shaped package.**

- `assemble_platform_target_group` (`crates/callisto-graph/src/matrix.rs:304-316`) calls `select_platform_target_source`; when neither `napi.targets` nor `[tool.maturin].targets` is present, it returns `Ok((None, Vec::new()))` — no group, no diagnostics, at all (`matrix.rs:311-316`).
- `build_matrix_report` (`matrix.rs:423-457`) only inserts a `platformTargets` entry when `group` is `Some`, so the package is simply absent from the report. This is confirmed by the existing test `assemble_platform_target_group_empty_array_is_present_not_absent` (`matrix.rs:996-1018`), which only covers the *explicit* `targets: []` case, not "no `napi` key at all."
- This is **documented as intentional design**, not a bug, in `docs/00-design.md:2135-2140`: "A package with no `napi.targets`/... simply has no entry in either map — matrix never synthesizes a placeholder." The design rationale is for packages that genuinely aren't native — it does not address a package that *looks* napi-shaped via other signals (devDependency, build script) but forgot to declare targets. That's a real, uncovered gap.

**No existing "napi-shaped" heuristic exists to detect `@napi-rs/cli`/`napi build` scripts.**

- `detect_npm_role` in `crates/callisto-graph/src/walk.rs:561-613` is the only npm "role inference" logic in the codebase, and it detects something different: whether a `package.json` is a *platform stub* package (generated by napi-rs, has `os`+`cpu` arrays), used to classify `ManifestRole::Platform` for drift-checking. It does not read `devDependencies` or `scripts` at all.
- `grep` across `crates/*/src/*.rs` for `devDependencies`/`@napi-rs/cli`/`"scripts"` turns up only `crates/callisto-manifests/src/npm.rs:263,302` (generic dependency-kind parsing for the dependency graph) — nothing that inspects `devDependencies` values or the `scripts` map for napi-signal detection. So the report's suggestion that this logic "already exists and could be reused" is **not accurate** — it would be genuinely new detection code, though `parse_package_json` (`matrix.rs:66-84`) already gives matrix.rs a parsed `serde_json::Value` it could cheaply extend to check `devDependencies["@napi-rs/cli"]` / `scripts["build"]` matching `napi build`.

**`callisto validate` never touches platform targets at all.**

- `crates/callisto-graph/src/commands/validate.rs:16-159` only builds diagnostics from `.changeset/*.md` files: `EmptyChangeset`, `EmptySummary`, `UnknownPackage`, `InvalidPackageName`, `AmbiguousPackageName` (lines 68-146). It never calls into `matrix.rs`, never reads `package.json`/`pyproject.toml` for napi/maturin shape, and its `is_valid` computation (line 151-153) is purely a function of changeset diagnostics. `crates/callisto-cli/src/commands/validate.rs` is a thin passthrough with no extra logic. So "validation passed despite the gap" isn't a hole in validate's napi check — validate has *no* napi/matrix check whatsoever to have a hole in.

**`DiagnosticCode` has no adjacent variant.** `crates/callisto-model/src/diagnostic.rs:94-176` — the closest entries are `UnrecognisedPlatformTriple` and `DuplicatePlatformTriple`, both fired only once a triple is already declared. Nothing fires when a package looks native-shaped but declares zero triples.

**Maturin/PyPI equivalent gap: CONFIRMED, and detection infrastructure is even thinner.** `select_platform_target_source` (`matrix.rs:260-294`) applies the identical "absent → `None`, no diagnostic" logic symmetrically to `[tool.maturin].targets`. A `grep` for `build-backend`/`requires.*maturin`/`pyo3` across `callisto-graph`/`callisto-manifests` (only hits in `python.rs` test fixtures using `hatchling`/`poetry`, none for `maturin`) confirms there is no "looks maturin-shaped" heuristic anywhere — not even the loose kind `detect_npm_role` provides for napi. The maturin_pyo3_layout test in `walk.rs:1499` is about promoting a *sibling Cargo+PyPI package pair* into the graph (a different feature entirely), not about detecting undeclared maturin targets.

**Fix shapes actually supported by the code:**
- New `DiagnosticCode` variant (e.g. `NapiShapedPackageMissingTargets` / a shared `PlatformShapedPackageMissingTargets` covering both ecosystems), following the existing kebab-case + doc-comment + roundtrip-test pattern already used for every other variant.

### Claim 2 — no reference pipeline pattern / `nativeMatrix` timing: **PARTIALLY CONFIRMED**

**`nativeMatrix` timing, precisely:** `.github/actions/callisto-action/action.yml:154-165`. It is computed inside the `else` branch of `if [[ "$HAS_CHANGESETS" == "true" ]]` (i.e., only on a run with *no* pending changesets) via a direct `callisto matrix --format json | jq ...` call at line 164 — this itself is standalone and doesn't depend on publish state. But it runs as line 164 of a single composite-action shell step (`callisto-orchestrate`, `action.yml:60-228`) that, if `INPUT_PUBLISH` is set, goes straight on to call `callisto publish` at line 186 in the *same* step, with no seam for a caller to inject a separate native-build matrix job in between. So the correction to the raw claim: `nativeMatrix` isn't populated "mid-way through the publish attempt" — it's populated *just before* the publish attempt starts, in the same atomic step, and is never populated at all on a run where changesets are still pending (the version-PR branch never reaches line 164). Either way, the practical problem is the same: this composite action gives no way to pause between "compute nativeMatrix" and "run publish" for a downstream matrix-build job's artifacts to land.

**`callisto matrix` CLI genuinely standalone: CONFIRMED.** `crates/callisto-cli/src/commands/matrix.rs:12-27` — `handle()` just calls `load_workspace` then `callisto_graph::commands::matrix`, with a passing test on a completely empty workspace (`handle_empty_workspace_succeeds`, lines 36-53, exit code 0). `crates/callisto-graph/src/commands/matrix.rs:16-50` confirms the graph-level `matrix()` function reads only manifests off disk via `ws.graph.packages()` — no changeset/version/publish state involved at all. `docs/00-design.md:2168-2177` states this as an explicit design invariant: "`matrix` runs independently, typically once per CI trigger before any version decision exists yet... `matrix` takes no changeset/cascade input at all."

**A reference pattern does partially exist in this repo, but it's broken/incomplete — so "not documented anywhere" is not quite right.** `ARCHITECTURE.md:472-495` shows exactly the two-job `matrix` → `build` pattern the report says is missing, using raw `callisto matrix --format json` in an early standalone job and `needs:`/`fromJSON(...)` to feed a downstream `strategy.matrix` build job — this is the "call `callisto matrix` standalone early" pattern already written down. However:
  - The build job's step invokes `callisto publish-target --package ... --target ...` (line 494), a subcommand that **does not exist** in the CLI (`grep` for `publish-target`/`PublishTarget` across `crates/callisto-cli/src/*.rs` returns nothing; `crates/callisto-cli/src/commands/` only has `publish.rs` and `plan_publish.rs`). `ARCHITECTURE.md:447` itself flags this: "the `callisto publish-target` subcommand described later in this section remain unimplemented."
  - The example stops at per-platform build; it never shows collecting artifacts back and calling `callisto publish` (or `callisto-action`) — the "collect artifacts → publish" half of the pipeline the report is asking about is absent even here.
  - `nativeMatrix` (the callisto-action output) isn't mentioned in this doc pattern at all — the doc example bypasses callisto-action entirely and calls raw `callisto matrix` in its own job, which is in fact the correct workaround, just never connected explicitly to callisto-action's `nativeMatrix` output or reconciled with it.

**No end-to-end example exists anywhere searched:** `grep` for `matrix`/`nativeMatrix` across `README.md`, `ARCHITECTURE.md`, `docs/*.md` turns up only the partial/broken pattern above and prose design rationale — no working matrix→build→collect→publish workflow YAML. `nativeMatrix` itself is referenced only in `action.yml` and internal `.claude/` planning artifacts, never in README/ARCHITECTURE/docs.

**Callisto doesn't dogfood this at all.** The repo has no `package.json`/`pyproject.toml` anywhere (pure Rust workspace), and its own `.github/workflows/callisto-release.yml:69-76` calls `callisto-action` with `publish: "true"` directly in a single job — no matrix/build job, no consumption of `nativeMatrix` output whatsoever. So there's no self-example to point to either.

**Fix shapes:**
- This is **primarily a docs/example gap**, not a required code change: the underlying pieces (`callisto matrix` standalone, `fromJSON(needs.job.outputs.x)` matrix wiring) already work as shown by `ARCHITECTURE.md`'s own partial example and the CLI's demonstrated independence from publish state. A corrected, complete example workflow — call `callisto matrix` in an early job, fan out a real build job (using `callisto build`/existing napi/maturin build tooling instead of the fictional `publish-target`), upload artifacts, then a final job that downloads artifacts and calls `callisto-action`/`callisto publish` — would close most of the gap without touching Rust code.
- One real (small) code/action fix is worth flagging: `callisto-action`'s `nativeMatrix` output is documented as defaulting to `"Empty array"` (`action.yml:51`) but is actually left completely **unset** (empty string, not `"[]"`) whenever changesets are pending, since line 164 is never reached in that branch — a caller doing `fromJSON(steps.x.outputs.nativeMatrix)` in that case would hit a JSON parse error, not get `[]`. That's a minor but genuine action-level correctness bug worth fixing alongside any doc update.
- Whether to also thread `nativeMatrix` computation into a separable, always-populated action step (independent of the changesets/publish branch) is a legitimate design choice for whoever owns the action, but is not required to unblock consumers — "run raw `callisto matrix` standalone, early, in your own job" is already fully supported by the code today and just needs to be written down as the sanctioned pattern, replacing the broken `publish-target`-based example currently in `ARCHITECTURE.md`.
