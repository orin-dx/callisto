• Yes. The “create / update / rotate / supersede” decision belongs in Callisto’s release-PR domain—not scattered through a Bash
  action.

  But it cannot be made from release artifacts alone: whether to create or update depends on external facts such as open PRs, branch
  heads, base SHA, labels, and permissions. The right split is:

  Callisto release plan + GitHub snapshot
                   │
                   ▼
         callisto release-pr decide
                   │
                   ▼
    { create | update | rotate | supersede | noop,
      reason, expected state, intended mutations }
                   │
                   ▼
   GitHub Action executes exactly that decision

  The action should only:

  - authenticate and collect the GitHub snapshot;
  - invoke Callisto;
  - execute the returned mutation request;
  - re-check expected state before mutation to handle races;
  - emit the decision/report.

  Callisto should own:

  - managed-branch identity and naming;
  - which PRs are eligible;
  - ambiguity handling;
  - branch rotation policy;
  - idempotency/fingerprint rules;
  - create vs update vs supersede semantics;
  - a typed JSON release-pr-plan and release-pr-report.

  Changesets has the same conceptual ownership, but packages it inside its action: it keeps a version PR current and exposes its PR
  number as an output. Its GitHub integration uses an API-oriented action implementation rather than a shell workflow rediscovering
  policy. Changesets action (https://github.com/changesets/action/blob/main/version/README.md), Changesets automation model
  (https://github.com/changesets/changesets/blob/main/docs/automating-changesets.md)
