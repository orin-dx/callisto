## The design decisions needed first

1. A plan must be an immutable intent, not a mutable status file.

   Define three separate concepts:

   - `ReleaseIntent`: what was approved to happen, with an exact semantic snapshot.
   - `ReleaseReceipt`: what was actually attempted and its terminal outcome.
   - `ReconciledReleasePlan`: a derived, read-only answer to “which downstream tag/release operations remain eligible?”

   This resolves the interruption bug cleanly. A tag or GitHub release is eligible only when every exact prerequisite operation has a terminal-success receipt—not merely “is not failed.” The present logic can treat unattempted operations as successful, and can retain a release that has no corresponding successful publish attempt ([publish.rs](/Users/gabe/Projects/callisto/crates/callisto-graph/src/commands/publish.rs:723)).

2. Identity must be exact and operation-level.

   `PackageId::matches` intentionally supports bare-name/wildcard semantics in polyglot contexts. That is useful for selection, but unsafe for authorizing a release operation. The durable model needs an exact `ReleaseOperationId`, including ecosystem, registry target, package identity, version, and operation role.

   A package version might entail Cargo, npm, PyPI, tag, and GitHub-release operations. “Package succeeded” is too weak an invariant.

3. Source binding needs a platform-neutral core and platform-specific evidence.

   A Git commit SHA establishes source identity, not signer identity. Keep these distinct:

   - Core `SourceIdentity`: Git commit, or potentially a content digest for hermetic/non-Git build contexts.
   - Adapter evidence: GitHub attestation, signature, protected-environment approval, etc.
   - Policy: whether evidence is optional, required, or unavailable for a given execution profile.

   This respects the architecture’s stated forge/build-system independence while allowing GitHub’s environment protection to be a strong adapter-level control ([ARCHITECTURE.md](/Users/gabe/Projects/callisto/ARCHITECTURE.md:360)).

4. The durable artifact must not contain raw registry endpoints.

   This is more serious than the proposed “secret scan.” Existing plan types serialize optional registry/index URLs ([plan.rs](/Users/gabe/Projects/callisto/crates/callisto-model/src/plan.rs:59)). A URL can embed credentials in userinfo or query parameters. “It came from repository config rather than environment” does not make it safe to persist in an artifact.

   The intent should carry a stable `RegistryKey`, not a resolved endpoint. Resolve the endpoint only during validated execution, after approval. If an endpoint must be di<truncated omitted_approx_tokens="867" /> fatal, and GitHub release creation is currently explicitly swallowed with `|| true` ([callisto-action](/Users/gabe/Projects/callisto/.github/actions/callisto-action/action.yml:212)).
- The durable-plan proposal’s field-source secret check would miss credential-bearing configured URLs. Make secrets impossible in the durable type instead.

For advisory reproducibility, `cargo-deny` already supports configuring an advisory `db-path`, and `--disable-fetch` lets CI ensure it audits a specific prepared checkout rather than silently fetching a different revision. That supports a single wrapper that fetches/records the database revision, then audits that exact checkout ([cargo-deny advisory configuration](https://embarkstudios.github.io/cargo-deny/checks/advisories/cfg.html)). The exception registry should also have one source of truth. A second structured exception file alongside independent `deny.toml` ignores will drift. ## 006 needs a product decision, not another validation rule

The current prerelease model uses snapshot keys that are inconsistent across readers, and bare package-name semantics are intentionally ambiguous in a polyglot workspace. Before implementing “abandoned” or group-conflict behavior, centralize the canonical prerelease member key.

Then choose one model deliberately:

- **Workspace-global prerelease shaping:** fixed/linked groups participate in the normal group calculation, then prerelease shaping applies consistently to all resulting versions.
- **Release-set-scoped prerelease authority:** introduce explicit membership as a first-class model. Do not infer it from `initial_versions` presence.

The current proposed “reject qualifying package” behavior is neither: it leaves difficult cases under-specified and becomes unsatisfiable with multiple qualifying packages. Any validation should aggregate all conflicts into one deterministic diagnostic, not fail on whichever package happened to be visited first.

## Crate choices

I would use:

- Existing `atomic_write` and the existing precondition-oriented model; no new persistence framework.
- `sha2` as a direct, explicit dependency for artifact byte digests if not already direct.
- `serde_json_canonicalizer` only if cross-language canonical JSON is a committed requirement.
- `url` only if raw endpoints remain anywhere that needs structural validation/redaction.

I would not use:

- `cargo_metadata` as release truth: Callisto is deliberately polyglot and already has graph/config semantics.
- A direct RustSec integration alongside cargo-deny.
- `cap-std` as part of this release project. It may be worthwhile for a separate filesystem-capability hardening effort, but coupling it here would obscure the release-state design decision.

## 1. Canonicalization must be a requirement decision

I agree: JCS should not be selected merely because it is a standard. The current architecture promises a standalone CLI usable from Bazel, Buck2, Nix, GitHub, GitLab, and local environments ([design](/Users/gabe/Projects/callisto/docs/00-design.md:231)), but it does not yet state that a non-Rust consumer must recompute the semantic digest.

Also, `olpc-cjson` being in `Cargo.lock` is not a strong reason to adopt it: it is transitive through `oci-client`, not a direct Callisto dependency ([Cargo.lock](/Users/gabe/Projects/callisto/Cargo.lock:4503)). Adopting either library into the release protocol is a real public-contract and supply-chain decision.

I would make the foundational spec choose explicitly among these profiles:

| Requirement | Correct mechanism |
|---|---|
| Verify artifact handoff only | SHA-256 over the exact uploaded bytes. No canonical JSON needed. |
| Verify semantic inputs only within Callisto | A versioned, deterministic domain digest transcript—not a serialization accident. |
| Allow arbitrary external tooling to independently reproduce a semantic digest | JCS/RFC 8785, or an explicitly specified length-prefixed binary transcript with test vectors. |

My default recommendation is the middle path: raw-byte SHA-256 for transport plus a versioned, domain-specific digest transcript for semantic inputs. It is simpler, avoids coupling security to JSON serialization details, and can still become cross-language if its byte layout and test vectors are specified.

Use JCS only if the requirement explicitly says that external systems need to produce or verify the digest from JSON. Do not use `olpc-cjson` for a public JSON interchange artifact.

## 2. 006 should cite the concrete behavior—but not prejudge it as a bug

Claude is right that the foundational work must cite the actual behavior:

```rust
let pinned_base = pre.initial_versions.get(id.name()).unwrap_or(&base);
versioning.bump_prerelease(...)
```

In `PreMode::Pre`, `bump_target` applies prerelease shaping to every package it is asked to bump; roster membership only determines whether the original prerelease baseline is pinned ([cascade.rs](/Users/gabe/Projects/callisto/crates/callisto-graph/src/cascade.rs:412)).

However, I would phrase this as a **semantic conflict requiring a product decision**, not automatically a bug. The current 006 draft expressly calls workspace-wide shaping intentional—even for an off-roster package ([SPEC-RELEASE-LANE-POLICY-006.json](/Users/gabe/Projects/callisto/.claude/specs/SPEC-RELEASE-LANE-POLICY-006.json:1)).

The foundation needs a requirement-level choice:

- **Workspace-scoped lane:** every bumped package becomes prerelease-shaped while the lane is active; roster is solely a baseline snapshot. This preserves current behavior.
- **Release-set-scoped lane:** only explicit members are prerelease-shaped. This requires a first-class member identity model, migration of `pre.json`, and reconciliation of the current bare-name key convention.

The existing partial rule—reject only rostered group members while allowing off-roster group members to be prerelease-shaped—does not establish a coherent authority model. It should not become normative accidentally.

That gives the foundational spec a clean, falsifiable contract and prevents both issues from being rediscovered downstream.
