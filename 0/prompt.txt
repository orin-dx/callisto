### 1. Protocol correctness — **CONFIRMED BROKEN**
`lib.rs:16-46` implements four `#[plugin_fn]` exports: `register_extension`, `define_extension_config`, `execute_extension`, `initialize_extension` — the right function *names*. But the wire types don't match moon's actual schema:
- Moon's real `RegisterExtensionInput` has one field, `id: Id` (the configured extension id). Callisto's (`extension.rs:6-8`) requires `moon_version: String`, a field moon never sends. Since it's non-optional/no `#[serde(default)]`, deserialization of moon's real payload will fail outright — `register_extension` cannot succeed against a real moon host, ever.
- Moon's real `RegisterExtensionOutput` is `{name: String, description: Option&lt;String&gt;, plugin_version: String}`. Callisto's (`extension.rs:11-15`) uses `description: &amp;'static str` (not `Option`) and `version` instead of `plugin_version` — field name mismatch will drop/ignore the version on moon's side even if it got that far.
- Moon's real `ExecuteExtensionInput` is `{args, context: MoonContext}`. Callisto's (`extension.rs:57-60`) is `{args, workspace_root: String}` — flat field instead of nested `context`. Deserialization from real moon input fails here too.

This is not a minor drift — the plugin was built against an assumed/imagined schema, never against moon's actual `pdk-api` types (no vendored moon crate exists in Cargo.lock to check against — grep confirms zero `moon_pdk`/`moon-pdk`/`warpgate` deps).

### 2. The exec seam — **CONFIRMED STUBBED / NOT WIRED**
`runner.rs:5-22` (`MoonCommandRunner`) implements `callisto_model::CommandRunner` (trait at `callisto-model/src/exec.rs:6-8`) using `std::process::Command::new(program).output()` directly — plain native subprocess spawning. Moon's real WASM plugins get host exec via a `moon_pdk`-provided `exec_command!` macro built on an extism `#[host_fn] fn exec_command(...)` declaration (confirmed via moon's own `wasm-plugins.mdx` docs). `callisto-moon` depends only on bare `extism-pdk` (Cargo.toml:15) — no `moon_pdk`, no `#[host_fn]` declaration anywhere in the crate (`grep` confirms). `docs/02-library-vs-moon-decision.md:34` explicitly documents this exact requirement and even warns that `std::process::Command` "compiles... it just fails at runtime via std's unsupported PAL shim" under WASI — i.e., the design doc predicted precisely the bug that shipped. The `CommandRunner` seam itself is real and well-placed (used correctly by `locator.rs` and `extension.rs`), but its WASM implementation is a native-process stub, not a host-function bridge. Under real extism/WASI sandboxing this will fail at runtime on the very first `moon project-graph --json` call (`locator.rs:37`), meaning discovery — and everything downstream, including any git-touching command — cannot function.

### 3. Locator — **PLAUSIBLE, architecture is sound but untested**
`locator.rs` shells to `moon project-graph --json` via the (broken) `CommandRunner`, parses into `MoonProjectGraph`, and derives `ProjectRoot`/`DeclaredEdge` by checking `Cargo.toml`/`package.json` existence at each project root (`locator.rs:119-137`, `161-175`) — filesystem existence checks, not a walk, so it avoids the "can't walk the FS in WASM" problem structurally. This mirrors the documented Q1a/Q1b design in `docs/02-library-vs-moon-decision.md:57-58` reasonably faithfully. But it's gated entirely behind item 2's broken exec seam — it can never reach the parsing logic against real moon.

No `panic!()`, no unsafe `.expect()` on external input.
